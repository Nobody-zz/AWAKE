# AWAKE 全局机制核验报告

**核验日期：** 2026-08-27  
**核验性质：** 只读静态审查与本地证据比对  
**审查对象：** AWAKE 当前源码、当前世界书文件、冻结候选包、事件数据、Bannerlord 本地反编译源码  
**本轮结论：** 未修改源码、配置、世界书或冻结候选；未启动 Bannerlord；未同步游戏目录。

## 1. 执行摘要

当前架构已经具备“世界书 → NPC 身份过滤 → 对话 → 结构化命令 → 世界状态”的基本设计意图，但**不能据此判定运行时闭环已经完成**。本轮核验发现：

1. 当前源读取器与实际部署的世界书清单版本不匹配。若把当前源构建直接作为运行版本，世界书初始化存在确定性失败路径。
2. 当前默认 `Rules` 目录没有可被事件注册表消费的即时事件规则；如果产品策略仍要求默认即时事件可用，则事件功能目前没有可触发内容。
3. 身份、年龄、职业、联系人、命令目标、异步结算、周报、事件账本和存档之间存在多处断链或语义错位。
4. 已核对的 Bannerlord 原版年龄、关系、家族关系、职业和技能事实，与 AWAKE 自定义能力规则并不等价，后续实现不能把自定义规则写成原版机制。
5. 当前 `dist` 与游戏目录的冻结 DLL 不是当前源 DLL；没有匹配当前源构建的 E4 游戏日志，也没有 E5 存档/重启/读档证据。因此静态发现不能直接等同于冻结候选的实际游戏表现。

**总判断：** 当前更适合进入“修复契约和闭环缺口”的阶段，不适合宣布世界知识、事件或命令系统已经完成，也不适合仅凭编译结果安排大规模实机测试。

## 2. 证据分层与边界

本报告使用以下证据等级：

- **A｜原版事实：** 来自本机 Bannerlord v1.3.15 对应的反编译源码；只说明原版代码中的事实。
- **B｜当前源代码事实：** 来自 AWAKE 当前 `src`、`ModuleData` 与工具文件；说明当前源码会如何运行或如何尝试运行。
- **C｜冻结候选事实：** 来自 `dist` 与游戏目录中现有冻结文件；只说明文件状态，不自动证明运行表现。
- **D｜运行推断：** 根据 B、C 推导出的风险；没有 E4/E5 日志时，不应写成已在游戏内发生。

凡是没有匹配版本的游戏日志支持的结论，均不作为“已实机验证”。

## 4. 世界书加载与知识调取

### P0-1｜源读取器与实际世界书格式不匹配

**证据链：**

1. `WorldbookRuntime` 只接受 `awake.worldbook.registry.v1` 或 `awake.worldbook.v2`。
2. `WorldKnowledgeLoader` 明确拒绝 `v1`。
3. 战役准备阶段在 `ProbeExtension` 中实际调用世界书初始化。
4. 当前三处世界书 `manifest.json` 仍声明：

```text
schemaVersion = awake.worldbook.v1
SHA-256 = 2115664E1BB6BB26E63D8CB2097B891B51C03A00504D76DF6F8520FD9448468A
```

5. 三处均没有当前 v2 路径所需的：

```text
runtime.json
index.json
package-manifest.json
```

三处各有 `759` 个 JSON、`335` 个 rules、`415` 个 personality/background 文件，但数量相同不代表读取契约相同。

**影响：** 若当前源 DLL进入游戏，世界书初始化可能失败，`WorldbookRuntime.Knowledge` 保持为空，NPC 知识决策被阻断，并退回“没有可靠说法/没有听说过”等兜底表达。旧 `WorldbookLoader` 虽然存在，但没有证据表明它已形成当前 `WorldbookRuntime` 的有效 fallback 路径。

**证据等级：** B 确定；对冻结候选的实际表现为 D，等待匹配 E4。

**处理建议：** 先确定唯一权威世界书契约，再让读取器兼容该契约；不要通过同时保留多条未定义的读取路径来掩盖版本错配。若仍需兼容旧格式，必须明确“迁移器”和“运行时格式”各自的职责，并为失败状态提供可见诊断。

### P1-1｜无关键词时可能绕过普通 AI 对话

`WorldKnowledgeQueryService.FindCandidates()` 对非空文本主要做关键词匹配；无命中时返回 `not_found`。`WorldKnowledgeDecision.AllowsAi` 只允许 `known/partial` 且有正文时调用 AI。

**风险：** NPC 询问一个世界书没有关键词覆盖、但本来可以进行普通社会交流的问题时，可能直接返回“我没听说过”，而不是继续普通对话、请求澄清或根据已知身份进行有限回答。

**建议：** 将“没有检索到世界知识”与“禁止进入 AI 对话”分离。前者应成为上下文缺失状态，后者必须由权限、内容安全或明确的领域规则决定。

### P1-2｜年龄没有完整进入知识查询

对话构造 `WorldbookQuery` 时没有设置 `Age`；`BannerlordWorldbookIdentityAdapter.Apply()` 也没有把 fallback 年龄写入 `query.Age`。但 `WorldbookIdentityEvaluator` 的年龄条件依赖 `query.Age`。

**影响：** 贵族年龄层、`MinAge`、`MaxAge` 等知识权限规则不能可靠触发。

### P1-3｜未知年龄被默认成 30

`AwakeNpcTarget` 在年龄读取失败或年龄小于等于 0 时使用 `30`。这会把“未知年龄”当作普通成年角色，和项目中“年龄无法确认时不能满足成人门控”的安全规则冲突。

**建议：** 使用显式的 `Unknown` 状态。未知不能自动满足年龄下限；需要成人门控时必须拒绝或转入无法确认分支。

### P1-4｜原版职业名称与 AWAKE 规则名不一致

Bannerlord 原版职业返回值包括 `GoodsTrader`、`RansomBroker`、`RuralNotable` 等；当前 AWAKE 规则期待 `goods_trader`、`ransom_broker`、`rural_notable`。现有规范化只处理小写、空格和连字符，没有可靠处理 PascalCase 拆分。

**影响：** 公证商人、赎金经纪人、头人、士兵等知识能力映射可能不命中。

**建议：** 建立显式原版枚举到 AWAKE 稳定身份能力的映射表，不要依赖字符串猜测；映射表应记录原版值、中文显示名、AWAKE 内部 ID、适用版本和验证来源。

### P1-5｜英雄身份刷新存在 `hero:` 前缀错配

`AwakeNpcTarget.FromHero()` 生成 `hero:<StringId>`，而 `NpcDialogueService.RefreshHeroInfo()` 使用原始 `hero.StringId` 比较。英雄的文化、王国、聚落、族长状态、技能和年龄等字段可能无法刷新到服务内部字段。

**建议：** 所有身份引用统一使用一个稳定 ID 规范；显示 ID、实体 ID 和联系人 ID 不得各自拼接而没有统一解析器。

### P1-6｜无名 NPC 联系键可能串接

场景 NPC 的稳定 ID 含 AgentIndex，但 `ResolveContactKey()` 会移除 `:a<AgentIndex>`。因此不同无名 NPC 之间存在 transcript/contact 记录串接风险。

目前只能确认联系人或对话记录层面的风险，不能扩大断言为所有 memory、relationship 都必然串接。

### P1-7｜当前检索是线性扫描，不适合长期扩容

知识查询主要依赖关键词索引并扫描候选条目。当前规模尚可用于离线审查，但随着多世界观、内容包和多语言词条增加，查询成本、重复命中和排序不稳定性会逐步放大。

**建议：** 先保证契约闭环，再引入编译期索引：领域、实体、地点、身份、时代、关键词和表达层级分别建立倒排索引；运行时只读取已过滤的候选，不在对话线程全量扫描。

## 5. Bannerlord 原版数值与 AWAKE 自定义规则

以下结论来自本机 v1.3.15 对应反编译源码，不能与 AWAKE 自定义规则混写。

### 5.1 原版年龄模型｜A

`DefaultAgeModel` 的关键年龄节点为：

```text
婴儿：3
儿童：6
少年：14
成年：18
中年：35
老年：55
最大年龄：128
```

`Hero.Age` 根据生日、死亡日和当前战役时间动态计算，不是一个应被 AWAKE 永久复制的静态字段。

### 5.2 原版关系｜A

```text
数值范围：-100..100
敌对边界：小于 -25
友好边界：大于 50
-25 与 50 仍属于边界内的中立区间
GetRelation()：有效关系
GetBaseHeroRelation()：基础关系
```

### 5.3 原版家族关系｜A

`Clan.GetRelationWithClan()`直接使用双方族长关系。当前没有证据证明原版存在一个独立持久的“家族内部家庭成员好感”字段。

因此不能把家族聚合关系复制成每个成员的个人关系，也不能把“族长更换后的家族关系变化”写成原版已有的独立成员关系系统。

### 5.4 原版职业｜A

原版 `Occupation` 包括：

```text
Tavernkeeper
Lord
GoodsTrader
Villager
Soldier
Townsfolk
RansomBroker
Merchant
Headman
RuralNotable
Guard
CaravanGuard
```

这些是原版职业枚举，不等于 AWAKE 的知识身份层级。

### 5.5 原版技能｜A

原版有 `Steward`，没有独立的 `Management` 技能。因此 `management = steward` 只能作为 AWAKE 自定义别名或映射规则，不能写成原版字段。

### 5.6 AWAKE 自定义规则｜B

以下均属于 AWAKE 设计，不是 Bannerlord 原版事实：

- `trust`、`love`、`hostility` 三条关系维度各自限制在 `-100..100`。
- 贵族知识年龄层采用 AWAKE 自定义阈值 `18 / 25 / 45`。
- `Steward/Management >= 80` 时提高贵族知识详细度。
- `local / regional / national / faction / elite / private` 是 AWAKE 的知识范围层级。
- `rumor / summary / detail / secret` 是 AWAKE 的表达详细度层级。
- 普通平民、头人、商人、酒馆老板、赎金经纪人、士兵和贵族的知识映射均为 AWAKE 规则。

后续规则文件必须显式标注“原版输入”与“AWAKE 计算结果”，避免编辑者或 AI 将自定义阈值误认为游戏原版数值。

## 6. 社交、命令与世界状态闭环

### P1-8｜原版 NativeSocial 读取器没有接入有效消费者

`BannerlordNativeSocialReader` 已能读取原版基础关系、有效关系、敌友状态、家族关系和家庭拓扑，但当前源码没有发现这些数据进入 NPC Prompt、关系结算、主动行为或 UI 的有效消费者。

当前 AWAKE 关系命令写入的是独立自定义状态，不能把它当成原版 `Hero.GetRelation()` 的替代品。

**建议：** 明确两条边界：原版关系是输入/依据，AWAKE 关系是自定义层；如果需要双向同步，必须单独定义同步方向、冲突策略和存档语义。

### P1-9｜世界事件命令的结果键错配

公开命令为 `awake.world.effect.record.v1`，但适配器实际入队 `awake.world.events.append`；`WorldCommandBridge` 按公开命令查询结果，而 `WorldStateStore` 按实际入队命令记录结果。

**可能结果：** 事件实际写入 Store，但 Bridge 找不到对应 owner result，调用方收到 `awake.world_state.write_pending`。

这属于命令契约不一致，应在命令注册表中为“公开命令 ID、内部队列 ID、结果 ID、最终事件 ID”建立显式映射，不能让调用方通过字符串猜测。

### P1-10｜金币命令的成功语义不准确

公开 `give_gold.v1` 只进入队列，实际扣款在后续 Tick 的多阶段结算中完成，阶段包括：

```text
awake.interactions.index.update.v1
awake.action.give_gold.pending.v1
awake.action.give_gold.complete.v1
awake.action.give_gold.compensated.v1
```

因此当前 `Succeeded` 不能直接解释为“金币已经成功扣除”。命令结果至少要区分 `accepted`、`pending`、`committed`、`compensated` 和 `rejected`。

### P1-11｜多个入口忽略 `EnsureWorldStateReadyAsync()`返回值

该方法失败时返回 `false`，但 NPC 对话命令、事件效果和 NPC `EnsureReadyAsync()` 等路径只等待而不判断结果。

**影响：** 依赖世界状态的后续处理可能在状态未准备好时继续运行，形成“表面成功、实际没有可用状态”的隐性失败。

### P1-12｜AI 回复完成早于命令结算

当前顺序为：

```text
AI 回复完成
→ 写入历史
→ FinishTurn
→ PushTurnCompleted
→ 异步执行命令
```

成功命令又被统一显示为“关系变化”和“对方的态度有了变化”。这会误报世界事件、承诺、金币等非关系命令，也会让玩家在命令尚未结算时看到过早结果。

**建议：** 对话轮次至少拆成“文本已生成”和“命令已结算”两个可观察状态；UI、日志和记忆只记录已经提交的结果。

### P1-13｜命令目标没有可靠绑定当前对话主体

输出校验主要检查命令结构、ID 格式、参数类型、数值范围和文本长度，没有发现当前入口把关系、金币、承诺等目标绑定到当前 `_heroId` 或实际可交互对象。

**风险：** AI 输出合法格式但指向另一个实体时，仍可能进入命令层。目标绑定应由代码根据当前会话上下文强制设置或拒绝覆盖。

### P2-1｜`promise_update` 未进入 NPC 对话白名单

该命令已经注册并实现，但不在 NPC 对话白名单中，因此“承诺系统已实现”不能等同于“NPC 对话可以产生承诺”。

### P2-2｜承诺账本没有形成消费闭环

当前没有证据表明承诺账本稳定进入 NPC Prompt、UI、主动行为或履行调度。存在数据结构不等于 NPC 会记得、会追问或会根据承诺行动。

### P2-3｜`_resultLedger`没有持久化契约

`_resultLedger`只在内存中维护，没有 `SyncData` 或 Store 持久化。重启或读档后，命令结果查询可能丢失。

### P2-4｜`SnapshotToken`不是世界状态快照

当前 `SnapshotToken`只哈希命令 ID 和规范化参数，不能证明世界状态在某个时刻的实际内容。它可以作为请求去重或审计标识，但不能作为完整状态版本号。

### P2-5｜世界事件绕过内存 Ledger

事件命令直接写 `WorldStateStore`，正常事件路径则经过 `WorldEventLedger`。周报和收件箱读取内存 Ledger，因此可能出现“已落盘但当前会话周报/收件箱不可见”。

## 7. 事件、周报与时间处理

### P0-2｜默认即时事件没有可触发内容

当前 `ModuleData\Rules` 只有 `README.md`；`AwakeRuleRegistry` 只扫描该目录下的 JSON；`AwakeEventEngine` 只从 Registry 中读取 `payload.kind == event`；`event_data\EventRecords.json` 为空数组。

`event_data` 下的开场摘要不是事件规则，也没有证据表明当前事件 Registry 会消费它们。AWAKE 工程中也没有发现默认内容包注册即时事件的实际调用者。

**结论：**

- 如果即时事件在当前版本策略中应当启用，这是 P0 的内容/入口缺口。
- 如果即时事件暂时明确不启用，应把状态记为 `not_enabled`，并在 UI、日志和文档中明确，而不是宣称“事件系统已完成”。

### P1-14｜事件引擎存在异步重入与线程边界风险

当前 `_busy` 是普通 `bool`；小时 Tick、链式事件和效果结算使用 fire-and-forget；选择后可能先释放 busy，再异步执行效果和下一个事件；`ConfigureAwait(false)` 后继续读取 Bannerlord 状态。

**风险：** 同一事件链重复进入、效果顺序不稳定、Bannerlord API 在错误线程访问、错误被吞掉或延迟出现。

### P1-15｜事件链规则不完整

- 只有选择 `a` 才推进，`b/discuss` 不推进。
- 链式事件不检查自身 `Condition`。
- 没有明确的链深度限制、循环检测和注册阶段目标验证。

**建议：** 先把事件链定义为显式状态机：每个节点有唯一 ID、条件、可选项、结果、下一节点和终止状态；注册时完成静态校验，运行时保留链实例状态。

### P1-16｜当前周报仍是七日周报

当前 `AwakeEventBehavior` 每七天生成，`WeeklyReportService` 读取最近七天；内容只有政治、经济、文化、战争四段，尚未实现此前讨论的“季度整理、世界概况 → 国家 → 地区”的报告层级。

另外：

- 定时 `Build()` 返回值被丢弃。
- 打开 UI 时重新读取并构建。
- 周报和收件箱在 UI 路径同步调用异步加载。

这违反项目规则中“UI/campaign/tick 路径不得执行阻塞文件、数据库或网络操作”的要求，也会造成重复生成和玩家打开界面时卡顿。

### P1-17｜事件账本加载存在竞态和容量方向问题

`LoadFromStoreAsync()`等待 Store 返回期间，如果有新事件写入内存，加载完成后会直接清空并覆盖这段期间新增的记录。

此外，Store 中事件使用新到旧顺序保存，加载后却从队列头裁剪，超过 50 条时可能丢弃最新记录而保留旧记录。

## 9. 已纠正或暂不列为已确认缺陷的判断

### 9.1 “低身份一定越级读取高详细度文本”暂不成立

当前有效详细度上限经过 `CapabilityMatches()` 检查，因此不能把“低身份直接读取高详细度文本”列为已确认 P1。

残留问题是 `partial` 判断使用 `RequestedDetail` 而不是有效身份上限，可能导致状态标记与实际可见详细度不一致。该问题应作为后续修正项，不应夸大为已经确认的越级读取。

### 9.2 冻结候选的实际表现不能由当前源代码单独证明

由于源 DLL 与 `dist/game` 冻结 DLL 不一致，且缺少匹配 BuildId 的 E4 日志，本报告不会把源代码中的确定性路径直接写成“当前游戏目录已经出现的玩家可见故障”。

### 9.3 原版家族关系不能直接替代个人关系

已经确认原版家族关系读取族长关系，但没有确认一个独立的、可为每个成员直接套用的持久“家庭成员好感”数值。AWAKE 若需要成员基础加成，必须作为自定义计算，并保留个人关系的独立性。

## 10. 建议的修复顺序

本节只确定优先级，不代表本轮已经实施。

### 阶段 A｜先统一运行身份与世界书契约

1. 为源构建生成唯一 BuildId，并同步状态文档。
2. 确定当前唯一运行时世界书格式、版本号和必需文件。
3. 让读取器、编译产物、`dist`、游戏目录和测试包使用同一份契约。
4. 加入启动期可见诊断：版本错配、缺文件、哈希不一致必须明确显示。

### 阶段 B｜修复知识查询的确定性输入

1. 统一实体 ID、英雄 ID、联系人 ID 和场景 NPC ID 的解析方式。
2. 将原版职业、文化、王国、聚落、族长状态、技能和年龄转换为稳定的 AWAKE 查询输入。
3. 未知年龄使用显式未知状态，不能默认 30。
4. 将“知识未命中”与“禁止普通 AI 对话”拆开。
5. 用显式映射表替代职业字符串猜测。

### 阶段 C｜修复命令事务语义

1. 公开命令、内部队列、结果键和事件键建立单一注册表。
2. 所有命令目标由当前会话上下文绑定，AI 不能任意改写主体。
3. 统一 `accepted/pending/committed/compensated/rejected` 状态。
4. AI 文本、命令结算、玩家可见提示和记忆写入按提交顺序发生。
5. 明确原版关系与 AWAKE 自定义关系的输入、写入和冲突策略。

### 阶段 D｜再处理事件、周报和持久化

1. 明确即时事件当前是“启用”还是“未启用”。
2. 事件引擎改为显式串行状态机，加入条件校验、循环检测和错误回收。
3. 事件写入统一经过内存 Ledger 与 Store 的提交路径。
4. 周报生成放到后台/定时阶段，UI 只读取缓存结果。
5. 将周报目标改为季度聚合，并采用摘要分层，避免玩家一次读取过量文本。
6. 为事件、命令结果、承诺和报告建立可存档、可重建的持久化契约。

### 阶段 E｜用证据闭环验证

1. 先以固定 BuildId 构建并同步候选。
2. 用户运行游戏后提供匹配日志，完成 E4：入口、调用、结算、可观察结果。
3. 用新存档、保存、退出、重启、读档完成 E5。
4. 在此之前，不把“类已注册、JSON 可解析、DLL 可编译”视为功能完成。

## 11. 本轮未做事项

- 未修改任何 C#、JSON、XML、配置、世界书或发布文件。
- 未构建新的可交付 DLL。
- 未覆盖游戏目录或测试包。
- 未启动 Bannerlord，也未修改启动器启用状态。
- 未声称冻结候选已经复现全部源码风险。
- 未声称 E4 或 E5 已完成；当前只有既有 E3 同步证据。

## 12. 结论

AWAKE 当前最需要的不是继续增加功能，而是先把以下三件事固定下来：

1. **唯一运行契约：** 当前 DLL、BuildId、世界书版本和同步目标必须能够一一对应。
2. **唯一因果路径：** AI 只能提出意图和候选，代码负责身份过滤、权限检查、命令结算、事件提交和持久化。
3. **可验证闭环：** 每个功能都必须证明“入口 → 调用 → 结算 → 玩家可观察结果 → 存档恢复”，而不是只证明结构存在。

在这三点完成前，继续扩展更多领域系统会放大返工范围。当前应先按 P0 → P1 的顺序收敛契约和闭环，再进入针对具体玩法的增量开发。
