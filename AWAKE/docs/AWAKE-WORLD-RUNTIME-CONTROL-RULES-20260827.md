# AWAKE 世界运行控制规则

**文档类型：** 宏观架构边界与实现前控制规则  
**文档版本：** macro-boundary-v1  
**状态：** 已通过三轮独立反向审查，可作为后续架构和实现的边界  
**日期：** 2026-08-27  
**范围：** AWAKE 对话核心、世界知识、NPC 认知、事件、报告、AI 编排、原版适配、兼容和存档  
**不代表：** 代码已经实现、游戏内闭环已经验证、当前冻结候选已经通过 E4/E5

## 1. 文档定位

本文件不是新的运行时 JSON Schema，也不是新的数值公式。它解决的是现有专项文档之间的上位问题：

- 哪类数据由谁拥有；
- 谁可以请求修改，谁可以实际提交；
- AI、代码、Bannerlord 和第三方模组各自能做什么；
- NPC 认知、玩家知识、世界事件和报告如何分开；
- 一个动作怎样从提案走到可观察结果；
- 发生延迟、失败、重复、读档或第三方修改时如何处理。

本文件与专项文档的关系：

- 大方向历史审查：`AWAKE-BIG-DIRECTION-REVIEW-20260826.md`；
- 原版状态边界：`AWAKE-NativeState-Adapter-Spec-v1.md`；
- 原版数值与 AWAKE 公式：`AWAKE-NativeState-NumericRules-v1.md`；
- 事件记录和现有报告投影：`WORLDBOOK-EVENT-REPORT-CONTRACT-v1.md`；
- 当前代码问题和证据边界：`AWAKE-GLOBAL-MECHANISM-AUDIT-20260827.md`。

专项文档负责具体字段、公式和实现细节；本文件负责防止这些文档互相越权或形成第二套权威。

## 2. 产品方向与首期边界

AWAKE 是建立在 Bannerlord 原版之上的 AI 原生模组。核心体验是：

```text
玩家用自然语言表达意图
→ 系统识别说话行为或行动请求
→ 代码检索允许使用的知识和原版状态
→ AI 在限定上下文内提出表达或行动候选
→ 代码校验权限、目标、条件、成本和时间
→ 原版或 AWAKE 规则完成结算
→ 事件、认知、关系和玩家信息产生对应投影
→ 玩家看到结果，存档在需要时恢复
```

首期优先验证“对话意图 → 知识处理 → 有限社交后果 → 事件/认知记录 → 存档恢复”，不把完整政治、经济、战争、宗教和全 NPC 自主世界模拟作为首期完成条件。

### 2.1 首期执行门禁

本文件为长期边界，但首期实现必须主动收缩：

- 原版状态适配首期默认只读；只有经过独立专项契约和 E4 验证的路径，才允许原版写回。
- AI 提议客观世界事件、玩家内容覆盖、季度报告迁移和第三方正式联动，首期默认未启用；本文件只为后续实现保留边界。
- 首期事件记录只接受原版已确认变化或现有 AWAKE 代码完成的确定性结算，不接受 AI 文字直接升级为事实。
- 首期只验证玩家与个人 NPC 的有限认知变化；队伍、家族、聚落和国家级集体认知只保留作用域接口。
- 首期不要求所有 NPC 长期记忆、后台学习、主动行动或完整世界广播。

“设计上允许”不等于“首期已经启用”；未启用能力必须在实现、配置、日志和验收中明确标记。

## 3. 数据权威与写入边界

### 3.1 总原则

“事实权威”和“写入权限”不是同一件事：

- 原版字段的事实权威属于 Bannerlord 当前运行时；AWAKE 可以通过受控适配器请求原版变更，但不能复制成第二个原版权威。
- AWAKE 自定义状态由 AWAKE 拥有，并通过 AWAKE 自己的提交路径写入。
- AI 输出永远是临时提案，不拥有任何事实或持久状态。
- 第三方模组只能通过公开接口接入，不能直接修改 AWAKE 内部存储。

### 3.2 权威矩阵

| 数据类别 | 事实/状态权威 | 谁可请求修改 | 实际写入路径 | 是否进入存档 | AI 是否可直接写入 |
|---|---|---|---|---|---|
| 原版角色、金币、原版关系、家族、任务 | Bannerlord 当前运行时 | AWAKE 适配器或原版/第三方合法入口 | 原版 API/原版行动结算，之后读回确认 | 由原版保存机制负责 | 否 |
| AWAKE 自定义信任、爱意、敌意、承诺 | AWAKE | AWAKE 代码结算 | AWAKE 状态提交路径 | 是，按版本保存 | 否 |
| 世界书静态设定 | 已启用内容包 | 作者工具、内容包发布流程 | 编译产物和运行时读取器 | 存包 ID、版本、哈希，不默认复制全文 | 否 |
| NPC 认知和记忆 | 对应 NPC 的 AWAKE 存档状态 | 事件、亲历、玩家传授、代码确认的认知提交 | 统一认知提交服务 | 是，按准入规则保存 | 只能提交候选 |
| 玩家已获知识 | 玩家存档 | 游戏交互、事件、报告和玩家确认 | 玩家知识记录 | 是 | 只能提出候选 |
| 玩家内容覆盖 | 玩家明确导出的内容层 | 游戏内编辑或外部编辑器 | 覆盖层导入/导出流程 | 可保存、可导出 | 只能辅助编辑 |
| 世界事件记录 | AWAKE 事件账本或原版已确认变化 | 代码验证后的事件生产者 | 统一事件记录服务 | **必须持久化；只有报告等投影可按事件重建** | 不能直接写事实 |
| 周报、索引、收件箱、摘要缓存 | 派生投影 | 报告服务/索引服务 | 从已提交记录生成 | 原则上可重建 | 只能生成受约束文本 |
| AI 提案、Prompt、临时上下文 | 当前请求 | AI 编排器 | 内存或临时请求记录 | 默认不作为世界事实保存 | 是，但没有写入权 |

### 3.3 原版与 AWAKE 双写规则

如果一个动作同时影响原版和 AWAKE：

```text
AWAKE 提案
→ 代码预检
→ 原版变更或 AWAKE 变更
→ 读回/校验实际结果
→ 写入对应事件和 AWAKE 记录
→ 持久化确认
→ 对玩家显示完成或失败
```

原版已经变更但 AWAKE 记录失败时，不得假装整个动作成功；必须进入“已发生但记录待恢复”的可恢复状态。重试、恢复或补偿必须由具体领域明确支持并使用幂等键；原版副作用不得盲目重试。

## 4. NPC 认知与知识权限

### 4.1 客观事实与认知主张分离

`FactRecord` 表示世界中已经被代码确认的事实。`KnowledgeClaim` 表示某个主体认知中的说法。认知主张可以是错误的，不能反向覆盖客观事实。

认知主张至少需要能表达：

- 主体和主题；
- 内容或指向的事实；
- 亲历、可靠知识、传闻、猜测或误信状态；
- 来源主体或来源事件；
- 获取时间和有效范围；
- 可信度、是否已核验和是否过期；
- 是否允许继续表达或传播。

这些字段是认知模型和元数据，不应全部压成一个“知识等级”数字。

### 4.2 五道权限门与意愿门

权限和 NPC 意愿分开处理：

| 门 | 解决的问题 | 主要责任 |
|---|---|---|
| 检索权 | 这条内容能否进入 NPC 的上下文 | 代码身份/范围/内容权限 |
| 表达权 | NPC 是否有资格说出这一级内容 | 代码详细度和表达层级 |
| 传播权 | NPC 是否能把内容传给其他主体 | 代码渠道、范围和传播规则 |
| 行动依据权 | 该认知能否影响行动 | 代码区分客观前置与主观信念 |
| 玩家观察权 | 玩家能看到事实、传闻、怀疑还是未知 | 代码和 UI 表现层 |
| 表达意愿 | NPC 此刻愿不愿意说、是否敷衍或转介 | 人物决策和受约束的 AI 表达 |

“可以检索”不等于“必须说”，“NPC 相信”不等于“客观事实满足前置条件”，“玩家能观察”也不等于“玩家看到世界真相”。

### 4.3 知识作用域

认知主张的主体作用域应允许：

```text
个人
队伍/团体
家族
聚落
国家/派系
```

首期可以只实现玩家和个人 NPC 的认知记录，但字段和接口不能把未来的集体认知写死成“只有个人”。

### 4.4 长期记忆准入

不是每次对话都生成长期记忆。以下内容才有资格进入长期记录：

- NPC 亲历的重大事件；
- 玩家或重要主体反复传播的内容；
- 会影响关系、利益、危险或后续行动的内容；
- 在较长时间内仍有用的信息；
- 被核验、纠正或明确标记为重要的内容。

普通闲聊、一天内无后果的细节和未被再次使用的临时上下文应留在短期对话状态或直接丢弃。

## 5. 事件、认知和定期报告

### 5.1 事件产生权

客观世界事件只能来自：

- Bannerlord 已确认的动态状态变化；
- AWAKE 代码验证并提交的领域结算；
- 经明确规则允许、且通过代码校验的事件候选；首期默认关闭 AI 直接提出客观事件的能力。

AI 可以提出事件候选、说明文本或叙事表达，但不能凭文字直接制造世界事实。玩家传播的谎言只能产生认知主张、传闻或关系后果。

### 5.2 四种投影

同一件事需要分成不同的读取视图：

1. **客观事件**：记录已经发生什么；
2. **NPC 认知**：某个 NPC 认为自己知道什么；
3. **玩家知识**：玩家实际通过渠道获得什么；
4. **定期报告**：从事件和允许公开的信息中生成的玩家信息视图。

事件不会自动广播到所有 NPC。传播需要考虑距离、身份、渠道、见证、利益和时间。

### 5.3 报告周期和命名

此前讨论的“周报”实际倾向于季度整理。为避免名称和周期冲突，在季度契约冻结前使用“定期世界报告”作为上位称呼。

报告规则必须明确：

- 事实部分只能使用已提交的客观事件；
- 传闻、争议和未知可以出现，但必须有标签；
- 报告不是玩家个人记忆的替代品，而是玩家获取信息的一个渠道；
- 世界概况、国家、地区等层级按摘要优先、主动展开；
- 报告缓存可以重建，不得成为第二份事实来源。

现有七日 `weekly-report.v1` 是历史/现行专项契约，不自动等于最终季度报告契约；迁移前不能混用两者的周期和 schema。

### 5.4 独立准入规则

事件重要性不能作为唯一总开关。长期记忆、报告、AI 上下文和玩家通知应分别判断是否纳入，因为：

- 一个事件可能值得进入报告但不值得写入每个 NPC 记忆；
- 一个私人承诺可能对某个 NPC 很重要但不应进入公共报告；
- 一个短期局部变化可能需要当前对话上下文，却不值得长期保存。

## 6. 命令、时间和结算

### 6.1 命令最小身份

每个可产生副作用的请求至少带有：

- `requestId`；
- `idempotencyKey`；
- 行动者；
- 目标；
- 受益者或受影响者；
- 地点；
- 创建时的游戏时间；
- 创建时的世界版本和相关实体版本；
- 内容包/规则版本。

### 6.2 不把所有状态压成一条直线

命令请求、原版副作用、AWAKE 副作用、持久化和玩家观察是不同状态轨道。它们可以关联，但不能假设所有领域都严格经过同一条线性状态。

请求轨道可使用：

```text
proposed
validated
queued
executing
rejected
cancelled
expired
stale
```

副作用轨道可使用：

```text
host_applied
awake_applied
partial
readback_verified
compensated
failed_unrecoverable
```

持久化和观察轨道可使用：

```text
persisted
observed
```

具体领域只采用适合自己的状态子集，并记录状态间的因果关系。

### 6.3 过时结果

AI 返回或后台任务完成时，必须重新检查：

- 目标是否仍然存在；
- 目标是否仍是原目标；
- 关系、金币、阵营或任务状态是否变化；
- 当前世界版本是否仍匹配；
- 当前权限和内容包是否仍有效。

过时结果只能采取三种处理之一：重新计算、明确拒绝、转入待处理。不能盲目应用。

### 6.4 线程和异步边界

- AI、文件和网络工作不得阻塞 Bannerlord UI、Campaign 或 Tick 路径；
- Bannerlord 状态读取和写回必须在已经核验的安全线程/生命周期执行；
- 异步任务必须可取消、可去重、可报告失败；
- 读档、退出对话或目标消失时，未提交的结果默认失效。

## 7. AI Provider、失败和资源调度

### 7.1 阶段化失败策略

| 失败发生阶段 | 处理原则 |
|---|---|
| AI 提案前 | 没有副作用，可重试、换 Provider 或提示暂不可用 |
| 提案已生成但未提交 | 丢弃、重新校验或要求玩家确认 |
| AWAKE 副作用已提交 | 按 AWAKE 记录和持久化状态恢复，不重复提交 |
| 原版副作用已发生 | 读回确认、记录未同步状态或按领域规则补偿 |
| 结果已显示但持久化失败 | 标记待恢复，不能伪造已保存 |

超时、429、无效 API Key、Provider 切换、格式错误、上下文过长和本地 worker 不可用都必须落入这些阶段规则，而不是统一返回“NPC 拒绝”。

### 7.2 资源服务等级

AI 调度至少区分：

- 玩家当前对话和重要 NPC：高优先级；
- 玩家近期接触的 NPC：普通优先级；
- 后台 NPC 和报告整理：低优先级，可延迟或批处理。

实现前需要固定并发上限、取消规则、去重规则、每轮/每 NPC/每游戏时间段预算和最低服务保证，但暂不在宏观文档中臆造具体数值。

禁止在每个 Tick 无条件调用 AI，也禁止让普通后台请求挤占当前玩家对话。

## 8. 原版和第三方模组兼容等级

### 8.1 四级兼容目标

| 等级 | AWAKE 行为 |
|---|---|
| 共存 | 不读取、不修改对方语义状态，只避免明显冲突 |
| 只读 | 读取原版或对方公开状态，转换为 AWAKE 上下文 |
| 可选适配 | 针对明确版本和明确 API 的专用适配器 |
| 正式联动 | 双方通过公开查询、命令、事件和结果契约联动 |

未知模组默认按共存或只读处理，不假设其内部数据结构，也不把缓存当成当前事实。

### 8.2 外部接入边界

对外只开放最小必要接口：

- 查询当前公开状态；
- 提交候选意图或命令；
- 订阅公开事件；
- 通过明确授权的适配器请求结算。

第三方不得直接写 AWAKE 内部认知、事件账本、关系状态或结果账本。

## 9. 内容包、玩家编辑与存档演进

### 9.1 内容层和认知层分开

以下两个概念不能混淆：

- **玩家内容覆盖**：玩家明确编辑并导出的内容层；
- **玩家/ NPC 认知**：游戏过程中听到、相信、怀疑或记住的内容。

玩家在游戏中说了一句错误的话，不等于修改了世界书；玩家编辑并导出一条世界知识，也不等于所有 NPC 立即知道它。

### 9.2 内容包标识

存档至少应记录已启用内容包的：

- ID；
- 版本；
- 哈希；
- 世界观命名空间；
- 依赖和兼容信息。

内容包缺失、版本不兼容或哈希不匹配时，不能静默把另一套世界观或新版本内容当成旧事实。应安全降级并明确提示。

### 9.3 冲突规则

内容层应采用显式层级和命名空间，不使用“最后加载的一定覆盖”作为隐式规则。至少要能区分：

```text
基础世界观
→ 内容扩展包
→ 玩家明确内容覆盖
```

最终冲突优先级、合并字段和拒绝条件属于实现前的专项契约，不能由 AI 临时裁决。

## 10. 可观察性和玩家反馈

### 10.1 运行追踪

每次重要交互使用关联 ID 追踪：

```text
输入
→ 说话行为/意图分类
→ 检索候选
→ 身份和权限结果
→ AI 提案
→ 代码接受或拒绝原因
→ 结算状态
→ 事件/认知写入
→ 玩家显示
→ 存档结果
```

默认不把完整 Prompt、玩家隐私或 API Key 写入普通日志，也不默认把全部原文外发到云端。调试模式可以在明确开关下记录脱敏摘要和关联 ID。

### 10.2 玩家可见结果

至少区分：

- NPC 角色拒绝；
- 玩家意图不明确；
- 代码权限拒绝；
- 目标已失效；
- AI 暂不可用；
- 等待结算；
- 已完成；
- 已部分完成；
- 已补偿；
- 无法恢复。

技术故障不得伪装成人物拒绝，人物拒绝也不能被显示成系统崩溃。

## 11. 实现前仍需单独冻结的事项

宏观控制规则已经收敛，但以下内容仍需在具体架构或实现计划中定稿：

1. 事件唯一 ID、事件键和命令幂等键的精确格式；
2. NPC 认知的唯一提交路径，以及玩家传授、亲历、事件传播、核验和纠正的合并规则；
3. 基础世界、扩展包、玩家内容覆盖之间的精确冲突优先级；
4. “定期世界报告”的游戏内周期、发布时机、阅读权限和季度窗口；
5. 每层 NPC 的具体 CPU、TOKEN、并发、延迟和最低服务预算；
6. 信任、说服、传闻传播和记忆衰减的具体公式；
7. 现有七日 `weekly-report.v1` 与未来季度报告之间的迁移方式。

这些是下一层契约问题，不应在本文件中被伪装成已经决定的数字或 schema。

## 12. 最小验收场景

后续实现至少要能用以下场景证明规则有效：

1. 玩家向普通平民传播完全错误的战争消息：NPC 可以误信，但客观事件、世界书和报告事实不被污染。
2. 玩家向贵族询问超出年龄、身份或权限范围的知识：NPC 不泄漏详细内容，可给出摘要、传闻、拒答或转介。
3. AI 生成给钱命令后超时：不重复扣款，玩家不会提前看到已完成。
4. AI 等待期间目标死亡、失踪或换阵营：旧结果被重新校验并安全拒绝、重算或转待处理。
5. 第三方模组修改原版关系或金币：AWAKE 重新读取当前原版值，不静默覆盖，也不把旧缓存当新事实。
6. 世界事件在玩家不在场时发生：事件、NPC 认知、玩家知识和定期报告可以按不同时间和渠道分别更新。
7. 内容包切换或缺失：未启用世界观知识不进入 Prompt，旧存档不被静默解释成另一套世界观。
8. AI 或世界书检索不可用：游戏不因一次 AI 失败产生错误世界状态，且玩家能区分系统不可用和 NPC 不愿意。
9. 保存发生在异步结算中间：读档后待结算动作可以恢复、取消或进入明确的可恢复状态。
10. 同一请求重试两次：通过幂等键只产生一次世界副作用。

## 13. 明确的非目标

当前不因为本文件而实施以下内容：

- 全 NPC 独立 AI 和独立向量数据库；
- 完整知识图谱或通用世界模拟 DSL；
- 一开始完成所有政治、经济、战争和宗教规则；
- Universal Mod API 或对所有第三方模组的语义级兼容；
- 为了脱离 AI 而复制完整的非 AI 游戏逻辑；
- 用复杂心理数值替代清晰的身份、事件和行为规则；
- 将完整世界事实、NPC 隐藏知识或调试状态直接展示给普通玩家。

## 14. 结论

AWAKE 的宏观方针可以按本文件收敛：

> **AI 提供理解、认知和表达的开放性；代码、原版运行时和明确内容包分别拥有自己负责的事实与状态；所有跨边界行为必须经过可追踪、可重试、可持久化的结算路径。**

后续工作的正确顺序不是继续添加更多宏观功能，而是：

```text
先冻结上位控制规则
→ 补齐事件 ID、认知提交和内容冲突专项契约
→ 以最小对话闭环实现
→ 用 E4/E5 证据验证
→ 再扩展领域和后台 NPC 行动
```

本文件只完成规则固化，不代表本轮已修改代码、重建 DLL、同步游戏目录或完成实机验证。当前冻结候选的首期实现仍以专项契约中“默认只读、已启用功能最小化”为准。
