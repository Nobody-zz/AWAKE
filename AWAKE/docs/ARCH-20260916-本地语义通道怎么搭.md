## 一、判断（先看这段）

**不用新建任何管线。语义要用的面（`IRagService`）、进程（Runtime Service）、契约（`RetrievalMode.Semantic`）都是现成的；要做的是五处改动，外加把模型打进包。**

⚠️ **两条前提必须说清（09-16 22:4x / 22:5x 补核）：**
① 那个"现成的接入点"所在的链路，**现在没有任何调用方**（见 §二 事实 4）；
② **而且那条链路是旧代、随世界书标准换代作废，不要去接**（见 §二 事实 5）。

三句话：

1. **走进程外 —— 而且不是"要不要走"，是已经在走。** 模组已经在拉起一个独立的 Runtime Service 子进程。
2. **入口不是 `EmbedAsync`，是 `Rag.SearchAsync` 的 `Mode` 参数。** 框架契约里已经写着 `RetrievalMode.Semantic`，服务侧现在**明确拒绝**它。
3. **模型不进游戏进程。** 随模组包分发、由服务进程加载；加载失败就只用字面那一层。**游戏进程一行依赖都不加。**

## 二、已定的五个事实（都有代码出处）

### 事实 1 ·「语义」是契约里声明了、实现里明确拒绝的一格

| 层 | 出处 | 状态 |
|---|---|---|
| 契约 | `MarcusAwakeFramework/src/StorageAndRagApi.cs:8` `enum RetrievalMode { Keyword, Hybrid, Semantic }`（⚠️ 原引 `:11`，枚举声明在 `:8`；09-17 晚核正） | ✅ **公开契约** |
| 请求 | `RagSearchRequest` 的完整构造函数**已含** `RetrievalMode mode` 参数 | ✅ **口子已留** |
| 服务实现 | `SqliteStorageAndRagBackend.cs:149` | ⛔ `if (request.Mode != RetrievalMode.Keyword)` ⇒ `rag.retrieval_mode_unsupported`（`Unsupported`） |
| 业务帧 | `StorageBusinessOperations.cs:232` 硬编码 `RetrievalMode.Keyword` | ⛔ **线上通道连 mode 都传不进来** |

**两条读数：**

- **好的一面**：拒绝是**有声的**（typed `Unsupported`），不是静默当关键词答。这与本项目反复强调的"静默成功最危险"是同一条纪律。
- **差的一面**：业务帧那一层把 mode 丢掉了，所以**就算客户端想传，也没有字段可传**。

⇒ 这一格的性质是「**留了位、明确没实现**」，不是「没人想过」。

### 事实 5 · 不是"一套四层"，是**新旧两代**（09-16 22:5x 甲方纠正后改判）

> ⚠️ **本节改判过一次。** 22:4x 我引下面那份 08-15 的"四层召回"判定"两套 = 一套四层里的一层没接上"。
> **甲方指出该依据已过期**。查证支持这个纠正，故按"新旧两代"重写；旧依据保留存档。
>
> **甲方原话（一字不改）**：当时世界书还是沿用的 AF 世界书标准，与先行世界知识体系标准完全不同了。所以现在没什么用了。

（已作废的旧依据，存档）`docs/AI-Retrieval-Memory-Principles-20260815.md` §一.2：

```
玩家输入/场景词
  → 规则层：精确关键词/身份/文化/地点条件命中（快、确定性）
  → 语义层：Marcus RAG（慢、但语义泛化）
  → 本地回退：倒排索引关键词命中
  → 无命中：不注入，用女神本知/角色本知作答
```

**旧代**（面向 AF 世界书标准）：

| 件 | 内容 |
|---|---|
| 定位 | `docs/AF-BORROWED-IDEAS-LOG.md:16`：世界书检索管线（关键词/短句/语义原型/条件变体/注入上限/命中率），**"计划：`KnowledgeService` 升级"** |
| 内容源 | 同处："自有 schema、**Marcus RAG、四档世界书为唯一内容源**" |
| 实现 | `KnowledgeService` → `_host.Rag`（IPC）＋ `_localIndex`（倒排）；AF 侧对应件是 `KnowledgeLibraryBehavior.cs` |
| 状态 | **从没建成** —— `AWAKE-HalfDone-Inventory-20260816.md:26`：「运行时语料 `awake_knowledge.json` 缺失；内容包语料未接入」 |

**新代**（现行世界知识体系 ＝ worldbook-studio 编译的世界书）：

| 件 | 内容 |
|---|---|
| 载体 | `ModuleData/Worldbook/packages/<pkg>/runtime.json`（458 条；authoring → 编译产物） |
| 实现 | `WorldKnowledgeQueryService`（`WorldbookRuntime.Knowledge`），**模组进程内**，读内存快照做子串匹配 |
| 在跑吗 | ✅ **每轮对话必经、无条件**（`NpcDialogueService.cs:1080`；逐环出处见 `docs/AWAKE-KNOWLEDGE-GATE-20260916.md` §二） |
| 接口 | `IWorldKnowledgeQuery` —— AWAKE 自己的接口，不是框架的 |

⇒ 该文档 §2 的标题是「**半成品：有入口但未闭环**」，开篇写明目的是"避免继续在重复或未接线功能上扩展"。
⇒ 但按新代实况重读：**它记的"语料缺失"应读作"它不再需要那份语料"** —— 世界知识已经换了载体。

**改判后的两条结论：**

1. **"两套"是两代，不是一套里的两层。** 旧代（`KnowledgeService` ＋ Marcus RAG ＋ 倒排）随世界书标准换代作废。
2. **语义要加在新代那条上** —— 即 `WorldKnowledgeQueryService`，**不要去接旧代。**

⇒ 于是 `IRagService` 这个接入点**仍然是最省的一条**，但**理由变了**：
不是"设计里留了位"，而是"**它是现成的、唯一能从模组侧问到服务进程的检索面**"
（另一条路是新开一条数据面 ⇒ 要改框架加槽）。

⇒ 一条仍然成立的老结论：**两条并列、字面是铁证、语义是宽网**（`DESIGN-NOTE` §四）。
它当初是从红测推出来的，不依赖上面那份旧设计，所以**改判不动它**。

⚠️ **一个要处理的细节**：新代查询带身份／文化／王国／聚落／角色／性别／技能条件（`WorldbookQuery` 的入参），
而 `IRagService` 不认识这些 ⇒ 建议**语义只负责召回，身份过滤仍留在模组侧**。

## 四、模型放哪（09-16 22:4x 已定：随包分发）

> ✅ **已定（甲方原话："打包，靠玩家自己装他们自己怕是搞不来"）⇒ 选 (a)：模型随模组发布包分发，由 Runtime Service 加载。**
> 决策记录：`docs/DECISION-20260916-本地模型随包分发.md`。
> 下面三条路的对比保留存档，用于说明 (b)/(c) 为何被排除。

三条路，模型都跑在玩家机器上（"离线可用"是硬约束）；差别只在**模型放在谁的目录里、谁来加载它**。

| | 模型放哪 | 谁加载 | 玩家要不要额外装东西 |
|---|---|---|---|
| **a** | 打进模组发布包 | 我们的 Runtime Service | 不要，装了模组就有 |
| **b** | 玩家自装的推理工具里 | 那个工具 | 要，否则退回关键词 |
| **c** | 不下模型，走云端接口 | —— | 要联网，**违反"离线可用"** |

**（a）模型打进模组发布包。** 体积就是选型表里的数字：`bge-small-zh-v1.5` 约 90 MB、
`gte-small-zh` 同体积、`gte-base-zh` 约 200 MB（见 `docs/LIGHTWEIGHT-EMBEDDING-CANDIDATES-20260916.md`）。
代价：服务进程要**自带** ONNX 运行库的 native 文件和分词实现 ——
这正是 `AF-CRITICAL-EVALUATION-20260815` 记下的坑（自写分词出错时**静默退化成常量向量**，不抛错）。

**（b）模型放在玩家自装的推理工具里**（Ollama 那类，`http://127.0.0.1:11434`），我们的服务侧只发 HTTP。
好处：我们一行模型代码都不写，分词由对方负责；连不上就返回 `Unsupported`，客户端退回关键词。
代价：**不能保证玩家有这个工具**，装了和没装的体验不一致。这个不一致消不掉。

⚠️ **本机实测（09-16）：Ollama 现在没在跑**（`curl 127.0.0.1:11434/api/tags` → 目标计算机积极拒绝）。
⇒ "本机服务会停"是事实，不是假设。开发期要有一条"起服务 → 验 → 关"的固定流程。

> ⚠️ **22:3x 那版我写了"建议 b"，理由是"少写代码、少踩坑"。理由成立，但漏了一步：没有先问目标是要哪种体验。**
> **若目标是"装了模组就该有语义"，答案是 (a)，不是 (b)。** 这条归 §五 第 2 件。

## 五、已定 / 仍待定

### 已定

1. **模型随模组发布包分发**（09-16 22:4x，甲方原话："打包，靠玩家自己装他们自己怕是搞不来"）⇒ §四 (a)。

2. **语义接"新代"那条（`WorldKnowledgeQueryService`），不接旧代（`KnowledgeService` / RAG）**
   （09-16 22:5x 甲方纠正 ＋ §二 事实 5 查证）。

### 工序（**以下四条是建议，未写进任何决定**）

1. **服务侧加载模型，先出一条「文本 → 向量」的自检** —— 先证明这一环活着，再谈检索；
2. **世界书 458 条写进服务侧**，作为检索语料（⚠️ 与旧代的 `awake_knowledge.json` 无关，那是另一份语料）；
3. 服务侧实现 `RetrievalMode.Semantic`；
4. **模组侧在 `WorldKnowledgeQueryService` 里加一路语义召回**，与现有字面召回并列；
   身份／文化／地点等过滤**仍留在模组侧**，不交给服务侧（与"规则层是权威"一致）。

### 仍待定

**分词这一环要先验。** `AF-CRITICAL-EVALUATION-20260815` 记的坑是**自写**分词出错后**静默退化成常量向量**、不抛错。
⇒ 第 1 步的自检不能只看"没报错"，要能证明**两句不同的话算出不同的向量**。
用现成分词库还是自己写，取决于它在服务进程的真实运行时里能不能跑通 —— **这个我还没验**，列入 §七。
