## 1. K4 本地 API 信任边界 —— 不加门

**结论**：接受现状。只要求把「威胁模型 + 接受理由 + 已知后果」写成书面记录，不新增校验、不改会话获取方式。

**理由**（按用户口径执行，补充依据）：

- 该产品是**离线单机工具**，服务只监听回环；攻击面是「本机已有进程」，而本机已有进程本来就能直接读写同一个工作区目录、读取同样的世界书文件 —— 加门并不能减少实际暴露面，只增加复杂度。
- 现状已有多层边界：回环绑定、精确 `Origin` 校验（`WebAiSessionStore.RequireExactOrigin`）、CSRF 会话、`/api/launcher/shutdown` 的 instance-id + HMAC 双重证明。
- 现有本地自动化（`scripts\*.ps1` smoke、CLI、客户验收脚本）依赖当前边界走权威链；加门会波及一批已验证的离线验收路径，收益小于风险。

**落地（批 4，只做记录）**：在安全边界文档与交付说明中写明：会话前提是"本机进程可信"，权威链（register → approve → compile-proof → compile → export）**不防御同机恶意进程**；如需多人/联网场景使用，必须另行设计鉴权。

**已知后果（如实记录）**：同机任意进程伪造 `Origin: http://127.0.0.1:<port>` 即可 bootstrap 会话。

## 2. D1-3 别名如何进运行包 —— 折进 `keywords`

**结论**：把文档的 `aliases`（如"巴拉维诺斯"）与地点锚点一并写入运行包 entry 的 `keywords`，**不扩展 runtime 契约、不改契约版本、不动消费端**。

**理由**（用户表示不熟悉，由执行方定案）：

- 别名与标题同属"玩家/NPC 可能用来检索这个词条的说法"，写进 `keywords` 在语义上就是既有字段的职责，不是新概念。
- 扩 runtime 契约会波及模组本体与冻结产物（属另一会话/发布边界），成本与风险外溢；本批的目标是让"检索查得到"，而不是重构契约。
- 最小改动可直接验证：编译 `pravend-cluster` 后检查运行包 entry 的 `keywords` 是否包含别名与地点锚点。

**代价与配套（必须一起做，避免换来新问题）**：

- 关键词变多会提高"一个词命中多条词条"的概率 → 批 3 必须同时落地 D1-2 的歧义诊断（数量 + 命中条目）。
- 不再把内部文档 id 当作主要关键词（内部 id 不是玩家会用的说法）。

**落地（批 3）**：`RuntimePackageCompiler.BuildEntry` 的 keywords 来源改为「标题（多语言）+ aliases + 地点/实体锚点的可读名称」，内部文档 id 保留但不作为检索词；验收用打包版 CLI 实测。

## 3. B4 Persona 交接 API —— 保留实现，显式标注未启用

**结论**：不接线、不删除。保留代码与测试，在文档与交付说明中显式标注为「实验性、未接入界面」，UI **不提供入口**。

**理由**（用户表示"没看出区别"，由执行方定案）：

- 接线 = 给 Persona Workbench 新建一条真实调用链，属**新功能扩建**，超出"修复批次"范围；而且 PWB 侧没有消费者，接一半比不接更糟。
- 删除 = 丢掉已有测试覆盖与 `integration-smoke.ps1` 的回归价值。
- 项目规则要求"新增服务必须同时接入口与调用方；存在但未调用按 P0"——对**既有**实现，等价的最小合规做法是：要么接线，要么**显式标注未启用**，不允许停留在"存在但没人知道它没接线"。

**落地（批 4）**：

- 交付说明与包内文档写明该 API 未启用、仅用于集成自检；
- 不加入"功能清单/客户可用能力"列表；
- 若后续要给 PWB 用，必须与入口一起交付（入口 + 调用方 + 验收），不得单独放行。

## 5. K5 工作区升级策略 —— 拒绝加载 + 明确提示

**结论**：采用 **fail-closed**：检测到不兼容的工作区（版本高于当前程序理解范围 / 契约不匹配）时**拒绝加载**，并给出人能看懂、能行动的提示；**不自动迁移**，**不做隔离只读**。

**理由**（用户表示不熟悉，由执行方定案）：

- 自动迁移是**不可逆**写操作，一旦理解错版本语义就会破坏用户唯一的正典数据 —— 与"宁阻断不静默修正"的既有原则冲突。
- 隔离只读实现成本高（要引入第二套状态），而收益只是"能打开不能存"，对用户误解的缓解有限。
- 拒绝加载最安全且完全可逆：用户换回旧版 Studio 即可继续工作；新建工作区也能立刻自救。

**落地（批 6）**：

- 明确"工作区版本从哪读、什么条件下判定不兼容、提示文案写什么、如何自救（换回旧版 / 新建工作区 / 先备份）"；
- 提示必须包含**工作区路径**与**程序支持的版本**；
- 禁止静默降级成"能打开但写坏数据"。

## 6. D2 / D7 范围声明

### 6.1 D2 文风归属 —— 自由文本 + 声明，不做受控词表

**结论**：Studio 保持"文风 = 自由文本约束"，**不引入四档受控词表、不做强校验**。四档文风（`卡拉迪亚（炫压抑）`=clean、`黑暗且压抑`=dark、`超绝炫压抑`=extreme、`血腥且压抑`=bloody）归属**消费侧内容规范**（世界书/rules 侧），Studio 只负责"把作者写的约束如实传给 AI 并展示结果"。

**理由**：四档文风的判定标准属内容/发布侧规则，且会随内容迭代变化；把它硬编码进编辑器会造成"改一次内容规范就要改一次程序"，并且会让 Studio 误以为能替作者判定文风合规。

**落地（批 5）**：在作者手册与 README 里写清"文风在这里是自由文本；四档对应关系以内容侧规范为准"。

### 6.2 D7 浏览器支持矩阵 —— 文档声明，不做启动期检测

**结论**：目标环境声明为 **Microsoft Edge / Google Chrome 最新稳定版（Chromium 内核）**；不做启动期能力检测（无 `WEB-*` 门槛逻辑）。

**理由**：这是一个本机单用户工具，浏览器由用户自己启动（启动器自动打开系统默认浏览器）；检测逻辑的成本与误报风险高于收益。遇到不支持的环境时，由页面现有错误提示兜底，并在文档里写明"请改用 Edge/Chrome 最新版"。

**落地（批 5）**：README / 安装说明写明支持矩阵与"不支持时怎么办"。
