## 一、哪些知识值得写（选题）

### 1.1 素材四级（冲突以 A 为准）

| 级 | 来源 | 用法 |
|---|---|---|
| **A 官方** | 游戏本体文本（DB 描述文 / 本地化行） | 中立内核的唯一母本；正文事实一律以它为准 |
| **B 编年史** | Animusforge PlayerExports | 只进**表达层**（身份观感版本）；先过台账质检再可用 |
| **C 模组** | 其他模组文本 | 不主动引入；确需时单独裁定 |
| **D 原创** | 自写内容 | **先登记才合法**；标注 universe/era |

三条坑（都踩过）：
- 官方文本存**两处**：`localization` ＋ `descriptionText`——判"官方没有"之前两处都查。
- B 级变体先过台账：现当代科学视角、空 When 百科腔、与 A 冲突的 → 弃或重写为中世纪口吻。
- 城堡类条目可能没有描述文——没有描述文 ≠ 不存在。

### 1.2 立档条件（三条全占才动手）

1. **有可定位来源**：A 引文（五元组可指回，见 §3.5）或已登记 B 变体。
2. **有调取场景**：说得出"谁、在哪、为什么问"（村民闲聊？商人问行情？贵族密谈？）。说不出的知识先不写。
3. **不与已有档重复**：动手前先 grep docs/ 和名录。同一素材已有档 → 扩表达，不新开档。

### 1.3 优先级（排期口径）

玩家会撞上的先写：**聚落 > 家族/人物 > 兵种/军制 > 重大事件 > 边角概念**。
素材池以台账 + 各批 PLAN 登记，不凭印象开档。

## 二、立哪种档（条目组织法）

### 2.1 档型封闭清单（只有四种，不开第五种）

| 档型 | 判据 | 锚点 | 例 |
|---|---|---|---|
| **实体本档** | 一个实体（聚落/家族/人物/势力/兵种）的核心事实 | entity_ids 挂登记表实体 | `doc.geography.charas-town` |
| **事件档** | 跨实体的关系变更（归属易手/战争/加冕），政治史线 | 可挂参与实体 | `doc.politics.varcheg-swap` |
| **专题档** | 非实体的主题知识（军制/兵器/信仰） | 不写 entity_ids，靠 aliases | `doc.war.crossbow` |
| **秘密档** | 权限特例：低权限绝不可见、需整档 deny 的内容 | 同其宿主实体 | `doc.politics.charas-cortain-secret` |

（探针/测试档只进 workspace 测试区，不进正典库。）

**判据细化（红测一 09-13 补）**：三问对"某聚落的归属沿革"这类单实体历史变更存在判据重叠——40 档实测 13 档有 entity_ids 而在"本档/事件档"两可。裁定消解口径：
- **第一问优先**：内容主体仍是"这个实体是什么样"→ 实体本档/侧档；主体是"归谁/易手/关系变更"且与实体本档调取场景不同 → 事件档（先例：`doc.politics.kachar-ownership`、`doc.politics.varcheg-swap` 均为事件档但挂参与实体锚点，合法）。
- **侧档约定**（现状成文）：slug = 实体名 + 场景后缀（`charas-bay` / `charas-origin-tales`）；锚点可同实体（多档共锚点是常态，town_s1 现挂 5 档）；侧档不承载归属/家族/秘密核心面。

### 2.2 立档三问（按顺序问，问完即知档型）

1. **它属于哪个实体？** → 是：实体本档。每个实体只有一个本档。
2. **它是实体之间的关系或变更？** → 是：事件档。
3. **它是"某类人绝不能看到"的内容？** → 是：秘密档（slug 加 `-secret`）。
   都不是 → **专题档**。

### 2.3 "一实体一档"的准确含义

- 一个实体**只有一个本档**，承载它的核心事实与归属关系。家族=一档：家史、成员、财富事实、与封地的关系，全进本档、档内分层（家族批按此执行；戴·科尔坦 8V 已在素材池）。
- 同一实体按 B4 调取场景可以另立**侧档**（这城什么样 / 这片水什么样 / 传说怎么说），但侧档只写自己场景内的内容，**不承载实体的归属、家族、秘密等核心面**——家族专属内容寄生在聚落档里是本次对账要清的病。
- **多域不双投**：同一素材可按调取场景在多域各立档（域标签非排他），但同一变体只投一处。

### 2.4 反碎片化

- **不为拆而拆**：两块内容若是同一条因果链，合档不同断言，并在闭合复验留痕（先例：吕卡隆银矿档承载一条政治沿革断言，因"合邦→被夺→银矿招兵祸"是一条因果链，不另立 politics 档）。
- 拆分边界：只有"调取场景真的不同"才拆（问城的样子 vs 问这地归谁，是两个场景）。
- 规模硬限：每档断言 1–3 条为宜；**每断言表达 ≤4 条**。

### 2.5 域标签（domain）的用法

domain 是检索与汇总的标签，**不是立档的唯一判据**（判据是立档三问）。已裁定的归属：
- **战争域 = 军制/兵种/兵器等背景知识**；战役事件归政治史线（Max 09-13 裁定）。
- 宗教不单列（并入文化域口径）。
- subdomain 必须在 taxonomy 白名单内，白名单外先扩表再立档。

## 三、怎么写（书写规范）

### 3.1 分层铁律

- **中立内核（assertion）**：纯 A 级事实，不撮合、不分层、不进观点。
- **表达层（expression）**：身份观感。同一件事不同身份知道的程度/说法不同 → 拆表达；**一表达 = 一文本 = 一层**。
- **不变式：每条 grant 的 min_detail 必须等于所在表达 layer**（运行时没有自动闸，违反 = 内容越限泄漏，两引擎都放行——探针 B 实测过）。

### 3.2 权限口径

- **身份上限表**：村民 local·rumor ｜ 市民 regional·summary ｜ 乡绅 regional·detail ｜ 商人/酒馆老板 faction·detail ｜ 士兵/头人 national·detail ｜ 贵族 elite·detail（age<18 rumor / ≥45 secret）。
- 硬门：scope 与 min_detail **双≥**；同维 OR、跨维 AND、空=不限；**Deny > Grant > 继承 > unknown**。
- **deny = 档级核弹，只允许出现在秘密档**，且必须定向到具体身份（禁用 commoner 这类祖链根——noble→notable→commoner 全链继承，会连 50 岁贵族一起炸掉）。
- 秘密档必须有**信息增量**：秘密面 = 政治解读 / 第一人称独白，不是公开文换个层。

### 3.3 口径与译名

- **中世纪口径**：无现当代科学视角词；rumor 类只陈述"说法"本身；推断一律标"待验证"。
- **译名先查后写**：英文精确匹配拿 stringId 再取 CNs（中文 LIKE 静默 0 命中）；正文一律官方名，考据名只进对照表左栏。
- 已裁年代不翻案：达鲁索斯≈950、潘德拉克=1077、登陆≈784、萨兰流放≈984。

### 3.4 命名三层

| 层 | 规则 |
|---|---|
| **slug**（文件名 = doc id 尾段） | 官方英文名 kebab-case；入库不改，要改走全链六步重编译（source_id/entity_id 层不动） |
| **title** | 双语官方名 `{zh-CN: X, en: Y}`，en 不得空 |
| **aliases** | 双语关键词（官方名 + 编年史旧称/俗称）；**必填**——无 aliases = 检索裸奔 |

同类档标题格式统一（先例：军制档统一「X军事力量」；沙拉斯系统一 charas）。

### 3.5 锚点与引文

- entity_ids 只写登记表白名单实体（小写）；概念档不硬挂，靠 aliases 进检索。
- **实体不在登记表 → 先扩表再立档**（红测三 09-13 补：登记表现存 890 实体 = hero 415 / clan 82 / settlement 393，戴·科尔坦等家族查无——家族批开工前须先扩登记表，流程并入 §六"生成"前置）。
- 每条断言 **claim→origin 可指回**，五元组齐全：`source_id + source_version + source_content_hash + locator + quote_hash`。
- A 引文程序化从 DB 拉，不手抄。

### 3.6 身份覆盖（war1 血泪教训）

新档自检时逐身份过一遍：**villager / townsfolk / soldier / merchant / headman / noble 六身份 × 各层是否有 grant 落点**。
漏配 merchant/soldier → 矩阵 not_found（war1 首跑 W10/W11 就栽在这）；无文化门兜底的档尤其要覆盖 soldier（national）与 merchant（faction）。
**覆盖口径以选题稿声明的调取场景为准，不是全员硬覆盖**（红测二 09-13 澄清：若按"每档必须六身份全有 grant"硬读，存量 21 档判违规而矩阵 61/61 全绿——两结论矛盾即口径错了）。传说类（tales）档商人/士兵问不到属预期；选题稿说"商人要能问到"而档里没配，才是违规。自检 v2 的覆盖检查输出**警告级**覆盖表，不判死。

## 四、写了怎么查

### 4.1 运行时检索链路（一条知识被问到的路径）

```
aliases → KeywordIndex 双向子串命中档 → 表达按 grant 匹配
→ SelectExpression 取最高分（culture +20 / kingdom +25 / settlement +30）
→ 返回文本
```

**查不到的排查顺序**：① aliases 有没有？② 有没有匹配 profile×条件的 grant（not_found = 无任何匹配，多半是漏配身份行）？③ 是不是被 deny？④ min_detail 是否 == layer（不变式破 = 语义错乱）？

### 4.2 state 语义（probe 实测口径）

| state | 含义 |
|---|---|
| known | 拿到 ≥ 请求层的文本 |
| partial | 拿到了，但低于请求层（分层封顶，正常形态） |
| blocked | 有 profile 匹配但门不过（deny 或 grant 不匹配） |
| not_found | 无任何 profile×条件匹配（档不可见） |

### 4.3 维护工具箱

| 工具 | 用途 | 备注 |
|---|---|---|
| **probe**（`tools/worldbook-runtime-sim`） | 按身份构造查档 | age 参数不驱动能力，测年龄上限用 detail 键覆写 |
| **矩阵** | 身份×档逐行验收 | 预期先写死 → 跑 → **程序化判定**（非肉眼）；一律以运行时模拟器为准，Studio 投影只作内容预览；**改档/改结构须同步重写 spec 预期**（红测三 09-13 补：secret 档已改版而旧矩阵行基于旧结构，预期过期则矩阵失去验收意义） |
| **越限自检脚本** | 逐表达断言 grant≤上限 + min_detail==layer | 编译后必跑 |
| **名录**（`WORLDBOOK-NAME-INDEX.xlsx`） | slug↔中文名总索引 + 交叉覆盖表 | 生成器 `_gen_name_index_20260913.py`，重跑即刷新；交叉覆盖 = quote_hash 跨档 ≥2 亮警（防重复双投） |
| **台账**（`WORLDBOOK-CHRONICLE-LEDGER`） | B 级素材登记与质检状态 | 新 B 变体先登记后使用 |
| **审查存档**（`docs/review-state/`） | 签收状态 | 先查 userSignoff 再引用结论 |

## 五、质量怎么评

### 5.1 硬门（一票否决，全脚本可查；任何一条不过 = 不进打分）

1. 六步编译 **0 诊断**（validate→register→select→approve→proof→compile，每步新 operation id；compile `--out` 相对工作区根）；
2. 矩阵行与预期一致（以运行时模拟器为准）；
3. `grant.min_detail == 所在表达 layer`（逐条）；
4. grant 不越身份上限（逐条）；
5. deny 只在秘密档且定向（无祖链根 deny）——**自检 v2 已脚本化**（`_selfcheck2_20260913.py`，v1 只查 grants 不查 denies，红测二补）；
6. 每条断言五元组齐全、可指回；
7. 译名已对库核对（正文无考据名裸奔）。

### 5.2 打分表（满分 100；生成后自评，独立审查复评）

| 维度 | 分 | 看什么 |
|---|---|---|
| **内容** | 40 | 来源等级与双源（A 内核 + B 观感）；表达之间有信息增量（不是换皮）；分层差异化成立（同一件事不同身份说法不同）；口径合规（中世纪、rumor 只述说法、推断标"待验证"） |
| **结构** | 25 | 档型归类符合立档三问；身份覆盖六身份×各层有落点；规模在硬限内；同变体不双投 |
| **检索** | 20 | aliases 双语齐全；命名三层一致（slug/title/aliases 同族同格式）；锚点正确（概念不硬挂） |
| **可维护** | 15 | sources 五元组齐全；该留痕的走了 corrections（原值逐字保留）；交叉覆盖表无警 |

### 5.3 等级与处置

| 分 | 等级 | 处置 |
|---|---|---|
| ≥85 | 优 | 入库 |
| 70–84 | 良 | 列小改项，改完即入库 |
| 60–69 | 中 | 列整改清单，下一批一并处理 |
| <60 | 打回 | 重做 |

打分项里能脚本化的（aliases 齐全度、en title 空缺、交叉覆盖警）已挂进名录生成器；**上限/不变式/deny 合规/身份覆盖/规模硬限已挂进自检 v2**（`_selfcheck2_20260913.py`，0 违规 + 警告级覆盖表）；其余先人评，后续逐步脚本化。

## 六、流程（从选题到入库）

```
选题稿（PLAN，含域定义与调取场景）
→ 〔重大批：独立审查 → Max 签收（落 docs/review-state/）〕
→ 生成（B 级素材先过台账）
→ 六步编译（validate→register→select→approve→proof→compile）
→ 矩阵验收（先写预期，程序化判定）
→ 硬门自检（越限脚本 + 名录重刷）
→ 打分（§5.2）
→ corrections_<date> 留痕（改历史产物时；原值逐字保留）
→ 限定路径提交
```

提交纪律：绝不 `git add -A`；add 自己的文件后 `git commit -F - -- <路径>`。
执行中发现章程与实测冲突：**停下回写本章程并报告**，不硬推（沿用 IMPL 先例）。
