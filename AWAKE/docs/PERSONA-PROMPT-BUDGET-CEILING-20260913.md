# Prompt 预算的天花板与合理值

> 2026-09-13 · 只读审计（含本机实测）· 未改任何源码、未提交
> 起因：Max 问「预算是不是给得太吝啬了？几万、十几万才合适点吧？」
> 结论：**方向对——现在只用到天花板的四分之一。但「十几万」是天花板本身，不是目标值；合理值是 64 KB 左右。**

---

## 一、结论先行

| 问题 | 答案 |
|---|---|
| 给少了吗？ | **是。** 当前 `MaxPromptUtf8Bytes = 32768` 字节，只占本地模型能力的 **25.6%** |
| 该给十几万吗？ | **不该。** 127 KB 就是本地 qwen2.5 的**物理天花板**（含输出会爆） |
| 那给多少？ | **65536 字节（翻倍）** 足以覆盖所有分项需求，仍余三到四成 |
| 但提总量能解决问题吗？ | **不能单独解决。** 真正的病是「分项配额太紧」＋「顶格会超载」＋「先砍人味」 |

---

## 二、先把单位弄对：字节 ≠ token

此前所有讨论都在「字节」上，但模型吃的是 **token**。本机实测换算率（`awake-token-ratio.py`）：

| 样本字数 | UTF-8 字节 | prompt tokens | 字节/token |
|---|---|---|---|
| 860 | 2820 | 749 | 3.77 |
| 3440 | 11280 | 2909 | 3.88 |
| 6880 | 22560 | 5789 | 3.90 |
| 8600 | 28200 | 7229 | 3.90 |

⇒ **中文实测 3.9 字节 = 1 token**（即 1 token ≈ 0.84 个汉字）。
（对比英文约 4 字符/token，中文的字节效率低得多——UTF-8 中文一个字 3 字节。）

**换算式：`token ≈ 字节 ÷ 3.9`**

## 三、天花板在哪：实测 Ollama 的 num_ctx

发逐级放大的超长 prompt，看服务端在哪儿截断（`awake-numctx-probe.py`）：

| 实际字节 | prompt tokens | 期望 tokens(÷3.9) | 是否被截 |
|---|---|---|---|
| 7 896 | 2 045 | 2 024 | 否 |
| 15 933 | 4 097 | 4 085 | 否 |
| 31 866 | 8 165 | 8 170 | 否 |
| 63 873 | 16 337 | 16 377 | 否 |
| 99 969 | 25 553 | 25 633 | 否 |
| **139 872** | **32 768** | 35 864 | **是（卡在 32768）** |

**读法**：139872 字节本该是 35864 tokens，实际只吃到 32768 —— 正好卡在 `qwen2.5` 的上下文窗口上限。

⇒ 两个结论：
1. **Ollama 0.23.1 默认 `num_ctx` = 模型的完整窗口**（不是老版本那个 4096 默认值，本机无需担心服务端偷偷截断）。
2. **本地 qwen2.5 的 prompt 天花板 = 32768 tokens ≈ 127 795 字节 ≈ 125 KB。**

### 三条路径的天花板

| 路径 | 窗口(tokens) | 折合中文字节 | 出处 |
|---|---|---|---|
| **本地 qwen2.5（7B）** | 32 768 | **≈ 128 KB** | 本机实测 |
| 本地 gpt-oss（20B） | 131 072 | ≈ 511 KB | `ollama show` |
| **云端 gpt-4o-mini**（MCM 默认） | 128 000 | ≈ 499 KB | 模型规格 |

**最弱的一环是本地 7B：128 KB。** 跨两条路径都能跑的配置，必须按这一条定。

> ⚠️ 还要扣掉**输出预留**：`num_ctx` 要同时装 prompt 和回答。按回话 600–2000 tokens 算，prompt 实际可用约 **120 KB**。

## 四、当前预算站在哪

```
当前 MaxPromptUtf8Bytes = 32 768 字节
                      ≈  8 402 tokens
                      ≈  本地天花板的 25.6%
```

**一句话：现在只用了四分之一。**

> 附带一个**待验证的推测**：`32768` 这个数恰好等于 qwen 系模型的 token 窗口（32768）。看起来像是**把 token 数当字节数写进去了**——同一个数字，单位错了一档。标记为推测，需向原作者（codex 线）确认，不作为结论。

## 六、但提总量本身解决不了问题（三条才是真病灶）

### ① 分项配额太紧 —— 这才是「吝啬」的直接体现

persona 给 4096，而卡的自然长度中位数 4068、最长 8640。
⇒ **46.1% 的卡装不下**，31 张报 `mandatory_budget_exceeded`（连强制段都砍）。
检索块同样 4096。**"吝啬"感就来自这两个数，不来自总池。**

### ② 顶格时总池会超载 —— 而且砍的是玩家的话

各块按配额**顶格**合计 **35 422 > 32 768**（超 2 654）。

一旦超线，`TruncationOrder` 第一个砍 **`player_turn`（玩家原话）**
⇒ **NPC 答非所问**。这是现在就有、只是没人撞上的隐患。

### ③ 截断从尾部砍 —— 先死的是「人味」

DSL 段序把 `[PERSONALITY_PRIVATE]`（私我）`[PERSONALITY_CONTRADICTION]`（底线）
`[CURRENT_IDENTITY]`（当下身份）排在**最后**。

实测 4096 档：`CURRENT_IDENTITY` **100% 丢失**、`CONTRADICTION` **71% 丢失**、`PRIVATE` **23% 丢失**。

⇒ **加预算是「缓解」，不改段序就只是让「表演层」更长。**
（详见 `PERSONA-DSL-BUDGET-AUDIT-20260913.md` §三）

## 七、不能无脑给：三个反方向的力

### 1. 成本（云端路径）

MCM 默认走云端（`ProviderIsCloud = true`、`gpt-4o-mini`），**prompt 长度直接等于钱**。

| prompt | tokens/次 | 相对成本 |
|---|---|---|
| 32 KB（现在） | ≈ 8 400 | 1× |
| 64 KB | ≈ 16 800 | 2× |
| 128 KB | ≈ 33 600 | 4× |

绝对量级很小（gpt-4o-mini 输入约 $0.15/百万 tokens ⇒ 每次对话不到半分钱），**成本不是反对理由**。

### 2. 延迟（本地路径）—— 这才是真约束

prompt eval 时间随 tokens 线性增长。本机 7B 实测：一次 25 553 tokens 的 prefill 就要几十秒。
⇒ **本地跑 128 KB 的 prompt，玩家要等半分钟才听到 NPC 回一句话。** 游戏体验直接崩。

### 3. 质量：注意力稀释

长上下文有已知的「lost in the middle」效应——**关键信息埋在中间会被忽略**。
我们现在的关键信息（底线、私我）恰好排在**尾部**（虽然被砍），改成合理长度后也会落在中段。
⇒ **加长度不等于加效果，且可能反而稀释。**

### 4. 还有一层：内容根本不够长

典型对话实测总 prompt 只用 **14 971 字节**（余额 17 797）。
**池子加大不会自动填满** —— 内容就那么多。
⇒ 「提总池」的收益是**间接的**：它的作用是**让各分项能同时放宽**，不是它自己有用。

## 八、建议（按优先级）

| # | 动作 | 效果 | 代价 |
|---|---|---|---|
| **1** | persona 4096 → **10240** | 截断 46% → 0% | 极低（总量仍余 11758） |
| **2** | 段序：`CONTRADICTION`/`PRIVATE` 提到 `PUBLIC` 之前 | 不加字节就救回「人味」 | 纯代码顺序 |
| **3** | 检索块 4096 → **8192** | 世界书装得下 | 低 |
| **4** | 总池 32768 → **65536** | 解锁 ①②③ 同时放宽 + 消除顶格超载 | 云端成本 ×2；本地延迟上升 |
| **5** | 压 `selfClaimExamples` | 又占地方又制造复读源 | 需动卡内容格式 |

**核心建议：先做 ①②③（都不动总池），再评估 ④。**
如果 ①②③ 做完后实机效果已明显改善，总池可以只提到 49152 而不必翻倍。

**不建议**：直接拉到 128 KB。它恰好等于本地天花板，等于没有输出余量，且会让本地延迟崩坏。

## 九、边界与待验证

1. 本审计**未改任何源码**；`MaxPromptUtf8Bytes = 32768` 仍在代码里。
2. 换算率 3.9 字节/token 是**本机 qwen2.5 tokenizer 实测**。换模型会变（不同 tokenizer 对中文的压缩率不同），量级不会差太多。
3. 天花板实测**只测了 qwen2.5**。gpt-oss / 云端的窗口值取自 `ollama show` 与模型规格，未实测。
4. 测试样本为**重复同一段中文**。重复文本可能触发 tokenizer 的额外压缩优化 ⇒ 换算率可能略偏乐观。**标为待验证。**
5. 「32768 疑似单位混淆」是**推测**，需向 codex 线确认。
