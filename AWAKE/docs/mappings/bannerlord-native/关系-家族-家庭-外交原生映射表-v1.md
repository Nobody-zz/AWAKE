## 二、核心关系数值

### 2.1 基础角色关系：唯一原生持久关系表

| 项目 | 原生实现 | 数值/默认值 | 存档归属 | 语义 |
|---|---|---:|---|---|
| 关系容器 | `CharacterRelationManager.HeroRelations._relations` | `Dictionary<long, Dictionary<long, int>>` | Campaign 存档 | 保存角色对之间的原始关系 |
| 单条关系默认值 | `GetRelation` 查不到记录 | `0` | 不保存零值 | 没有记录就视为中立 |
| 关系范围 | `Hero.SetPersonalRelation` | `-100..100` | 原生关系表 | 写入时按外交模型上下限钳制 |
| 关系键方向 | `GetHashCodes` | 按两个 Hero.Id 排序 | 对称键 | 原生关系不是“甲信任乙”和“乙信任甲”两条独立值 |
| 删除行为 | `SetRelation(..., 0)` / `Remove` | 零值记录移除 | Campaign 存档 | 角色注销时清理关系 |

证据：`CharacterRelationManager.cs:11-110`、`CharacterRelationManager.cs:129-162`、`Hero.cs:2018-2022`。

### 2.2 有效角色关系：行为和多数 UI 使用的关系

原版 `Hero.GetRelation(otherHero)` 不是简单读取基础表，而是：

```text
1. 用 GetHeroesForEffectiveRelation 把双方通常映射到各自家族族长。
2. 读取映射后双方的基础角色关系。
3. 加入 Honor、Valor、Mercy 的人格相容修正。
4. 将结果钳制到 -100..100。
```

原版映射例外：

- 如果双方映射到同一个有效角色，则改用原始两个 Hero；因此同一家族成员之间不是自动读取族长对自己的关系。
- 玩家与玩家同伴之间使用原始两个 Hero 的关系。
- 没有家族的角色使用其自身作为有效角色。

人格修正是离散加减，不是比例：

| 特质 | 同向 | 反向 |
|---|---:|---:|
| Honor | `+2` | `-2` |
| Valor | `+1` | `-1` |
| Mercy | `+1` | `-1` |

同向/反向由双方特质等级乘积的正负决定；乘积为零不产生修正。

证据：`DefaultDiplomacyModel.cs:71-77`、`DefaultDiplomacyModel.cs:857-888`、`DefaultDiplomacyModel.cs:913-933`、`Hero.cs:2024-2036`。

### 2.3 原生关系阈值

| 名称 | 数值 | 实际判断 |
|---|---:|---|
| 最小关系 | `-100` | 写入和有效关系下限 |
| 最大关系 | `100` | 写入和有效关系上限 |
| 最小中立阈值 | `-25` | 基础关系 `< -25` 才是 `IsEnemy` |
| 最大中立阈值 | `50` | 基础关系 `> 50` 才是 `IsFriend` |
| 中立区间 | `-25..50` | 边界值仍不满足敌对/友好判断 |
| 加入王国谈话最低关系 | `-10` | 独立于友好/敌对阈值的外交条件 |

重要区别：`Hero.IsEnemy`、`Hero.IsFriend`、`Hero.IsNeutral` 直接读取基础关系，不读取 `Hero.GetRelation` 的有效关系人格修正。这会造成“有效关系显示”和“敌友布尔判断”不完全一致。

证据：`DefaultDiplomacyModel.cs:65-77`、`Hero.cs:2038-2055`。

## 三、关系变化入口

### 3.1 通用关系变化

`ChangeRelationAction.ApplyInternal` 是原版主要增量入口：

```text
正增量 → GetRelationIncreaseFactor 修正
        → 映射到有效角色
        → 读取有效双方的基础关系
        → 相加并钳制 -100..100
        → SetPersonalRelation
        → 触发 OnHeroRelationChanged
负增量 → 不经过正向关系增益修正，直接进入后续流程
```

正向关系增益包含：

- Charm 关系效果：`CharmRelationBonus` 每点 Charm 为 `0.005` 的 AddFactor，即每点约 `0.5%`。
- 异性关系且拥有 `InBloom`：再加 `20%` 因子。
- 同性关系且拥有 `YoungAndRespectful`：再加 `20%` 因子。
- `GoodNatured` 对 Mercy 为正的目标额外 `+1`。
- `Tribute` 对 Mercy 为负的目标额外 `+1`。

如果双方都不是玩家，关系增益计算中使用哪一方作为技能/Perk 来源存在随机选择；涉及玩家时优先使用玩家。不能把正向关系增量简化成固定的“原始数值”。

证据：`ChangeRelationAction.cs:14-27`、`DefaultDiplomacyModel.cs:171-196`、`DefaultSkillEffects.cs:267-272`、`DefaultPerks.cs:2204-2211`。

### 3.2 `affectRelatives` 不是现成的家族传播机制

`ChangeRelationAction.ApplyPlayerRelation` 的签名保留了 `affectRelatives` 参数，但当前 `ApplyInternal` 路径没有使用它，也没有在该参数为 `true` 时遍历父母、配偶、子女或家族成员。

因此不能依据参数名推断“玩家得罪一个人会自动扣全家关系”。原版关系对家族成员的影响主要来自有效关系映射、家族聚合计算和具体事件脚本，而不是这个参数。

证据：`ChangeRelationAction.cs:14-37`。

### 3.3 关键事件数值

| 事件 | 原生变化 | 说明 |
|---|---:|---|
| 婚姻模型第一次关系增加 | 基础 `20`，再按 Charm 关系效果修正并四舍五入 | `DefaultMarriageModel.GetEffectiveRelationIncrease` |
| 婚姻事件第二次关系增加 | `30`，再走通用正向关系增益 | `CharacterRelationCampaignBehavior.OnHeroesMarried` |
| 无 Charm 时婚姻关系理论基础合计 | `20 + 30 = 50` | 还会受当前关系上限 `100` 截断 |
| 族长死亡后的新族长继承关系 | 死族长对目标基础关系的 `70%` | `GetRelationChangeAfterClanLeaderIsDead` |
| 叛乱离开王国 | `-40` | 对旧王国各家族族长逐一变化 |
| 普通离开王国 | `-20` | 对旧王国各家族族长逐一变化 |
| 城镇/城堡关系礼物 | 城镇 `+20`，城堡 `+10` | DiplomacyModel 常量，具体入口另行调用 |

婚姻的 `20` 和 `30` 不是简单相加后一次写入；两次正向调用都可能再次受到 Charm/Perk 修正，实际结果必须按调用链计算。

证据：`DefaultMarriageModel.cs:136-141`、`MarriageAction.cs:17-27`、`CharacterRelationCampaignBehavior.cs:410-426`、`DefaultDiplomacyModel.cs:65-69`。

## 四、家庭成员数据：有亲属拓扑，没有独立家庭好感值

### 4.1 Hero 中实际保存的家庭字段

| 字段 | SaveableField | 形式 | 语义 |
|---|---:|---|---|
| `Father` | `700` | Hero 引用 | 父亲 |
| `Mother` | `710` | Hero 引用 | 母亲 |
| `ExSpouses` | `720` | Hero 列表 | 前配偶 |
| `Spouse` | `730` | Hero 引用 | 当前配偶 |
| `Children` | `740` | Hero 列表 | 子女 |
| `Siblings` | 无独立存档字段 | 运行时计算 | 从父亲或母亲的子女列表推导 |

原版没有 `FamilyAffection`、`FamilyTrust`、`HouseholdDisposition` 一类独立数值。家庭关系如果需要数值表达，仍然落在同一张角色对基础关系表中。

证据：`Hero.cs:142-161`、`Hero.cs:783-873`。

### 4.2 家庭关系与家族关系不能混淆

- “家庭”是父母、配偶、子女、兄弟姐妹的亲属拓扑。
- “家族”是 `Clan`，拥有族长、领主成员、领地、影响力、声望和等级。
- “家族关系”不是家庭好感的总和；原版至少有两个不同计算路径，见下一节。

## 五、家族关系与家族数值

### 5.1 `Clan.GetRelationWithClan`：族长有效关系

```text
Clan.GetRelationWithClan(otherClan)
→ Leader.GetRelation(otherClan.Leader)
```

这条路径使用有效关系，因此包含族长映射和人格修正。它不是独立保存的 Clan-to-Clan 数值。

如果任一方没有族长，返回 `0`。

证据：`Clan.cs:940-947`。

### 5.2 `FactionManager.GetRelationBetweenClans`：领主加权基础关系

该方法使用双方所有存活、成年领主的基础关系，计算加权平均：

```text
普通领主基础权重：0.1
族长额外：+0.2
族长配偶额外：+0.05
双方同时为族长：该组合权重 ×20
只统计 Age > HeroComesOfAge 的双方领主
返回 int(num / num2)
```

由此可得常见组合权重：

| 双方组合 | 权重 |
|---|---:|
| 普通领主 - 普通领主 | `0.2` |
| 族长 - 普通领主 | `0.4` |
| 族长 - 族长配偶 | `0.45` |
| 族长 - 族长 | `10.0` |

特殊情况：一方是没有存活领主的匪徒家族、另一方不是匪徒家族时返回 `-10`。

该值的输入是基础关系，不是有效关系；它主要供入王国、离开王国、驱逐家族、婚姻议价和部分王国决策使用。

证据：`FactionManager.cs:206-252`；调用点包括 `DefaultDiplomacyModel.cs:250-325`、`MarriageBarterable.cs:57`、`ExpelClanFromKingdomDecision.cs:177`。

### 5.3 族长更换

换族长时原版不是简单把旧族长关系复制给新族长：

```text
对每个存活 Hero：
    新族长的当前基础关系
    + 旧族长对该 Hero 的基础关系 × 0.7
    → SetPersonalRelation（再次按 -100..100 钳制）
设置 Clan.Leader
触发 OnClanLeaderChanged
```

这意味着：

- 新族长会得到关系迁移，但不是等比例复制。
- 家族关系读取结果会随新族长变化而变化。
- AWAKE 如果以后缓存家族关系，必须在 `OnClanLeaderChanged` 后失效，不能保存一套旧族长派生值。

证据：`ChangeClanLeaderAction.cs:41-51`、`DefaultDiplomacyModel.cs:890-893`。

### 5.4 Clan 的政治数值不是关系

| 数值 | 原生形式 | 范围/阈值 | 不能替代什么 |
|---|---|---|---|
| `Influence` | `float`，SaveableField `62` | Setter 本身不做固定上下限钳制；UI 对低于 `-100` 显示警告 | 不能替代好感、信任或亲属关系 |
| `Renown` | `float`，SaveableProperty `88` | 决定 Clan Tier | 不能替代家族关系 |
| `Tier` | `int` | `0..6` | 不能直接解释为 NPC 对家族的喜欢程度 |
| `CurrentTotalStrength` | 缓存值 | 动态计算 | 是军事力量，不是外交关系 |

原版 Clan Tier 声望下限为：

```text
Tier 0: 0
Tier 1: 50
Tier 2: 150
Tier 3: 350
Tier 4: 900
Tier 5: 2350
Tier 6: 6150
```

证据：`Clan.cs:63-91`、`Clan.cs:191-205`、`Clan.cs:307-327`、`DefaultClanTierModel.cs:11-66`、`ChangeClanInfluenceAction.cs:3-15`。

## 六、外交：没有连续的“王国好感值”

### 6.1 原生持久外交状态

`FactionManager` 保存的是 `FactionManagerStancesData._stances`，键为无方向的 faction 对，值为 `StanceLink`。

`StanceLink` 的核心状态只有：

| 状态 | 类型/意义 |
|---|---|
| `StanceType` | `Neutral` 或 `War` |
| `BehaviorPriority` | 站队/外交行为优先级 |
| `WarStartDate` / `PeaceDeclarationDate` | 战争与和平时间 |
| `TroopCasualties1/2` | 双方部队伤亡 |
| `SuccessfulSieges1/2` | 成功围城次数 |
| `SuccessfulTownSieges1/2` | 成功攻城次数 |
| `SuccessfulRaids1/2` | 成功劫掠次数 |
| `TotalTributePaidFrom1To2` | 累计贡金方向值 |
| `DailyTributeFrom1To2` | 当前每日贡金方向值 |
| `DailyTributeInstallments` | 贡金剩余期数计算输入 |

因此，王国/派系外交的持久事实是“中立/战争 + 战争统计 + 贡金”，不是一条 `-100..100` 的王国好感。

证据：`FactionManager.cs:10-35`、`FactionManagerStancesData.cs:5-64`、`StanceLink.cs:10-59`、`StanceLink.cs:117-217`、`StanceLink.cs:486-540`。

### 6.2 派系外交状态的更新

- `FactionManager.DeclareWar` 将姿态设为 `War`。
- `FactionManager.SetNeutral` 将姿态设为 `Neutral`。
- 进入战争时重置战争统计并记录 `WarStartDate`。
- 从战争转为中立时重置战争统计并记录 `PeaceDeclarationDate`。
- 匪徒/某些派系组合可以由 `DiplomacyModel.IsAtConstantWar` 派生为恒定战争，不等同于普通可谈判战争。

证据：`FactionManager.cs:74-183`、`StanceLink.cs:61-85`。

### 6.3 外交决策使用的“关系”是派生值

例如：

- 议和/宣战评分会调用 `Clan.GetRelationWithClan`。
- 入王国、离王国和驱逐家族会调用 `FactionManager.GetRelationBetweenClans`。
- 宣战关系评分将两个有效家族关系取平均，并在负值时按 `-250` 系数与力量比计算影响。
- 战争进度来自 `StanceLink` 的战争统计和其他战力/领地模型，不是额外的外交好感条。

这些都是“运行时计算结果”，不是应该再保存一份的权威字段。

证据：`DefaultDiplomacyModel.cs:250-308`、`DefaultDiplomacyModel.cs:379-400`、`DefaultDiplomacyModel.cs:1273-1292`。

## 七、与当前 AWAKE 实现逐项对照

### 7.1 当前 AWAKE 有什么

AWAKE 当前保存 `awake.relationship.state.v1`：

| 字段 | 默认 | 范围 | 当前用途 |
|---|---:|---:|---|
| `trust` | `0` | `-100..100` | AI/事件自定义信任轴 |
| `love` | `0` | `-100..100` | AI/事件自定义爱意轴 |
| `hostility` | `0` | `-100..100` | AI/事件自定义敌意轴 |

存储键为 `hero.<heroId>.v1`，当前命令只携带一个 `heroId` 和三个 delta，没有原版 Hero 对、玩家 ID、来源角色或关系方向字段。

AWAKE 的主动 NPC 逻辑还把三个轴合成为：

```text
affinity = clamp(trust + love - hostility, -100, 100)
```

并使用自己的阈值和概率：

| 条件 | 阈值/概率 |
|---|---:|
| 无关系记录 | `2%` |
| 普通 | `5%` |
| 熟悉 | `affinity >= 10`，`8%` |
| 高亲和 | `affinity >= 50`，`16%` |
| 敌意 | `affinity <= -30`，`9%` |

概率还会按设置缩放，并封顶。

- `C:\Users\26811\OneDrive\文档\New project\_houkai_merge\AWAKE\src\WorldStateStore.cs:2652-2694`
- `C:\Users\26811\OneDrive\文档\New project\_houkai_merge\AWAKE\src\AwakeWorldCommandAdapters.cs:94-165`
- `C:\Users\26811\OneDrive\文档\New project\_houkai_merge\AWAKE\src\NpcProactiveService.cs:306-403`
- `C:\Users\26811\OneDrive\文档\New project\_houkai_merge\AWAKE\src\NpcProactiveModels.cs:36-43`

### 7.2 当前 AWAKE 与原版的实际关系

对 `AWAKE\src`、`ModuleData`、`GUI` 做静态搜索，目前没有发现 AWAKE 调用以下原版关系 API：

- `Hero.GetRelation`
- `Hero.GetBaseHeroRelation`
- `ChangeRelationAction`
- `Hero.SetPersonalRelation`
- `CharacterRelationManager`
- `Clan.GetRelationWithClan`
- `FactionManager.GetRelationBetweenClans`

因此当前 AWAKE 的 `trust/love/hostility` 不是原版关系的镜像，也没有改变原版好感；它是一个独立的 AWAKE 自定义状态系统。

这同时意味着：

- 当前 AWAKE NPC 主动行为不能自动看到原版玩家好感、敌友状态或家族关系。
- 当前 AWAKE 自定义关系不能自动影响 Bannerlord 原版的交易、招募、外交、敌友判断或家族决策。
- 两套系统如果继续并行，必须在读取层明确“原版关系”和“AI 认知状态”是两个不同维度，不能把其中一个命名成另一个。

## 八、目前可以确认的结论

1. **原版没有可供 AWAKE 复用的独立家族好感值。** 只有角色对基础关系、族长有效关系和领主加权家族关系派生值。
2. **原版家庭成员没有独立好感字段。** 父母、配偶、子女、兄弟姐妹是亲属拓扑；数值关系仍使用角色对关系表。
3. **原版关系是对称的。** 它不能表达“NPC 信任玩家 60，但玩家只信任 NPC 10”这种方向性差异。
4. **“关系显示”“敌友判断”“家族关系”“外交决策”可能走不同路径。** 不能只读取一个 API 后假设整个游戏都用同一数值。
5. **族长更换已经有原版迁移规则。** AWAKE 不应再造“旧族长关系按比例发给家族成员”的公式。
6. **`affectRelatives` 当前不是实际传播开关。** 不能以参数名为依据实现家族关系联动。
7. **AWAKE 当前关系状态是独立的、目标中心的自定义三轴。** 目前没有原版关系接线，也没有双角色关系键。
8. **在设计任何类似功能前，第一步应是做只读原生快照和明确的语义映射，而不是给现有 `trust/love/hostility` 再套一层家族公式。**
