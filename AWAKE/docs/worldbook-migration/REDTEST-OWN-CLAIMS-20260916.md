**我还漏报了一个新风险**：`？？？`（纯标点）从 `OK` 变成 **过(458)**。

⇒ **归一化会造出"归一化前非空、归一化后为空"的新空串，必须配"归一化后再判空"兜底。** 这一条我上一轮完全没想到。

**另一处退步**：`头盔` 2→4。模糊化必然带来过匹配增长——**只报收益不报代价**，是我上一轮最典型的毛病。

## 二、逻辑被证伪（3 条）

### J1「模型治不了过匹配，换什么模型都白搭」——**过强，错**

反例：embedding 检索**通常带相似度阈值**。`doc` 这类无意义输入与所有条目相似度都低 ⇒ **被阈值挡掉**。
⇒ 换成 embedding 后，`doc` 反而不炸了——**不是治好了根因，是根因被换掉了**（不再依赖 keywords 列表）。

**但仍有一半成立**：若做**混合检索**（精确+向量），`doc.` 依旧会从精确那一半炸出来 ⇒ **改数据仍然必要**。
正确措辞应是：「单走向量可以让这个洞消失，但只要混精确匹配，就必须改数据」。

### J7「不要直接上 0.6B：中文仅 +4.6，体积 ×26，**延迟 ×500**」——**数字滥用**

`×500` 是把 `Qwen3 780 ms/句` ÷ `bge-small 几 ms` 得来的。这两个数来自**不同来源、不同硬件、不同精度（FP16 vs INT8）、不同实现**，
而且原出处自己注明"PyTorch 默认只用了 4 个线程，我们没有调优"。
⇒ **这个比不成立**。体积 `×26`（23→610 MB）数学上对；延迟那句必须撤回。

### J8「AnimusForge 0.98G ≈ Qwen3-Embedding-0.6B 档」——**类别错误**

AnimusForge 用它做**文本识别**（生成式模型）；我拿它跟 **embedding 模型**比。
生成模型与 embedding 模型**除了"体积都接近 1G"没有任何可比性**——参数量、架构、用途、推理成本全不同。
⇒ **这条是真错误**，应删除类比。

## 三、流程违规与顺序问题（J9）

> 我上一轮建议：三步走「① 算法 → ② 修 keywords 数据 → ③ 可选上模型」

两个问题：

1. **顺序可能是反的**：实测第 ① 步会让**过匹配变差**（11→12）。先上算法，系统会**先变差再变好**。
   ⇒ 更稳的顺序是 **② 改数据在前、① 算法在后**（先堵住最大的洞，再补召回）。
2. **我建议删的东西，没查它是谁加的、为什么加**（见下节 —— 查完发现我打错了靶）。

## 三之二、补查：`doc.` 关键词的来历（我上一轮的靶打偏了）

追到编译器 `RuntimePackageCompiler.cs:108-121`，那里有**明写的设计注释**：

```
K1：keywords 是运行时的可读检索词，来源为「标题（多语言）+ 别名（多语言）+ 实体锚点的可读名称」。
    内部文档 id 保留为兜底检索词并排在最后：它不是玩家/NPC 会用的说法，不应再充当主要关键词。
```

⇒ **结论三层：**

1. **它是刻意的，不是失误**。我上一轮"100% 覆盖不像失误"的直觉对了，但开出的方子（**删掉它**）**打错了靶**——它有设计编号 K1、有明确意图。
2. **真正的毛病更尖锐：那个设计意图没有生效。**
   设计者假设"排在最后"＝兜底／弱化；但 `FindCandidates` 里**数组位置完全不参与匹配**（只做集合成员判定），
   `MatchQuality` 也只看**匹配串长度**。⇒ **"排在最后"没有任何语义效果**，兜底词与主词**在匹配上完全等权**。
3. ⇒ 正确的修法**不是删**，而是**让"兜底"这个意图真的生效**：例如兜底关键词**不参与反向匹配**，或只在正向匹配时可用。
   这样既保住它作为检索入口的功能，又不让它炸出一大片。

> 这一条是整轮红测里最有价值的发现：**如果我只按上一轮的判断去"删关键词"，就会把一个有意设计的功能删掉，而真正的 bug（意图未实现）会原样留下。**

## 五、修正后的结论

**站得住的（1 条）**
- 漏报可以用「归一化 + 拼音 + 编辑距离」大幅改善：**19 → 2**。归一化一步就占 11 条。

**被推翻/需撤回的（4 条）**
- ~~"这套方案能打掉过匹配大部分"~~ → **过匹配 11 → 12，不降反升**。
- ~~"加模糊匹配的收益"~~ → 必须同时报**代价**：`头盔` 2→4、`？？？` OK→458。
- ~~"延迟 ×500"~~ → 撤回。
- ~~"AnimusForge ≈ Qwen3-Embedding-0.6B 档"~~ → 类别错误，删除。

**必须改序的（1 条）**
- 三步顺序改为：**先查清 `doc.` 关键词的来历 → 修数据（且修法是"让兜底生效"而不是"删掉"）→ 再上算法 → 最后评估要不要模型**。

**降级为待验证的（4 条）**
- 模型体积/分数、.NET 落地可行性、吞吐数字、"行业标准做法"。

## 六、一句话总结

这套判断里：**关于"漏报"的部分比我自己说的更好**（19→2）；**关于"过匹配"的部分我说错了**（11→12，不降反升）；**关于模型的那几条一半是二手、一条是类别错误**。
