# 词条联系现状核实（2026-09-18）

> 起因：甲方指出「知识之间暂时没有联系是现在初期的缺陷，**但是设计上词条是应该互相联系或者引用的**」。
> 本文只做核实，不排期、不开工单。所有断言带路径。
> 口径：**"没有"一律限定在括号里写清搜的是哪个目录。**

## 一、要回答的三个问题

1. 引用图当初被排到哪个批次了？为什么停着？
2. 契约里到底有没有"联系/引用"的位置？（还是要从零加字段）
3. 现在的 482 条内容里，联系填了没有？运行时读不读？

## 二、核实结果

### 2.1 引用图：**哪一批都没排** —— 不是"排在后面"，是从没被排回来

在 `AWAKE/docs/` 下搜 `引用图` 及其同义词（`互链`／`关联图`／`关系图`），命中如下：

| 出处 | 原话 |
|---|---|
| `docs/PLAN-WorldbookStudio-B1-ENTITY-CATALOG-20260824.md:48` | 「不加入知识条目引用图。」 |
| `docs/PLAN-WorldbookStudio-KnowledgeTaxonomy-20260824.md:95` | 「不实现知识引用图、自动拆分多领域档案或自动复制条目。」 |
| `docs/superpowers/specs/2026-08-24-worldbook-entity-catalog-design.md:96` | 「五领域 `geography`、**知识引用图**、人物/家族权限条件和新版运行时契约不在 B1 内实现。」 |
| `docs/PLAN-AWAKE-WorldbookPlatform-20260822.md:21` | 「定义事实、表达、身份配置、**转介**、包、补丁、运行时更新之间的**引用图**、必填字段、闭包检查和版本约束。」 |

⇒ 前三条是**"不做"名单**，第四条是**"要做"的要求**。**`docs/` 里没有任何一处把它排进 B1 之后的某个批次。**

### 2.2 契约里：**位置早就留好了**（不是从零）

`tools/worldbook-contract/v1/common.schema.json` 的 `knowledge_entry`（`:195-259`），`additionalProperties: false`，
必填 `id`／`domain`／`title`／`summary`／`expressions`／`keywords`，另有：

| 字段 | 定义 | 行 |
|---|---|---|
| `subdomain` | 字符串，`^[a-z][a-z0-9_]*$` | `:245-248` |
| **`related_domains`** | 数组，**minItems 1 / maxItems 4**，元素是 `knowledge_domain` | `:249-257` |

`tools/worldbook-contract/v1/runtime.schema.json`：

| 字段 | 定义 | 行 |
|---|---|---|
| `indexes` | **必填**，含 `keywordToEntryIds` ＋ **`domainToEntryIds`** | `:14-16`、`:113-119` |
| `referrals` | **必填**，每条必须带 `id`／`displayName`／`reason`／`priority`／`publiclyAskable` | `:80-112` |

★ **两个纠正我先前说法的点**：
- **`referral` 不是"空壳"**：契约里它是有 5 个必填字段的正式对象（含 `reason`、`priority`、`publiclyAskable`）。
  之前说的"写死台词"（`AUDIT-20260918-身份链潜在问题.md` A6）说的是 **AI 生成层没放行**，不是它没数据。
- **"领域 → 条目"这张表是契约要求必须有的**（`domainToEntryIds` 必填）。我 09-18 上午做级联实验时
  拿"条目 id 的类目段"临时顶的那个"类"，**正解就在这个字段上**。

⚠️ **但 `related_domains` 只到"领域"这一级**（最多 4 个领域，如 geography ↔ war），
**不是"条目 → 条目"**。契约里**没有**条目级引用字段（`knowledge_entry` 的 properties 全部列尽，`additionalProperties: false`）。

### 2.3 锚点覆盖：**镜像档与上线包两个口径差 5 倍**（09-18 下午更正，本节的旧数字作废）

⚠️ **本节初版（09-18 上午）把两个口径混成了一个**：我量的是 `docs/worldbook-migration/projection/authoring-out/`
里的 yaml 草稿，而**上线包里那份是 `extensions.entityRefs`** —— 名字不同、覆盖也不同。

```
口径 A · 镜像档 yaml（projection/authoring-out，482 个档）   含 entity_ids:  81 / 482
口径 B · 上线包（ModuleData/.../calradia/runtime.json）     extensions.entityRefs: 402 / 482  ← 81%
```

**两个数字都是真的，但只有 B 是"检索链看得见的那份"。** 差异成因：上线包是从 Studio 工作区
（`tools/worldbook-studio/workspace/`，未入库）编译的，镜像档是更早的草稿导出；**两者没同步**。

★ **按类别看上线包侧锚点覆盖**（这一版才是"图碎在哪"的准确答案，口径 B）：

| 类别 | 有锚点 | 无锚点 |
|---|---|---|
| `geography.villages` | **273** | 0 |
| `geography.castles` | **67** | 0 |
| `geography.towns` | **53** | 0 |
| `war.weapons` | 0 | **32** |
| `economy.items` | 0 | **15** |
| `culture.tales` / `economy.goods` | 1 / 1 | 5 / 5 |
| 其余山水、军制、制度等 | 3 | 26 |
| **合计** | **402** | **80** |

⇒ **聚落类（村庄/城堡/城镇）100% 有锚点**；缺锚点的 80 条**全是非聚落类**。

🚨 **而这 80 条不是"没填"，是"挂不上"**：编译器 `CanonicalEntityRef`
（`RuntimePackageCompiler.cs:251-261`）**只接受 `entity.<hero|clan|settlement>`**，别的 kind 直接抛
`WB-DOC-003`。器物、兵种、军制、山水在游戏里**本来就没有对应实体** ⇒
**头盔题、兵种题永远拿不到游戏锚点** —— 除非先改契约＋编译器。
⇒ **"补锚点"这条路对它们是不通的，不是漏工。**

* **`related_domains`：482 条里一条都没填。** 全目录搜只命中一个生成脚本的**说明文字**
  （`_gen_classification_registry_20260914.py:153`：「3. **跨域关联有正式字段**：`related_domains`（最多 4 项、唯一、按 taxonomy 顺序、不得含主域）」）
  ⇒ **字段定了、脚本里还写着规矩，条目里是空的。**（⚠️ 上线包里 `relatedDomains` 也是 **0/482**；
  但这个字段**运行时零消费者**，见 2.4 —— 填了也暂时白填。）

* **实体锚点的共享情况**（口径 B，按出现次数排）：
  `town_s1` × 5、`town_v7` × 4、`town_es4` × 2、`castle_village_v6_2` × 2，**其余 389 个锚点全是一次**。

🚨 **这行数字是本节最要紧的一条**：**402 条条目、393 个锚点，其中只有 4 个被 2 条以上共用。**
⇒ 锚点虽然覆盖 83%，但它**是自己锚自己**（村庄条目锚它那座村）⇒ **构不成图**，
只有"同一个地方被多个领域分别写到"时才生出边（上面那 4 组）。
⇒ **"图碎"的真原因不是覆盖率低，是复用率低。**

★ **那几组共享不是巧合，是设计里的"多领域档案"**：

| 共享 `entity.settlement.town_s1`（瓦尔切格）的条目 | domain |
|---|---|
| `peninsulas-kachar.yaml` | geography |
| `tales-kachar-rulership.yaml` | culture |
| `territories-kachar-ownership.yaml` | politics |
| `territories-varcheg-swap.yaml` | politics |
| `towns-varcheg.yaml` | geography |

⇒ **同一个地方，在多个领域各有一条。这就是现成的"条目 → 条目"边**——
只不过它不是靠新字段，是靠**两条条目指向同一个实体 id**。第 2 条 `town_v7`（查拉斯）完全同构。

### 2.4 运行时：**领域索引只被"校验"，没人读；`related_domains`／`subdomain` 零命中**

在 `AWAKE/src/` 下搜 `related_domains|RelatedDomains|subdomain|Subdomain|domainToEntryIds`，**只有两处命中**：

```
src/WorldbookPackageIntegrity.cs:132  Require(... index["domainToEntryIds"] is JObject, "WB2-INDEX-MISMATCH:indexes_missing")
src/WorldbookPackageIntegrity.cs:134  Require(Canonicalize(runtimeIndexes["domainToEntryIds"] ...) == ..., "WB2-INDEX-MISMATCH:domains")
```

⇒ `domainToEntryIds` **只用于完整性校验**（在不在、对不对），**没有一处拿它做检索**；
`related_domains`／`subdomain` **在 `src/` 里零命中**。

★ **09-18 下午补测：`entityRefs` 与 `relatedDomains` 在运行时链路上同样零消费者**（口径写进同一句，免得被读成"全仓没有"）：

```
① 运行时 + 三个验台源码：src/**/*.cs 与 tools/{worldbook-runtime-sim,worldbook-runtime-smoke,worldbook-rag-merge}
   grep "entityRefs|relatedDomains"  → **零命中**（只有预编译的 MarcusAwakeFramework.dll 二进制命中）
② 全仓其余命中（排 bin/obj）**有很多**，但都不是运行时：
   · tools/worldbook-studio/src/**：Application.cs / AuthoringDraftContracts.cs / AuthoringTemplateFactory.cs
     —— 是**建档、校验、编辑**那一侧（`relatedDomains` 的写入与上限校验）
   · framework/MarcusAwakeFramework/src/GameDataAndContext.cs：`ContextContribution.EntityRefs`
     —— **另一件事**（游戏数据上下文的实体引用），与世界书条目无关
```

⇒ **锚点在运行时的唯一作用发生在编译期**：`RuntimePackageCompiler.cs:120-122` 把锚点的**可读名称**
加进 `keywords`（K1 机制）。写进 `extensions.entityRefs` 的那一份，**运行时没有任何人读**。
⚠️ **所以之前那句"条目 → 条目的边靠共享 entity_ids 已经在跑"是错的** —— 边**在包里躺着**，
**没有消费者**。正确说法：**料在那儿，接没接是两回事。**

`relatedDomains` 则更进一步：**契约里有（`runtime.schema.json:193`）、包里 0 条、运行时没有消费者** ——
三重空。

### 2.5 ⚠️ 领域这一级切不开：内容极度倾斜（**这条推翻我自己上一轮的判断**）

| 维度 | 最大一类的占比 |
|---|---|
| `domain`（5 个领域） | `geography` **411 / 482 = 85%** |
| `subdomain`（17 个） | `settlements` **396 / 482 = 82%** |
| id 类别段（`domain.段`） | `geography.villages` **273 / 482 = 57%** |

其余分布：领域 `war` 37／`economy` 21／`politics` 7／`culture` 6；
类别段 `geography.castles` 67、`geography.towns` 53、`war.weapons` 32、`economy.items` 15，
其余 20 余类全是 1–6 条的长尾。

★ **顺带核掉一件事**：482 条里 `id` 的第二段与 `domain` 字段**完全一致**（`SAME=482 DIFF=0`）
⇒ 09-18 上午那份级联实验用的"类"**本来就是真领域**，那组数字不用重跑。

⇒ **`domainToEntryIds` 读了也切不开。** 85% 同域、57% 同类别 —— 不管拿哪一级当第一刀，
最大的一类都过半。**"接通领域索引就有第一级粗筛"这句话是错的。**

（成因看着是内容进度：近几批做的是聚落，所以 `geography.villages` 一家独大。
以后武器甲、兵种、物品铺开，分布会变 —— 但**按现在的库，它没有收窄能力**。）

## 三、结论

1. **设计没漏，是没接。** 领域层（`subdomain`／`related_domains`／`domainToEntryIds`）与转介层（`referrals`）
   **契约里全都有、且部分是必填**；引用图则在 B1 被明确排除后**从未被排回来**。
2. **"条目 → 条目"没有专门字段；锚点虽然覆盖 83%，但它不构成图。**
   402 条条目、393 个锚点，**其中只有 4 个被 2 条以上共用** —— 因为锚点是"自己锚自己"
   （村庄条目锚它那座村），所以边只在"同一地方被多领域分别写到"时才出现。
   ⇒ **图碎的真原因是复用率低，不是覆盖率低**（覆盖率那半是我上午写错的，见 2.3）。
   ⇒ 且这份锚点**运行时零消费者**（见 2.4）：**料在，没接。**
3. **"乙"（焦点＝一组候选）的落地账，关键不在算法侧，在那张"谁属于谁"的层级表**：
   - **领域与类别都切不开**（见 2.5）。真正能把 273 条村庄切成几十份的，是**村庄归属哪个城堡／城镇**——
     这层关系**游戏数据里现成，登记表里已核到 `exact_base`**，**不需要作者补任何内容**。
   - ⇒ 这一步已在 09-18 下午落地：**`docs/FEED-20260918-聚落归属料表.md`**
     ＋ 料档 `docs/mappings/worldbook-settlement-hierarchy/20260918/settlement-hierarchy.v1.json`
     —— **274 条边（村庄条目 → 父城堡/城镇条目），零缺漏**（村庄无归属 0、父无条目 0）。
   - ⚠️ 但它**同锚点一样，现在还没有消费者**：契约里没有条目级引用字段，所以先落成独立料档。
     **"接"仍然要做**，只是这一步把"补"做掉了。
   - `related_domains` 填了也帮不上这一刀：它跟 `domain` 同级，同样粗（且运行时无消费者）。
