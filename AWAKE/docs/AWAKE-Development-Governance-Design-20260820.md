# AWAKE 开发工作治理重构设计

> 日期：2026-08-20
> 状态：设计稿，等待用户最终审阅后进入实施计划。
> 背景：依据 AWAKE `0.2.1` 复盘、本地 Ollama Worker 实测和现有 Codex Skills 职责审查制定。

## 1. 目标

将当前分散、重叠的开发规则重构为一套可执行、可恢复、低确认成本且证据可追踪的治理体系，解决以下问题：

- 短任务被误用为“每一步都等待用户回复继续”；
- 多个工作流 Skill 同时争夺任务选择和停止权；
- 巨型任务队列混合当前状态、历史和工具项目检查点；
- 候选 DLL 在等待真机验收期间继续漂移；
- 构建、Smoke、同步和真机证据被混用；
- 本地 Worker 被用于不适合的少量语义任务；
- 429、超时、取消和外部 Provider 错误缺少统一熔断策略。

新体系不追求增加更多流程，而是减少重复入口，明确每一层的唯一职责。

## 2. 核心决策

### 2.1 不新增第五套总控 Skill

现有 `bannerlord-mod-development-orchestrator` 已经承担任务分类、工具路由、验证和报告职责。继续新增一个 AWAKE 总控 Skill 会再次制造重叠。

因此采用以下方案：

- 将 `bannerlord-mod-development-orchestrator` 升级为唯一执行调度入口；
- `awake-task-continuity` 仅负责恢复和维护项目状态；
- `long-horizon-short-task-execution` 仅负责已批准批次内的短任务执行；
- `local-ollama-batch-worker` 仅负责明确输入的批量初筛；
- `abort-aware-execution` 仅负责回合中止后的终止行为；
- AWAKE `AGENTS.md` 只保留项目架构、内容、构建和真机硬规则。

### 2.2 批次授权替代逐任务确认

用户批准一个开发批次后，云端主模型获得该批次的执行租约 `Execution Lease`。租约覆盖计划中所有明确列出的、可逆且非高风险的短任务。

租约内执行循环：

```text
读取当前检查点
→ 选择批次内下一短任务
→ 最小检查
→ 最小修改
→ 窄验证
→ 写检查点
→ 自动进入下一短任务
```

短任务边界用于保存状态和限制故障范围，不再自动要求用户回复“继续”。

执行租约只在以下情况终止：

- 批次全部完成；
- 发现计划外的产品或架构选择；
- 需要不可逆删除、迁移或覆盖；
- 需要 API Key、账号、隐私数据或其他用户秘密；
- 需要启动 Bannerlord 或由用户执行真机操作；
- 需要同步游戏目录但未获得本轮明确授权；
- 出现 `429`、客户端中止、外部状态不确定或连续失败熔断；
- 现有证据推翻了已批准计划的关键假设。

进度消息只用于告知，不构成需要用户回答的确认请求。

## 3. 规则优先级与职责边界

### 3.1 权威优先级

从高到低：

1. 系统、开发者和当前用户明确指令；
2. 目标文件作用域内最近的 `AGENTS.md`；
3. `bannerlord-mod-development-orchestrator` 的调度决策；
4. 被调度的专项 Skill；
5. 计划文件、任务队列和历史检查点；
6. 本地 Worker 输出。

本地 Worker 永远不具有审批、修改、删除、发布或同步权。

### 3.2 `bannerlord-mod-development-orchestrator`

唯一负责：

- 任务分类；
- 判断是否需要计划、grill、调试、内容审计或发布流程；
- 选择和组合专项 Skill；
- 决定是否调用脚本、本地 Worker、子代理或云端直接处理；
- 管理执行租约；
- 判断停止、熔断和报告时机；
- 汇总各证据等级并决定任务状态。

禁止：

- 重复实现专项 Skill 的详细规则；
- 每次读取所有历史文档；
- 为简单问题启动完整计划流程；
- 在没有用户授权时创建 Codex Goal 或子代理。

### 3.3 `awake-task-continuity`

仅负责：

- 读取精简的当前状态文件；
- 恢复活动批次、候选构建、阻断项和唯一下一动作；
- 确保同一时间只有一个活动实施批次；
- 在用户切换方向时暂停旧批次并记录检查点；
- 将已完成检查点归档。

不再负责：

- 工具路由；
- 逐短任务停止；
- 新功能设计审查；
- 构建和发布门禁细节；
- 本地 Worker 调用规范。

### 3.4 `long-horizon-short-task-execution`

仅负责已批准批次内部执行：

- 将批次拆成单一结果、最小写集和窄验证的短任务；
- 在执行租约内自动接续；
- 每个短任务结束后写检查点；
- 将 429、取消和外部阻断交回 orchestrator；
- 批次末尾才执行集中广泛验证。

原有“每个短任务结束后停止，不自动进入下一项”改为：

> 每个短任务结束后必须保存检查点；只要执行租约仍有效，就自动进入同一批准批次的下一项。不得自动跨越批次、版本目标或真机门禁。

### 3.5 `local-ollama-batch-worker`

仅负责：

- 必填字段检查；
- 简单计数和分类；
- 关键词存在性；
- 确定性字段规范化候选；
- 重复、矛盾和结构异常候选初筛。

继续执行以下硬边界：

- 只读取工具调用中明确传入的文本或 JSON；
- 不扫描路径，不执行 Shell，不修改文件，不访问网络；
- 同步、串行调用；
- 输出必须携带稳定 `record_id`、`content_hash`、`batch_id`；
- 云端校验全部输出；
- 本地输出不能直接触发任何不可逆操作。

### 3.6 `abort-aware-execution`

只处理：

- `turn_aborted`；
- 用户取消；
- 客户端取消或断开；
- 恢复后禁止自动续跑旧回合动作。

不得扩展为通用网络重试或任务调度 Skill。

### 3.7 AWAKE `AGENTS.md`

只保留：

- AWAKE 与 MarcusAIFramework 的架构契约；
- Bannerlord 生命周期和线程规则；
- MCM、Gauntlet、存档、世界书和内容红线；
- 构建、同步和游戏目录安全规则；
- 真机验证必须来自用户日志。

应删除或缩短与通用 Skill 重复的任务连续性、确认次数和工具选择描述，改为引用唯一 orchestrator。

## 4. 任务与批次状态模型

### 4.1 状态机

```text
idea
→ needs_plan
→ approved
→ implementing
→ offline_verified
→ candidate_frozen
→ pending_game
→ game_verified
→ release_ready
→ done
```

附加状态：

- `paused`：用户主动切换或暂缓；
- `blocked_sync`：候选构建与部署目录不一致；
- `blocked_external`：依赖外部仓库、Provider、框架或用户环境；
- `rate_limited`：429 或上游额度限制；
- `decision_needed`：必须由用户决定产品或不可逆事项；
- `rejected`：方案明确不采用。

`fixed_pending_game` 不再作为正式状态。它应拆成：

- 修复后仅完成离线门禁：`offline_verified`；
- 候选已冻结并等待游戏：`pending_game`；
- 旧构建曾通过：作为证据标签 `verified_prior_build`，不作为当前任务状态。

### 4.2 WIP 限制

- 同时最多一个 `implementing` 批次；
- 同时最多一个 `candidate_frozen` 构建；
- 候选进入 `pending_game` 后禁止继续修改同一运行时 DLL；
- 等待真机期间可进行不进入候选 DLL 的文档、测试设计、内容审计或独立工具工作；
- 新反馈先登记，只有 P0 且阻断当前候选时才中断活动批次。

## 5. 状态文件重构

### 5.1 `AWAKE-CURRENT.md`

用途：每轮恢复时唯一需要完整读取的状态文件。

最大建议长度：100～200 行。

必须包含：

- 当前版本目标；
- 活动批次 ID、状态和执行租约；
- 当前候选 BuildId 与哈希；
- 当前阻断项；
- 最近验证证据；
- 唯一 `next_action`；
- 最近一次错误分类。

### 5.2 `AWAKE-ROADMAP.md`

仅维护版本目标、批次依赖和升版门槛，不保存逐轮日志。

### 5.3 `AWAKE-VALIDATION.md`

以矩阵记录功能证据：

| 功能 | E0 | E1 | E2 | E3 | E4 | E5 | 当前候选 |
|---|---|---|---|---|---|---|---|

### 5.4 `docs/checkpoints/`

每个批次使用独立检查点文件：

```text
<batch-id>-checkpoint.md
```

保存：

- 已完成短任务；
- 文件修改；
- 窄验证；
- 未验证项；
- 下一动作；
- 错误分类。

完成后移动到 `docs/archive/checkpoints/`。恢复普通任务时不读取整个归档。

### 5.5 旧任务队列迁移

当前 `AWAKE-Task-Queue-20260816.md` 转为只读历史来源。迁移脚本或人工迁移只提取仍有效的当前任务、版本目标、反馈和验证状态，不原样复制历史检查点。

## 6. 证据等级与完成定义

| 等级 | 证明内容 |
|---|---|
| E0 | 文件、类、路由、命令或入口存在 |
| E1 | 单元测试或确定性逻辑测试通过 |
| E2 | 构建、SdkSmoke、静态审计通过 |
| E3 | root、dist、游戏或发布目标哈希与版本一致 |
| E4 | 正式游戏入口真实执行并出现可观察结果 |
| E5 | 保存、退出、读档或新进程后结果仍正确 |

最低完成门槛：

- 纯确定性工具或解析器：E2；
- UI、对话入口、世界书运行时加载：E4；
- 记忆、关系、承诺、金币、事件状态：E5；
- 候选发布：E3 + 所需功能的 E4/E5；
- Level 0 内测：安装、启动、对话、存读档和 final drain 的 E4/E5。

最终报告必须分开列出 E1/E2、E3、E4/E5 和剩余风险。

## 7. 候选构建身份

每个候选生成：

- `Version`；
- `BuildId`；
- `SourceManifestHash`；
- DLL SHA-256；
- `WorldbookManifestHash`；
- `BuildTimeUtc`；
- `BannerlordApi`。

建议 BuildId：

```text
awake-<yyyyMMdd>-<sequence>
```

启动日志至少打印：

```text
module_load version=0.2.0 build_id=awake-20260820-001 dll_hash=F863D8EF5D53 worldbook_hash=<short> api=1.3.15
```

所有真机结论必须绑定：

```text
BuildId + DLL hash + log session
```

候选冻结后，任何代码或内容变化都必须产生新的 BuildId，并使旧候选状态失效。

## 8. 工具路由

### 8.1 优先使用确定性工具

以下任务默认使用 PowerShell、Node、项目脚本或现有测试：

- JSON/XML 解析；
- 文件数量和哈希；
- 重复 ID；
- 必填字段；
- 本地化键集合；
- manifest 一致性；
- 日志事件计数；
- DLL 和版本同步。

如果脚本可以得到确定答案，不调用 AI。

### 8.2 本地 Worker 使用门槛

必须同时满足：

- 输入已明确准备；
- 任务包含重复记录；
- 输出能用 ID/hash 校验；
- 本地结果仅作为候选；
- 预计收益高于调用和复核成本。

推荐路由：

| 任务 | 路由 |
|---|---|
| 少于 8 条的规则、计划或架构比较 | 云端直接处理 |
| 8～20 条短记录的字段/关键词检查 | Worker `low` |
| 20～40 条极短、结构一致的机械记录 | Worker `low`，必要时拆批 |
| 4～8 条有限语义重复/矛盾候选 | Worker `medium`，仅在预期可节省人工复核时使用 |
| 架构、优先级、权威来源、代码根因 | 云端 |
| 文件解析、哈希、精确重复 | 确定性脚本 |

本次实测中，6 条规则摘要的 `medium` 初筛等待 180 秒后超时，证明“小批量语义治理审查”应直接由云端处理。

### 8.3 本地 Worker 熔断

- `low` 或 `medium` 超时均进入 `in_doubt`；
- 不自动重放；
- 不自动升级 `high`；
- 检查任务快照后，由云端决定转人工、拆批或明确 retry；
- 同一输入 retry 必须使用新 `request_id` 并保留原失败记录；
- 一次内置格式重试后仍无效，停止该批；
- 不为了使用 Worker 而制造任务；
- 不宣传其必然节省云端 token。

## 9. 用户交互准则

需要用户决定：

- 新机制和产品范围；
- 多个合理方案之间的取舍；
- 不可逆删除、迁移或覆盖；
- 是否同步游戏目录；
- 是否进入真机验收；
- API Key、账号或外部服务；
- 正式提版和发布。

不需要用户回应：

- 常规读取、编辑和窄验证；
- 同一批准批次内进入下一短任务；
- 运行既定构建和 Smoke；
- 更新检查点；
- 进度通知。

用户说“继续”或“做”时：

- 存在活动执行租约：继续该批次；
- 无活动执行租约但存在唯一 `next_action`：执行该动作；
- 存在多个互斥候选：列出选项并等待选择；
- 不得自行挑选新版本或新机制。

## 10. 故障与重试策略

| 故障 | 处理 |
|---|---|
| Shell/命令语法错误 | 修正一次并重跑，不升级为项目阻断 |
| 测试失败 | 根据新证据修复，最多三轮；无新证据则停止 |
| 429 / exceeded retry limit | 保存检查点，标记 `rate_limited`，当前回合停止 |
| `turn_aborted` / 用户取消 | 立即终止本回合，不再调用工具 |
| Local Worker 超时 | 标记 `in_doubt`，不自动重放，云端接管 |
| Provider 429/503 | 标记 `upstream_error`，不凭此修改项目代码 |
| 游戏目录哈希不一致 | 标记 `blocked_sync` |
| 旧日志 BuildId 不匹配 | 不接受为当前候选证据 |
| 游戏正在运行 | 禁止覆盖游戏目录，改用 `-SkipGame` 或等待授权 |

同一操作连续两次失败且条件无变化时必须熔断，不允许通过重复调用制造进展假象。

## 11. 新功能、修复和审计的不同门禁

### 11.1 新功能、机制或内容批次

继续执行：

```text
grill-me-codex
→ 锁定 PLAN
→ 独立只读审查
→ VERDICT: APPROVED
→ 用户签收
→ 获得执行租约
→ 实施
```

### 11.2 Bugfix

如果只是恢复既定行为、不改变玩法规则：

```text
日志/复现
→ 第一错误状态
→ 回归测试
→ 最小根因修复
→ 窄验证
→ 批次验证
```

不要求重新 grill 整个功能。

如果修复实际改变玩法、存档契约、权限、经济结算或内容规则，则升级为新机制门禁。

### 11.3 审计

审计只产生：

- 证据；
- 风险等级；
- 候选修复；
- 是否需要新计划。

审计结果不能自动授权修改。

## 12. 实施范围

设计批准后，实施计划应覆盖：

1. 修改 `bannerlord-mod-development-orchestrator/SKILL.md`；
2. 精简 `awake-task-continuity/SKILL.md`；
3. 修改 `long-horizon-short-task-execution/SKILL.md` 的短任务停止规则，引入执行租约；
4. 收紧 `local-ollama-batch-worker/SKILL.md` 的使用阈值和超时接管；
5. 精简 AWAKE `AGENTS.md` 中重复的工作流规则；
6. 新建 `AWAKE-CURRENT.md`、`AWAKE-ROADMAP.md`、`AWAKE-VALIDATION.md`；
7. 迁移当前有效状态并将旧队列改为只读归档来源；
8. 为 AWAKE 构建和启动日志增加 BuildId/哈希指纹；
9. 使用 `0.2.1` 候选冻结与真机验收作为首轮实测。

## 13. 非目标

本轮治理重构不包含：

- 新增 AWAKE 游戏机制；
- 修改 Persona Workbench 功能；
- 切换 Codex 当前 Provider 或模型；
- 让本地 Worker 直接读取项目；
- 让本地模型写代码或决定发布；
- 自动启动 Bannerlord；
- 自动同步游戏目录；
- 自动创建或消耗 Codex Goal token 预算。

## 14. 验收标准

治理重构完成后必须满足：

- 新请求只由一个调度入口决定工作模式；
- 批次获得授权后不再逐短任务要求“继续”；
- 无活动任务时不会自动选择新功能；
- 当前状态恢复只需读取精简 CURRENT 文件；
- 历史检查点不再占用每轮上下文；
- 同时只有一个活动批次和一个冻结候选；
- 真机证据能对应 BuildId、DLL hash 和日志会话；
- Worker 仅处理满足门槛的显式批量输入；
- Worker 超时不会自动重放或升级 high；
- 构建、Smoke、同步、真机和读档证据明确分层；
- `0.2.1` 可以按“冻结候选 → 同步 → 真机 → 读档”闭环收口。
