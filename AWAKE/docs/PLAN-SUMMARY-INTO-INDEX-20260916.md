# 「把综述放进索引」到底改哪里 —— 落点判断

> 2026-09-16 · 起因：探针证明「补 summary ＋ 2-gram」能把口语问法从 0/13 拉到 5/13（见 `RETRIEVAL-PROBE-RESULT-20260916.md`）。
> 本文只回答一件事：**这些字是从哪一步进索引的，该在哪一步改。**
> 全部结论来自读代码，行号可直接核。

---

## 一、结论先摆

1. **综述早就在内存里了 —— 是索引那一层没伸手拿。** 不需要改包、不需要重编 448 档。
2. **绝不能把综述整句当成一个词条塞进去。** 匹配规则是「整串包含」，51 字的句子塞进去等于没塞。
   必须**先拆成小片（原词 ＋ 2-gram）**，并且**在排序上给它一个比真关键词更低的位次**。
3. **包里那份关键词索引别去动。** 运行时**搜索不读它**，只拿它做哈希对账 ⇒ 改了是白改。

---

## 二、数据流：综述现在走到哪一步就断了

```
包 runtime.json
   └─ entries[].summary            ← 448/448 都有，中位 51 字
        │
        │  WorldKnowledgeLoader.cs:64   Summary = Localized(value["summary"] …)
        ▼
   WorldKnowledgeEntry.Summary      ← ★ 已经进内存了，每条都带着
        │
        ├─── WorldKnowledgeQueryService.cs:312   entry.Summary + NewLine
        │        ⇒ 唯一读取点：只拼进**输出文本**（给模型看的材料）
        │
        └─── ⛔ 到这里为止。**没有任何一步把它拆成检索用的 term。**
```

**断点就在"建索引"那一步**，而不是在数据来源。

## 三、建索引的地方有**两处**（平行实现，必须同源）

| # | 位置 | 何时跑 |
|---|---|---|
| 1 | `WorldKnowledgeLoader.cs:160` `BuildKeywordIndex` | 加载包时 |
| 2 | `WorldKnowledgeQueryService.cs:353` `RebuildKeywordIndex` | 动态条目替换时（`:124`）／Overlay 改了标题/综述/关键词时（`:142`） |

两处代码**内容几乎一样**，都是：

```csharp
foreach (WorldKnowledgeEntry entry in snapshot.Entries.Values)
    foreach (string keyword in entry.Keywords)      // ← 只遍历 Keywords
    {
        // 塞进 snapshot.KeywordIndex：term -> [entryId]
    }
```

⚠️ **只改一处必炸**：`add_keyword` 之类的 Overlay 一跑就会走另一处，索引里综述那一层会凭空消失。
（本项目已立过的纪律：**平行实现必须同源**。）

## 四、为什么"整句塞进去"是白做

查询侧的匹配规则（`WorldKnowledgeQueryService.cs:212`，`FindCandidates` 内）：

```csharp
if (text.IndexOf(pair.Key, …) < 0 && pair.Key.IndexOf(text, …) < 0) continue;
```

**双向整串包含**：要么"关键词是问句的子串"，要么"问句是关键词的子串"。

- 关键词「帕拉汶德」（4 字）：问句「帕拉汶德是谁的」包含它 ⇒ 命中。
- 如果把整条综述「拉迈萨位于耶什姆海东岸的开阔平原，附近有稀疏的金合欢树林，阿塞莱最好的马匹在此放养。」
  （52 字）当成**一个 term** 塞进去 ⇒ 问句永远不可能整串包含这一整句 ⇒ **一次都不会命中**。

⇒ 所以"放进索引"的**真实含义**是两步，缺一不可：
1. **拆**：把综述切成 term —— **原词（按标点/虚词断）＋ 2-gram（两字一组）**；
2. **改匹配粒度**：匹配改成"按 term 命中"，不再是"整串包含"。

> 这一条正是设计文档 `docs/AI-Retrieval-Memory-Principles-20260815.md:299` 早就写下的要求：
> 「`keywords/title/documentId/`**`content`**` 归一化后拆成 term；中文 term 用**关键词原样 ＋ 2-gram 兜底**」。
> ⇒ 不是新主意，是**补做**。

## 五、★ 排序那一关（这里最容易埋雷）

`MatchQuality`（`WorldKnowledgeQueryService.cs:229-244`）给的位次是：

| 位次 | 条件 | 「具体度」取什么 |
|---|---|---|
| 0 | 标题**整句**等于问句 | 标题长度 |
| 1 | 某个关键词**整句**等于问句 | 该关键词长度 |
| 2 | 标题与问句互为子串 | 标题长度 |
| 3 | 关键词与问句互为子串 | **匹配到的最长关键词长度** |

排序是 `Rank` 升序 → 同级按 `Length` **降序** → 再按 Id。

⚠️ **两个必须处理的点：**

1. **综述命中必须排在真关键词之后。** 否则"标题/别名/关键词"这三层被综述压掉，等于拿噪声盖住正典。
   ⇒ 给综述单独一个位次（如 **4**）。
2. **位次 4 的「具体度」不能用"综述有多长"。** 综述 51 字 ⇒ 恒为最长 ⇒ 同级里**永远排第一**。
   这正是**今天刚删掉的 `doc.*` 那个病**（37 字符的 id 凭串长压过真关键词）——
   ⇒ 位次 4 的 Length 只能用**实际命中的那个 term 的长度**，不能用整条综述的长度。

## 六、不要去动的那一处（会白做）

包里**确实**带了一份关键词倒排表：`runtime.json` → `indexes.keywordToEntryIds`，
且 `index.json` 里有一份同样的。但它在本仓源码里**只有一个读取者**：

```
WorldbookPackageIntegrity.cs:132-134
  Require(runtimeIndexes["keywordToEntryIds"] == index["keywordToEntryIds"] …)
  Require(runtimeIndexes["domainToEntryIds"]   == index["domainToEntryIds"]   …)
```

⇒ **它只被"对账"读，搜索一行都不读它。**
搜索用的是 `_snapshot.KeywordIndex` —— **运行时加载时自己现建的**那份（§三 那两处）。

⇒ **若把综述拆 term 写进编译期那份索引（`RuntimePackageCompiler`）：**
- 要重编 448 档、要重投包；
- 运行时**照样不读**它；
- **净收益 0。**
**⇒ 落点选运行时那两处，不动包、不动编译器。**

### 第 1 步 · 改（3 处，都在 `src/`）

★ **关键取舍：综述命中走"兜底"通道，不与关键词混算。**

理由两条：
- 关键词那条路径**一行不改** ⇒ A 组那 7 条**结构上不可能掉**（靠结构保证，不靠测试保证）；
- 2-gram 若混进同一张表，任何问句都会共享几个 gram ⇒ **过匹配**，把关键词层冲稀。

具体：

| # | 改点 | 内容 |
|---|---|---|
| 1 | `WorldKnowledgeModels.cs` | 新增 `FallbackTermIndex`（term → ids），与 `KeywordIndex` **并列**，不混 |
| 2 | `WorldKnowledgeLoader.cs` | 新增 `internal static class WorldbookTermIndex`（**建表＋切词的唯一实现**）。`BuildKeywordIndex` 末尾调它；`WorldKnowledgeQueryService.RebuildKeywordIndex` 也调**同一个**它 ⇒ 两处平行实现**结构上同源** |
| 3 | `WorldKnowledgeQueryService.cs` | `FindCandidates`：先按原逻辑查 `KeywordIndex`；**仅当一无所获**才调 `FindFallbackCandidates` |

**⚠️ 两处与原方案的偏离（已执行时改的，理由在此显式说明）：**

1. **表名不叫 `SummaryTermIndex` 而叫 `FallbackTermIndex`**：词表来源实测是**标题＋综述**（不止综述），
   叫 `Summary…` 名不副实。**关键词不进这张表**（它自己那条路径仍在）。
2. **没有给 `MatchQuality` 加位次 4**，而是让兜底自带一套排序（共享 term 数 → 最长共享 term → id）。
   理由：`MatchQuality` 那四级的语义是「**整串**全等／互为子串」，往里面塞一个「term 重叠」的位次
   **会污染原语义**；而兜底路径本来就与关键词路径互斥，**自带排序更干净，也让「既有位次一个字不动」变成结构性事实**。
   ⇒ 原方案"Length 不能用综述长度"的顾虑随之消失（兜底根本不用 `MatchQuality`）。

- **拆 term 的规则**：起点 = 标点断开 ＋ 2-gram（虚词先不丢，简单可测）；测完再决定去不去虚词、要不要加权。

## ✅ 第 3 步结论（2026-09-16 实测定案）

**最终取值（都在源码里，带注释）：**

| 旋钮 | 取值 | 位置 |
|---|---|---|
| `FallbackMinSharedTerms`（至少共享几个 term） | **1** | `WorldKnowledgeQueryService.cs` |
| `FallbackMaxCandidates`（最多吐几条） | **5** | 同上 |
| `MaxTermDocumentFrequency`（高频 term 不进口，覆盖条目数上限） | **40** | `WorldKnowledgeLoader.cs`（`WorldbookTermIndex`） |
| 拆 term 规则 | 去标点断句 → 每段原样（≥2 字）＋ 段内全部 2-gram；**虚词不丢** | 同上 |

**为什么阈值取 1 而不是当初写的 2（数说了算）：**

| 高频词截断 | 阈值 | B_hit1 | B_hit3 | 合计_hit1 | 笼统话最坏候选数 |
|---|---|---|---|---|---|
| 不截断 | 1 | 7/13 | 9/13 | 16/26 | **205** |
| 不截断 | 2 | 5/13 | 7/13 | 14/26 | 87 |
| 40 | 1 | **7/13** | **9/13** | **16/26** | 67 →（加候选上限后）**5** |
| 40 | 2 | 5/13 | 7/13 | 14/26 | 67 |
| 20 | 1 | 7/13 | 9/13 | 16/26 | 67 |

⇒ 阈值 2 **白白丢掉 2 条召回，且没能拦住洪水**；阈值 1 ＋「高频 term 不进口(40)」是同时拿到最好召回与最坏情形减半的组合。
（截断从 40 再收到 20 数字完全不变 ⇒ 取 40，**最小干预**。）

**为什么还要"候选上限 5"这条：** `Query()` 的输出受 `ByteBudget`（默认 4096 字节）截断、且**按本方法的排序顺序装**
（`WorldKnowledgeQueryService.cs` 的循环）⇒ 排第一的正确答案一定进得去，砍尾巴只省 token、不丢答案。
实测：`村民的一亩地归谁` 2 条、`帝国的一座城` 恰好 5 条（卡住上限）。**这条把 205 那类洪水关掉了。**

**两条"我以为 vs 实测"（写下来防止下次又拍脑袋）：**
1. 我原以为「单个 term 就会召回一片」⇒ 阈值必须 ≥2。**实测：三个无关话探测在阈值 1 和 2 下都给 0**，
   它们根本判不出阈值好坏。真正能量出差别的是**笼统话**（`村民的一亩地归谁`），而那组是后来才加的。
2. `说说这座城堡坐落于哪儿` 召回 **67 条**，我一度以为是自己引入的过匹配。**开/关兜底对照：都是 67**
   ⇒ 那是**关键词层「整串包含」的既有性质**（短/泛关键词一撞就中一片），**本轮不动、也不认领**。

**⚠️ 一处刻意分叉（别被数字误导）：** Python 探针的 `CheapIndex` 臂给 B **5/13**，上线给 **7/13**。
两者**机制不同**——那臂是「全库 2-gram 打分」，上线是「仅兜底的 term 通道 ＋ 高频词不进口 ＋ 候选上限」。
⇒ 那条臂只用来回答「补 summary 值不值」，**不是上线实现的复刻，不能拿来预测上线数字**；
调参一律跑 C# 验台（约 4 秒一轮、带回门禁）。已在 `_bge_probe_20260916.py` 的 docstring 里写明。

**验台新增三条对照（都在 `RetrievalProbeCases.cs`，每条都必须是"能判"的）：**
① 无关话 ≤3 条候选（阴性对照）；② 笼统话 ≤5 条候选（**真能判上限**，且故意写死独立数字，源码常量被放宽时门禁会红）；
③ 关键词路径的 67 条只报数、不设门禁（既有行为，见上）。
