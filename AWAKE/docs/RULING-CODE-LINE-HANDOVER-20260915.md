## 二、裁决 1 · 三条腿的排序

**结论：先把上面那一跑收口，再走 A；B、C 排后。**

1. **第 0 件（优先于 A）**：定位上表四个缺陷。其中两个疑在框架侧，且**已经在游戏内发生**。
   本线自己说过"零游戏内验证本身可能就是最该先解的一件事"——我同意，而且**这件事已经开了头**，先把它用完。
2. **第 1 件 · A（工具候选）**：唯一"纯接线"，成本最低；而且它正是 v0.3「活起来」的素材——
   工具候选接上了，NPC 才谈得上"做事"。**先做它。**
3. **B（事件落盘）、C（资产与生图）排后**：两者都要动框架。**框架的注入口一旦开始加就是一轮大改**，
   不该和 A 混在一批里做。
   （C 的生图已有**原版源码可 port、片 1 已落地**，比原先估计便宜；但**片 2 要碰共享协议**、片 3 要搬 728 行资产 CAS
   ⇒ **排序不变**：先 A，再回 C 的片 2。）

> 排序理由不是"难度"，是**风险隔离**：A 是接线，改坏了只影响一个调用点；B/C 是改框架，改坏了影响所有线。

## 五、裁决 4 · 状态列"从证据自动生成"

**结论：方向对，但现在不做。先做一件小得多的事。**

**为什么方向对**：手工维护的状态列**必然腐烂**，本项目已经验证三次——
`AWAKE-CURRENT.md`（83 KB，名字叫当前、装的是 08-24～09-11）、`control-plane/CURRENT.json`（指针指向不存在的 checkpoint）、
`AWAKE-VALIDATION.md`（停 09-11，E3/E4/E5 全 `unverified`）。**状态是人手写的 ⇒ 状态会骗人。**

**为什么现在不做**：
- 自动生成需要一套**稳定的证据锚点约定**（你提的"每个能力登记三个锚点、由探针跑"），这套约定本身要设计。
- 更关键：**它必须有游戏内判据才有意义**。现在离线全绿、游戏内零判据 ⇒ 自动生成出来的状态**只会是"全绿"**，
  比人写的**更有欺骗性**，因为它穿着"自动、客观"的外衣。
- 项目里已有反例教训：**恒 False 的判据＝从未执行的校验；恒 True 的判据＝没测。**
  锚点选错，自动生成会产出**系统性假绿**。

**⇒ 先做这件小的**：把那份清单的「当前状态」列**直接删掉**（或整列标注"停更于 08-28，勿引用"），
只留「能力 ＋ 证据锚点在哪」。**先停止生产假状态，再谈自动生成。**
等游戏内判据成型、探针能跑，再把锚点接上自动生成——那时它才有真值可跑。
