# 斯拉涅斯之拥 · 从 AF 独立版更新计划借鉴清单

> 日期：2026-08-14
> 来源：`AnimusForgeHoukai/下一步工作计划与更新方案_20260814.md`、`PLAN-DivineAlchemyTaboo-20260813.md`、`审查与验证记录.md`、`通俗内容说明.md`
> 原则：只借鉴流程、机制、验证和可玩性设计；不复制 AF 的反射/Harmony 依赖，不引入爱与恨耦合。

## 1. 流程与验证门禁

| AF 的做法 | 斯拉涅斯之拥现状 | 建议 |
| --- | --- | --- |
| 阶段 0 游戏内验证 → P1 稳定 → P2 体验 → 发布门禁 | 已有构建 + SdkSmoke，但游戏内验证未形成固定门禁 | 每个功能批次增加 `RUNTIME_VERIFICATION_PENDING` 标记，玩家确认前不宣称通过 |
| 每次更新固定动作：构建、离线验证、同步、文档、运行时标记 | 部分手动执行 | 为斯拉涅斯之拥补 `tools/verify_altar_runtime.ps1` 或至少写固定验证清单 |
| 游戏内验证闭环输出日志和体感 | 游戏日志已有，但缺“体感验收”模板 | 每个批次列出玩家该测什么、看什么日志 |
| 普通修复不随意提版，发布稳定包才升级 | 当前 v0.0.2 已保持稳定 | 继续沿用，不因功能数量提版 |

## 2. 结算与防刷

| AF 的做法 | 斯拉涅斯之拥现状 | 建议 |
| --- | --- | --- |
| 整批预检，任一失败整批拒绝，不部分入账 | 祭坛计划已采用原子预检 | 保持并扩展：所有带成本/奖励的动作都走 dry-run |
| 被拒事件不烧冷却、不写完成记录 | 祭坛计划已采用 | 后续事件系统沿用，不单独写完成标记 |
| 拒绝路线不扣成本、不发奖励，选项显式分类 | 女神效果桥已有 allowlist | 未来事件选项加入显式 accept/refuse/neutral，不按 ID 猜语义 |
| 成本与返还二段式：GoldCost / GoldDelta | 祭坛计划可吸收 | 后续任何金币玩法统一“成本 + 返还”语义，避免净额歧义 |
| 独立每日上限：工作台净值、普通事件、技能 XP 分开 | 祭坛计划有每日档位限制 | 增加独立 `AltarGoldNetDailyLimit`，与普通事件互不污染 |
| 世界影响关闭时，所有带原生效果的动作/事件整体禁用 | 已有 `EnableWorldEffects` | 关闭时不仅拒绝命令，也应隐藏/禁用献祭与奖励入口，避免白嫖愿力 |
| 技能经验按门类注入，18 技能全覆盖，混合拒绝 | 尚未接入技能经验 | 后续若献祭/祈祷给技能，直接采用五大门类 + 单技能 + 每日上限模型 |

## 4. 可玩性设计

| AF 的做法 | 斯拉涅斯之拥现状 | 建议 |
| --- | --- | --- |
| 大地图“齁改”总览入口 | 目前只有城镇/城堡/村庄/领主府菜单 | 后续加“斯拉涅斯之拥”总览：祭坛、神谕、愿力、状态 |
| 独立营地菜单 + 驻营等待 | 暂无自有营地 | 若做营地玩法，参考 AF 自建菜单，不挂原版不存在的 camp 菜单 |
| 五档金币阈值缩放 | 祭坛目前固定三档 | 后续可按玩家金币动态分档，前期买得起、后期有感 |
| 神谕/炼金/禁忌三条玩法线各自闭环 | 目前只有神谕 + 祭坛 | 未来神术、禁忌、炼金按“独立入口 + 独立冷却 + 独立账本”拆开 |
| 发情周期统一时钟和 HUD | 尚未接入 | 借鉴 7 天周期和大地图 HUD，但由马库斯/本模组自建 |
| 事件链 flag 推进 | 暂无事件链 | 未来事件用 flag + 冷却推进，不靠随机重复触发 |

## 5. 日志与可观测性

| AF 的做法 | 斯拉涅斯之拥现状 | 建议 |
| --- | --- | --- |
| 结构化日志名，普通日志不刷屏 | SlaaneshLog 已有基础 | 增加菜单/献祭/恢复/补偿的结构化事件名 |
| 开发者模式才输出诊断类日志 | 部分已有 | 全局应用：非开发者模式只写关键路径 |

| 日志定位失败层 | 已有部分 | 每个失败都带 code / correlation，方便排查 |

## 6. 不建议复制

- 不复制 AF 对 AnimusForge 的反射签名表、Harmony patch 依赖。
- 不复制爱与恨本体接口，斯拉涅斯之拥保持独立。
- 不复制 AF 的事件 JSON 包结构，除非未来做自有事件目录时借鉴 schema 审计方法。
- 不复制 AF 的“合并 Standalone + Adaptive”双模式，斯拉涅斯之拥目前只做独立版。

## 7. 下一步优先级

1. 先吸收“验证门禁”：给祭坛/献祭批次建立运行时验证清单，不宣称游戏内通过。
2. 再吸收“日志与原子结算”：献祭日志结构化、补偿路径可追踪。
3. 后续做技能奖励、事件链、总览 UI 时，再引入 AF 的数值模型。
4. 神术、炼金、禁忌等未来玩法按 AF 的“独立闭环”思路拆开设计。
