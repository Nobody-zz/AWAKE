## 三、★★ 与 §七 原方案的差异（本节最该读）

§七 的改动清单第 1 项是「**删掉** `NpcDialogueService.cs:1125-1128` 的提前 return」。**实际没删，也不需要删。**

**为什么：**

- 那处提前 return 本身的语义是"不能开口就别装配"，**它没错**。错的是 `AllowsAi` 的定义（只认 known/partial）。
- 把 `AllowsAi` 改成新语义后，这一处**自动就对了**：`not_found` 通过，`blocked`／`referral` 继续短路。
- **保留它反而是对的**：`blocked`／`referral` 短路时不必白跑一遍装配（`PersonaSessionHydrationAdapter.HydrateAsync` ＋ `Prompts.CompileAsync`），
  而 §七 §六-4 自己就担心过"放开后可能暴露新的性能与失败点"。

⇒ **§七「两处必须同时改，只改一处等于没改」这个前提，在落点选在 `AllowsAi` 定义时不再成立。**
实测推理：`ShouldCallAi = Knowledge.AllowsAi && PromptText 非空`（`WorldKnowledgeModels.cs:322`），
装配跑完、prompt 编译成功 ⇒ `PromptText` 非空 ⇒ **只改 `AllowsAi` 一处，链路就通**。
§七 那句推理（"只改 2 ⇒ 装配根本没跑"）建立在 `AllowsAi` 的旧定义上。

**那第二处（`BuildPromptBlock`）为什么还是改了？** 理由和 §七 写的不一样：
- 不是为了"链路通"，而是**不让"给不给知识"继续绑在"能不能开口"上** —— 否则 `not_found` 时会给模型一份写着"知识状态：not_found"的空知识块，等于两根绳子还粘着；
- 同时保住 `dialogue_context.knowledge = present/absent`（`NpcDialoguePromptPipeline.cs:181`）的语义：
  若在知识层塞文案，它会一律变成 `present`，这个现成观测点当场作废。
