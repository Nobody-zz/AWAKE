# AWAKE 原版状态适配层规范 v1

> 状态：架构规范草案；本文件不批准运行时代码实现、不修改冻结候选、不修改游戏目录。
>
> 编制日期：2026-08-23
>
> 目标版本：Bannerlord v1.3.15 / AWAKE 0.2.x 设计基线
>
> 相关原生审计：`docs/mappings/bannerlord-native/关系-家族-家庭-外交原生映射表-v1.md`

## 1. 规范目的

本规范定义 Bannerlord 原版社会状态如何进入 AWAKE，以及 AWAKE 如何把原版状态转换成自己的行为、知识和记忆用途。

核心原则只有一条：

> **原版提供权威游戏事实；AWAKE 用自己的确定性代码进行语义转换；AI 只生成表达，不直接结算数值或修改世界状态。**

AWAKE 不复制一套“看起来像原版”的关系系统，也不把原版数值原样塞进提示词。原版关系、家族、家庭和外交状态必须先经过适配层，才能被知识调取、对话、主动行为或事件系统使用。

## 2. 已确认的事实与范围

### 2.1 已确认的原版事实

本规范依赖本机 Bannerlord v1.3.15 对应 BLsource 静态审计，已确认：

- 原版基础角色关系是 `-100..100` 的持久角色对关系，并且关系键按 Hero ID 排序，不能表达方向性信任。
- `Hero.GetRelation` 是经过有效角色映射和人格修正后的关系，不等同于基础关系。
- `Hero.IsFriend`、`Hero.IsEnemy` 等敌友判断使用基础关系阈值，不应被有效关系替代。
- 原版没有独立持久的“家庭好感度”或“家族好感度”字段。
- 家庭主要是父母、配偶、子女等拓扑关系；家庭成员的数值关系仍走角色关系。
- `Clan.GetRelationWithClan` 与 `FactionManager.GetRelationBetweenClans` 是不同的家族关系计算路径，不能混成一个字段。
- 原版已有族长更换后的关系迁移逻辑，AWAKE 不得再造一套族长关系扩散公式。
- 原版外交主要通过 `StanceLink`、战争/和平、贡金和战争统计表达，不是一个独立的连续王国好感值。
- `ChangeRelationAction` 是原版关系变化的合法入口；AWAKE 不得直接改写原版关系管理器内部字典。

### 2.2 AWAKE 当前事实

当前 AWAKE 已有：

- `WorldStateStore` 中的 `awake.relationships` 自定义状态。
- `trust`、`love`、`hostility` 三个 `-100..100` 轴。
- 关系状态当前以单个 `heroId` 为核心，尚未形成明确的 source → target 方向性关系键。
- `NpcProactiveService` 当前将三轴压缩为 `trust + love - hostility` 的 `affinity`。
- 当前 AWAKE 源码没有接入 `Hero.GetRelation`、`ChangeRelationAction`、`CharacterRelationManager` 或家族关系 API。

因此，当前 `trust/love/hostility` 不是原版关系的镜像，而是 AWAKE 独立的自定义状态。后续接入原版数据时不得静默改变其语义。

### 2.3 本规范第一阶段范围

第一阶段只冻结以下内容：

1. 原版状态的只读快照模型。
2. 原版字段到 AWAKE 用途的明确映射。
3. 纯代码语义投影的边界。
4. 对话、知识和主动行为如何消费投影结果。
5. 原版关系写回的合法入口和禁止事项。
6. 离线测试和后续真机验证要求。

第一阶段不实现新的关系公式，不修改现有 `trust/love/hostility` 的存档结构，不把原版关系自动同步进 AWAKE 状态。

## 3. 权威边界

```text
Bannerlord 原版运行时状态
        │ 只读采集
        ▼
AWAKE Native Snapshot
        │ 确定性代码投影
        ▼
AWAKE Semantic Context
        │ 按用途选择
        ├── 对话上下文
        ├── 世界知识权限判断
        ├── NPC 主动行为
        ├── 事件规则
        └── 周报/日志摘要

AWAKE 事件结算
        │ 仅在确有原版玩法影响时
        ▼
原版合法 Action 入口 + AWAKE 自定义状态命令
```

### 3.1 原版状态的权威性

以下内容必须以原版运行时为准，AWAKE 只读或派生：

- 角色基础关系；
- 角色有效关系；
- 原版敌友布尔状态；
- 角色所属家族、家族族长和家族等级；
- 父母、配偶、子女等家庭拓扑；
- 家族关系聚合结果；
- 王国或派系之间的姿态、战争/和平状态；
- 原版战争统计和贡金状态。

AWAKE 可以缓存短生命周期快照，但缓存不是新的权威来源。

### 3.2 AWAKE 状态的独立性

以下内容属于 AWAKE 自己的状态，不能被原版字段直接覆盖：

- 是否相信某个具体说法；
- 某个信息来源的可信度；
- 玩家是否曾经欺骗、帮助或背叛 NPC；
- 某条知识是否已被该 NPC 听闻；
- 对某件事的记忆、怀疑和误判；
- 情境性信任、戒备、依赖、兴趣或敌意。

原版关系可以作为这些状态的输入或先验，但不能默认等于这些状态。

## 4. 字段适配矩阵

下表是第一版适配层的权威字段矩阵。`直接调用` 表示某个 AWAKE 判断可以直接使用原版 API 的语义结果；`代码投影` 表示必须由 AWAKE 代码根据用途转换；`不自动变动` 表示读取原版字段不会自动修改 AWAKE 持久状态。

| 原版字段/结果 | 原版来源 | 原版语义 | AWAKE 使用方式 | 是否可直接调用 | 是否自动改变 AWAKE 状态 | 备注 |
|---|---|---|---|---|---|---|
| 基础角色关系 | `CharacterRelationManager` / `Hero.GetBaseHeroRelation` | 原始、持久、对称的角色关系 | 需要原始关系语义的敌友、关系事件和原版兼容判断 | 是 | 否 | 不可当作方向性信任 |
| 有效角色关系 | `Hero.GetRelation` / `DefaultDiplomacyModel` | 经过有效角色映射和人格修正的社会关系 | 对话基线、合作倾向、社会距离 | 是 | 否 | 与基础关系可能不同 |
| 原版友好状态 | `Hero.IsFriend` | 基于基础关系的友好判断 | 原版友好门槛的兼容判断 | 是 | 否 | 不用有效关系重新推导 |
| 原版敌对状态 | `Hero.IsEnemy` | 基于基础关系的敌对判断 | 威胁、敌对交互和原版行为门控 | 是 | 否 | 不用 AWAKE affinity 替代 |
| 原版中立状态 | `Hero.IsNeutral` | 基于基础关系的中立判断 | 无专门友好/敌对状态时的回退 | 是 | 否 | 仍需保留其他事件上下文 |
| 所属家族 | `Hero.Clan` | 角色当前的家族归属 | 判断家族政治、身份和知识范围 | 是 | 否 | 不复制成 AWAKE 家族好感 |
| 家族族长 | `Clan.Leader` / 原版族长状态 | 当前家族权威角色 | 族长相关关系、家族意见和权威传播 | 是 | 否 | 族长更换后必须重新取快照 |
| 家庭拓扑 | `Hero.Father`、`Mother`、`Spouse`、`Children` 等 | 亲属结构 | 家庭事件、家庭知识范围和关系语境 | 是 | 否 | 拓扑不是数值好感 |
| 有效家族关系 | `Clan.GetRelationWithClan` | 双方族长有效关系的家族层读取 | 家族间政治或外交语境 | 是 | 否 | 不用于个人信任 |
| 领主加权家族关系 | `FactionManager.GetRelationBetweenClans` | 按领主、族长、配偶权重聚合的运行时结果 | 需要原版家族关系聚合语义的政治判断 | 是 | 否 | 不是独立存档字段 |
| 派系姿态 | `StanceLink` / `FactionManager` | 中立、战争、和平等派系状态 | 战争知识、外交行为和世界事件上下文 | 是 | 否 | 不转换成王国好感度 |
| 战争统计 | `StanceLink` 相关统计 | 战争持续时间、伤亡、围城、劫掠等事实 | 周报、战争知识和事件条件 | 是 | 否 | 需按事件或报告窗口读取 |
| 贡金状态 | 原版外交/姿态数据 | 贡金方向、剩余期数等 | 外交知识和政治事件上下文 | 是 | 否 | 不自动改变 NPC 信任 |
| 关系变化事件 | `ChangeRelationAction` 及原版事件 | 原版关系发生合法变化 | 触发 AWAKE 快照失效、事件记录或规则评估 | 监听/读取 | 仅按显式规则 | 不是所有变化都等于信任变化 |
| 族长更换事件 | `ChangeClanLeaderAction` | 原版族长和关系迁移已结算 | 清除旧快照、重新读取家族语境 | 监听/读取 | 否 | 禁止重复传播关系 |

### 4.1 直接调用的条件

只有满足以下条件时才允许直接使用原版结果：

1. AWAKE 要表达的正是该原版结果的语义。
2. 调用点明确写出使用的是基础关系、有效关系、家族聚合还是派系姿态。
3. 调用不把该结果重新保存成同名的 AWAKE 权威字段。
4. 调用不会在游戏 tick 中重复访问或持有 TaleWorlds 实时对象。

### 4.2 代码投影的条件

以下用途必须经过 AWAKE 代码投影，不能直接把原版数字传给 AI：

- 玩家说法是否更容易被相信；
- NPC 是否愿意透露所属阶层不应公开的知识；
- NPC 是否愿意主动接近玩家；
- NPC 是否愿意执行一个有风险的请求；
- NPC 是否把玩家的行为理解为挑衅、讨好、欺骗或威胁；
- 原版关系如何影响 AWAKE 的记忆更新。

这些都是 AWAKE 玩法语义，不是原版字段本身的定义。

## 5. 建议的数据契约

以下是实现阶段应采用的逻辑契约。字段名是内部代码契约，最终可以按现有项目命名规范调整，但语义不得改变。

### 5.1 原版只读快照：`NativeSocialSnapshot.v1`

```text
snapshotVersion
sourceHeroId
targetHeroId
capturedAtGameTime

baseRelation
effectiveRelation
nativeFriendState
nativeEnemyState
nativeNeutralState

sourceClanId
targetClanId
sourceClanLeaderId
targetClanLeaderId
sameClan
familyLinks[]

effectiveClanRelation?
weightedClanRelation?
factionStance?
warContext?
```

约束：

- 只保存稳定 ID、标量、枚举和短数组，不长期持有 `Hero`、`Clan`、`Kingdom` 等原版对象。
- 不可取得的值使用明确的 `unknown`/缺省状态，不用 `0` 伪装成中立或没有关系。
- `baseRelation`、`effectiveRelation` 和敌友状态必须分开保存。
- `sameClan` 只能由家族 ID 计算，不能由族长关系推断。
- `familyLinks` 是拓扑标签，不是关系数值。
- 该快照是派生缓存，不进入 AWAKE 存档作为权威关系状态。

### 5.2 AWAKE 语义上下文：`AwakeSocialContext.v1`

语义上下文由纯代码从原版快照和 AWAKE 自定义状态组成，供具体业务使用：

```text
nativeSocialBaseline
nativeConflictState
familyContext
clanContext
politicalContext
knowledgeDisclosureContext
beliefContext
requestDispositionContext
proactiveContext
```

不同业务只取自己需要的投影，不允许所有业务共享一个未经解释的 `affinity`。

### 5.3 当前 AWAKE 关系状态的处理

在没有经过独立迁移计划前：

- `trust`、`love`、`hostility` 继续作为 AWAKE 自定义状态读取。
- 原版关系不自动覆盖三个轴。
- 三个轴不自动写回原版关系。
- 新适配代码不得继续扩大 `affinity = trust + love - hostility` 的适用范围。
- 任何需要同时使用原版关系和 AWAKE 三轴的业务，必须在自己的投影函数中明确两者的用途。
- 未来要支持 NPC-NPC 方向性关系时，另行设计 source/target 关系键和存档迁移，不在本规范内偷偷改变现有键。

## 6. 语义投影目录

### 6.1 社会交往基线

用途：决定 NPC 与玩家是否愿意继续进行普通交往。

允许输入：

- 原版有效角色关系；
- 原版敌友状态；
- 家族归属和家庭关系；
- 当前场景、身份和正在发生的事件；
- AWAKE 记忆中的近期行为。

输出应是可解释的代码结果，例如：

- `open`：愿意正常交谈；
- `guarded`：愿意交谈但保持戒备；
- `cold`：只进行必要交流；
- `hostile`：进入敌对或拒绝交往路径。

该投影不直接改变任何关系值。

### 6.2 知识分享基线

用途：决定 NPC 是否有资格知道、愿意说出或能够验证某条世界知识。

允许输入：

- NPC 身份、阶层、职业和所在地；
- 世界书授予的知识权限；
- 原版家族/政治/战争事实；
- 原版有效关系作为社会合作倾向；
- AWAKE 对玩家的信任和近期记忆；
- 当前是否存在风险、旁听者或利益冲突。

输出应拆开：

- `knowledgeAccess`：是否知道；
- `expressionDetail`：最多能说到哪种详细程度；
- `willingness`：是否愿意说；
- `verificationAbility`：是否有能力核实；
- `referralTarget`：不知道时是否转介给公证商人、赎金经纪人、酒馆老板等广知 NPC。

原版关系只能影响“愿不愿意合作”一类因素，不能越权授予 NPC 不属于其身份的知识。

### 6.3 玩家传授知识后的相信判断

用途：决定 NPC 是否接受玩家传授的说法、暂时记住、怀疑或转述。

代码必须分别考虑：

- NPC 是否本来就知道这件事；
- NPC 是否亲历过相关事件；
- 玩家与 NPC 的原版社会关系；
- AWAKE 方向性信任和近期欺骗记忆；
- 玩家身份、声望和可验证证据；
- 说法是否与 NPC 已知知识冲突；
- NPC 是否有渠道核实；
- 该说法对 NPC 是否有利。

该投影的输出不是一个 AI 自由填写的百分比，而是代码定义的有限结果，例如：

- `accept`;
- `tentative`;
- `skeptical`;
- `reject`;
- `refer_for_verification`。

具体权重、阈值和衰减公式必须另立数值方案，经审查后才能进入代码。

### 6.4 请求结算

用途：决定 NPC 是否接受玩家请求、提出条件、拖延、拒绝或转为敌对反应。

原版关系可以作为社会态度基础，但不能单独决定结果。至少要与以下因素分离：

- 请求风险；
- 身份和权力差；
- 利益；
- 家族或政治后果；
- NPC 当前知识和目标；
- AWAKE 记忆中的承诺、欺骗和报复。

输出应是代码枚举，不是 AI 自由决定：

```text
accept
accept_with_condition
delay
refuse
retaliate
escalate_to_authority
```

### 6.5 NPC 主动行为

当前 `NpcProactiveService` 使用 AWAKE 三轴 `affinity`。适配原版状态时，第一版只允许把原版快照作为额外上下文输入，不能直接把原版关系加进现有 `affinity`。

后续应将主动行为拆为独立因素：

- 社会可接近性；
- 主动动机；
- 当前风险；
- 最近互动冷却；
- 原版敌对门控；
- AWAKE 记忆和自定义状态。

在该拆分完成前，不得宣布“原版关系已经接入主动 NPC 系统”。

## 7. AI 上下文边界

### 7.1 默认不发送原始数字

AI 默认只接收经过代码处理的语义标签和允许范围，例如：

```json
{
  "social_baseline": "guarded",
  "native_conflict": "none",
  "same_clan": false,
  "family_link": "none",
  "knowledge_access": "partial",
  "expression_detail": "summary",
  "belief_outcome": "skeptical",
  "request_outcome": "accept_with_condition"
}
```

除非某条专门路由明确需要，`baseRelation`、`effectiveRelation` 等原始数字不得进入提示词。

### 7.2 AI 不拥有结算权

AI 可以：

- 识别玩家说法的主题和意图；
- 选择符合代码结果的表达风格；
- 生成 NPC 的自然语言回复；
- 提供待审查的语言建议。

AI 不可以：

- 自己决定 NPC 是否知道某条知识；
- 自己授予身份权限；
- 自己修改原版关系；
- 自己写入 `trust/love/hostility`；
- 自己创造未经事件系统确认的世界事实；
- 自己把错误说法写入客观世界知识库。

## 8. 读取、缓存与失效

### 8.1 读取原则

- 游戏数据读取走 AWAKE 的 `GameData`/上下文适配边界，不让业务层到处访问 `Campaign.Current`。
- 适配层在安全生命周期或一次业务请求开始时生成快照。
- 对话、知识和主动行为在同一结算链中复用快照，不重复读取同一组 Hero/Clan 数据。
- UI/campaign tick 中不得执行阻塞的文件、网络或存储操作。

### 8.2 快照失效事件

以下事件发生后，相关快照必须失效或在下一次使用时重新读取：

- 角色关系变化；
- 族长更换；
- 角色加入、离开或更换家族；
- 婚姻、配偶或家庭拓扑变化；
- 战争/和平姿态变化；
- 贡金状态变化；
- 当前战役或会话切换。

第一版如果无法可靠订阅某类原版事件，必须采用短生命周期读取，而不是无限期缓存。

### 8.3 缺失数据回退

- 当前没有 Campaign、目标 Hero 不存在或数据不可用：返回 `unknown`，不伪造中立。
- 原版字段暂时无法读取：跳过需要该字段的 AWAKE 投影，保持原版行为不变。
- 原版关系不可用时：不得用 AWAKE `affinity` 冒充原版敌友状态。
- AWAKE 存储不可用时：使用无自定义记忆的安全回退，但不改变原版关系结果。

## 9. 原版写回边界

### 9.1 默认只读

原版关系读取接入后，默认模式是只读。读取原版状态不会自动造成任何写入。

### 9.2 允许写回的唯一条件

只有 AWAKE 事件已经完成代码结算，并且该事件确实应影响原版玩法时，才允许：

```text
AWAKE 事件
→ Preflight / 权限 / 幂等校验
→ 计算原版关系变化量
→ 调用 ChangeRelationAction 等合法原版入口
→ 记录事件和结果
→ 使原版快照失效
```

禁止：

- 直接修改 `CharacterRelationManager` 内部关系字典；
- 直接改写原版 Hero 的私有或存档字段；
- 用 AWAKE 自定义关系状态持续覆盖原版关系；
- 因为 AI 输出了“关系变好/变坏”就直接写回原版；
- 重复实现族长更换时的关系迁移；
- 把家族聚合关系拆成并写入多个个人关系。

### 9.3 双写的一致性

如果一次 AWAKE 事件同时影响原版关系和 AWAKE 自定义状态，必须保留同一个：

- `eventId`；
- `correlationId`；
- `causationId`；
- `idempotencyKey`；
- 结算前快照 token；
- 原版写回结果；
- AWAKE 状态写入结果。

任一侧失败时不得伪造“双写成功”。具体补偿策略另列实施计划。

## 10. 推荐实现分层

实现阶段建议保留以下职责边界：

| 组件 | 职责 | 不负责 |
|---|---|---|
| `NativeSocialSnapshot` | 保存一次读取得到的稳定标量快照 | 保存原版对象、决定行为 |
| `BannerlordNativeSocialReader` | 在安全入口读取原版 Hero/Clan/派系状态 | 写回原版状态、生成 AI 文本 |
| `AwakeSemanticProjector` | 将快照和 AWAKE 状态转换为业务语义 | 访问网络、修改存档 |
| `KnowledgeAccessPolicy` | 判断身份、知识权限和表达详细度 | 判断原版敌友、写关系 |
| `BeliefResolutionPolicy` | 结算玩家传授内容的接受结果 | 生成最终对话文本 |
| `NativeRelationMutationGateway` | 通过原版 Action 执行批准的关系变化 | 自己维护第二张原版关系表 |
| `AwakeSocialContextProvider` | 为 AI 路由提供已筛选的语义上下文 | 把原始数字直接塞进提示词 |
| `WorldStateStore` | 保存 AWAKE 记忆和自定义状态 | 保存原版关系镜像 |

这些名称是实现建议，不代表本文件已经批准新增类或接口。

## 11. 数值和公式门禁

本规范故意不在此处批准具体权重或阈值。后续数值方案必须逐项回答：

1. 该数值来自原版还是 AWAKE 自定义？
2. 是直接调用、区间映射、事件增量还是长期衰减？
3. 数值是否有方向性？
4. 是否持久化？存档键是什么？
5. 是否会和原版同类数值重复计算？
6. 该数值影响哪一个具体行为，而不是“所有行为”？
7. AI 是否完全不需要自行计算？
8. 原版状态变化后何时重新计算？
9. 数值不可用时如何回退？
10. 如何通过离线测试证明边界和单调性？

第一批公式设计必须先产出“数值来源与公式表”，通过单独的机制审查后才能进入代码。

## 12. 非目标

本规范不包含：

- 新的家族好感公式；
- 新的家庭成员关系传播公式；
- 玩家信任度最终公式；
- 将 `trust/love/hostility` 合并成统一社会分数；
- NPC-NPC 全量方向性关系存档迁移；
- 自动把 AI 回复写入世界知识库；
- 自动同步或覆盖冻结的 AWAKE 游戏候选；
- 启动 Bannerlord 进行真机测试。

## 13. 实现前验收标准

只有满足以下条件，适配层实现才算达到本规范要求：

### 13.1 静态与单元验证

- 原版基础关系、有效关系、敌友状态分别有独立读取和测试夹具。
- 测试证明敌友判断不会错误使用有效关系替代基础关系。
- 测试证明家族关系不会被当作个人信任。
- 测试证明家庭拓扑不会被当作数值好感。
- 测试证明族长更换后不会叠加 AWAKE 自定义传播公式。
- 语义投影输入相同，输出稳定且不依赖 AI。
- 原版数据不可用时返回 `unknown` 或安全回退，不伪造 `0`。

### 13.2 接线验证

- 对话入口能够获取一份与本次请求一致的原版快照。
- 知识权限入口能够消费身份/家族/战争语义，但不会越权授予知识。
- 主动 NPC 入口明确记录是否使用原版投影；在未接线前不得声称已接入。
- 原版关系写回只经过 AWAKE 命令治理和原版 Action 入口。
- AWAKE 自定义状态仍通过 `WorldStateStore`，不写入原版关系表。

### 13.3 性能与运行安全

- 同一业务结算链不重复读取相同 Hero/Clan 数据。
- 不在游戏 tick 中进行网络、文件或阻塞存储操作。
- 不长期持有 TaleWorlds 实时对象。
- 快照具有明确生命周期和失效条件。
- AI 提示词默认不携带原始关系数字。

### 13.4 证据等级

- `E0`：本规范、字段矩阵和实现计划完成。
- `E1`：编译、解析和适配层单元测试通过。
- `E2`：离线 smoke 覆盖读取、投影、缺失回退和命令拒绝。
- `E3`：新候选构建、同步和哈希核对完成。
- `E4`：用户运行匹配 BuildId 的游戏，完成对话/知识/关系入口闭环。
- `E5`：验证存档、读档、族长更换、战争状态变化后的重建和时间线隔离。

本文件完成后最多宣称 `E0`，不代表运行时已经接入原版关系。

## 14. 下一批实施顺序

在通过项目要求的 grill、独立只读审查和用户签收后，按以下顺序实施：

1. 建立原版社会状态读取边界和稳定快照 DTO。
2. 用离线夹具验证基础关系、有效关系、敌友和家庭/家族拓扑的差异。
3. 建立第一版纯函数语义投影，先只输出标签和门控结果，不写新公式。
4. 将投影接入一个只读对话上下文入口。
5. 接入知识权限判断，但保持知识权限由世界书和身份规则决定。
6. 单独设计并审查数值公式，再决定是否接入主动 NPC 和 AWAKE 自定义状态。
7. 最后再设计原版关系写回命令和双写持久化，不与只读批次混在一起。
