# 超轻量本地模型 · 检索方案调研（09-16）

> 背景：关键词识别红测（`REDTEST-KEYWORD-20260916.md`）暴露 48 条样本 **RED 30**。
> 本问：换超轻量本地模型来检索，会不会靠谱一些？最轻量的能不能达标？
> **本报告只做纸面调研与方案判断，未下载、未运行任何模型**（按甲方要求）。候选模型的体积/参数量来自公开模型卡与实测帖，非本机实测。
>
> ⛔ **前置红线（09-16 二次核实补入）**：`AF-CRITICAL-EVALUATION-20260815.md` 已把「本地 ONNX / embedding / rerank 推理」列为**明确不学**，理由见其 §ONNX 教训（自写 tokenizer、自建推理栈、硬塞 native 依赖）。该裁决**未过时**。
> ⇒ 本报告的价值是**把代价量化清楚**，不是给"上模型"开绿灯。真要动，先走规则 3 的论证前置。
>
> ✅ **09-16 二次核实**：本机 `Modules/AnimusForge/ONNX/` 是一份**正在运行的现成双模型实现**（`onnx=True` 443 次、`semantic_done` 475 次实测），拆解见 `../ANIMUSFORGE-LOCAL-MODEL-ANALYSIS-20260916.md`。下文带"二次核实"标记的段落据此修正。

## 一、先给判断

**模型这条路技术上完全可行、成本也比想象低（最轻 23 MB、纯 CPU、.NET 原生、不需要 Python）；但它不是"替换检索"，而是"多叠一路召回"——而且它治不了红测里最贵的那条。**

三句话：

1. **能治**：错别字、同音、换说法（语义级相似）——这是子串方案结构上做不到的。
2. **治不了**：`doc` 命中全库 458 条这类**过匹配**。那是**数据问题**（keywords 里写了内部编号），换模型不修数据，照样炸。
3. **而且不划算**：红测 30 条红里，**大头根本不需要模型**——「归一化 + 拼音 + 编辑距离」用几 KB 的表就能打掉错字/同音/繁简/全半角/词中空格标点五大类，**显存占用是 0**。

> ⚠️ **反直觉但重要**：embedding 会**加剧**过匹配。它在语义空间里把「铁帽」和「铁甲」拉得很近——红测里 `铁` 已经答出了无关的【奢华布面铁甲】，上了 embedding 只会更糟。
> ⇒ **embedding 不能单独用，必须与精确匹配混合**；混合之后，过匹配那一半还是得改数据。
>
> **09-16 二次核实 · 这条已被真机佐证**：AnimusForge 的融合打分里，词法锚点是**独立分量**——
> `raw= ctx= mixed= rerank= amp= rank= candidate= lexicalAnchor= matchedSeed= intent=`
> 它保留 `lexicalAnchor` / `matchedSeed` 和 `CalculateTokenOverlapScore`，从设计上就没让向量承担"文本里有没有提到某个词"。
> ⇒ 指望"换 embedding 自动免疫 `doc` / `war` 过匹配"，方向就是错的；真机也是靠词法通道兜这一层。

## 三、"关键词检索基本功能"能不能达标

按红测口径定三条判据：

| 判据 | bge-small-zh-v1.5（INT8） | Qwen3-Emb-0.6B | 纯算法（归一化+拼音+编辑距离） |
|---|---|---|---|
| ① 认错字/同音（`锅奎`→锅盔） | ✅ 能 | ✅ 能 | ✅ 能（同音+1字差） |
| ② 不炸泛词（`盔`/`doc` 不该命中一片） | ❌ **反而更炸** | ❌ **反而更炸** | ✅ **能**（加长度/占比门槛即可） |
| ③ 资源（显存/内存/延迟） | ✅ **23 MB，CPU 几 ms** | ⚠️ 610 MB，CPU 780 ms/句 | ✅ **0，微秒级** |
| ④ 换说法（"头上扣的那口锅"） | ✅ 能 | ✅ 更强 | ❌ 不能 |

**结论：最轻的模型在"认错字"这一条上达标，在"不炸泛词"上反而倒退。**
⇒ 它是**补充**，不是**替代**。

**部署可行性（09-16 二次核实，已按 AnimusForge 真机修正）**：

原写"用 NuGet `Microsoft.ML.OnnxRuntime` + `Microsoft.ML.Tokenizers`（含 `BertTokenizer`）"——**真机实测与本机现成实现的实际情况**：

- `Microsoft.ML.OnnxRuntime`（官方托管封装）**确实可用、且真机在用**：Bootstrap 每次启动 `Preloaded private dependency 'Microsoft.ML.OnnxRuntime ... from ...\bin\Win64_Shipping_Client\Microsoft.ML.OnnxRuntime.dll'`，与原生 `onnxruntime.dll` 配套，**不需要 Python、不需要独立服务**。这一条维持。
- **但分词库不是现成的**：真机 bin 里只有 `onnxruntime.dll`，**没有 `Microsoft.ML.Tokenizers`** ⇒ 它是**自写**的（DLL 字符串有 `BertNormalizer`），并且自写带来了静默失效风险（分词失败退化成常量向量，不抛错）。
- 本机就有一份**可直接对照的现成实现**（`Modules/AnimusForge/ONNX/`，含双模型 + 分词器 + 门控 + 降级链），若要评估方案不必从零起步。

⛔ **更重要的前提**：项目在 `AF-CRITICAL-EVALUATION-20260815.md` 已把「本地 ONNX / embedding / rerank」列为**红线**，规则 3 要求"任何必须在游戏侧跑本地模型的需求，先说明框架能力为何不足、替代方案为何不可行，再决定是否立项"。
⇒ **本报告第四节第 3 步（加 bge-small-zh 做语义召回）与这条红线直接冲突**，不能直接执行；要先按规则 3 走论证，或先证明 Marcus RAG 覆盖不了。

## 四、建议路线（分三步，前两步做完再评估第三步）

| 步 | 措施 | 成本 | 预期打掉 |
|---|---|---|---|
| **1** | **归一化 + 拼音 + 编辑距离**：Unicode 归一化、全角→半角、繁→简、去空白与词中标点、大小写折叠；建拼音索引做同音匹配；短词加最小长度/占比门槛 | **0 显存，几 KB 表**，纯 C# | 错别字 3/3、同音 2/2、繁体 3/4、空格 4/4、标点 3/6、全半角 1/1、过匹配大部分 |
| **2** | **修 keywords 数据**：生成器不再把 `doc.<id>`／分类名／原始 XML id 写进 keywords | 生成器改一行 + 全库重生成 | `doc` 命中 458 → 0；`geography` 408 → 0 |
| **3（可选）** | 加 **bge-small-zh-v1.5 INT8** 做语义召回，与精确匹配**混合排序** | 23 MB + ONNX 运行时 | 换说法/长句描述 |

**为什么这个顺序**：第 1、2 步会大幅改变"还需不需要模型"。先做，再评估——否则是拿模型去补一个改一行数据就能补的洞。

**若一定要上模型，选 `bge-small-zh-v1.5` INT8**：体积最小（23 MB）、中文够用（57.8）、MIT 可商用、CPU 就能跑。
**不要直接上 0.6B 或加 reranker**——AnimusForge 的实测代价摆在那里：reranker 一层就是 **1.036 GiB**，而它每轮对话花在检索上的开销（~400 ms）几乎全在**词法实体检索**上，语义阶段只报 1.6–4.6 ms。
> 原写"延迟 ×500"，是未实测的拍脑袋数字，已删除。

## 六、两个后续核到的事实（09-16 晚补，**会改变本报告的取舍方向**）

问题"要不要上轻量模型"的前提，比本报告前四节设想的**要更靠前一步**：**语义这一格在 AWAKE 里本来就是空的，而且是"留了位、没人实现"。**

### 事实 1 · 我们现成的 RAG 也是**词法**检索，不是语义

`AWAKE/src/AwakeHostComposition.cs:73` 原文注释：

> `// RAG 数据面经 IPC 转发给 Runtime Service；SQLite/FTS5 与语料仍由服务侧独占。`

⇒ **RAG 侧 = SQLite FTS5 全文检索 = 词法。**

而设计文档 `AI-Retrieval-Memory-Principles-20260815.md:21-24` 写的三级回退是：

```
→ 语义层：Marcus RAG（慢、但语义泛化）        ← 实现是 FTS5（词法）
→ 本地回退：倒排索引关键词命中                  ← 也是词法
→ 无命中：不注入，用女神本知/角色本知作答
```

**⇒ 三级里最高的两级，实现上其实是同一类（词法）。「语义」这一级是空的。**

⇒ 这把本报告的病根判断往前推了一层：**现在的漏报不只是"子串匹配太笨"，而是整条链上没有任何一级做语义。**
⇒ 也纠正一个可能的误解：**不是"有 RAG 却还漏"，是两级都是关键词。** 所以第 3 步（加语义召回）不是"锦上添花"，而是**补上一个设计里早已声明、实现里一直空着的层级**。

### 事实 2 · 框架把 embedding / rerank 的接口留好了，**实现是"宿主不可用"占位**

| 层 | 证据 | 状态 |
|---|---|---|
| 接口 | `framework/MarcusAwakeFramework/src/Compat/IAiModelService.cs:10` `EmbedAsync(EmbeddingRequest, ...)` → `OperationResult<EmbeddingResult>`；同类还有 `RerankAsync` | ✅ **已定义** |
| 能力声明 | `Compat/ProviderCapabilityInfo.cs:20` `EmbeddingDimensions`；构造参数含 `bool rerank` | ✅ **已定义** |
| 真实实现 | `HostApi.cs:1046-1051` `UnavailableAiModelService` —— `EmbedAsync` / `RerankAsync` 都是 `HostUnavailable.TaskFailure(...)` | ❌ **占位（宿主不可用）** |
| 配置 | `docs/profiles.awake.deepseek.routes.json` 两处 `"embeddingDimensions": []` | ❌ **空数组** |
| AWAKE 侧 | `grep EmbedAsync` 在 `AWAKE/src/` 无实现 | ❌ **无人实现** |

**⇒ 结论：这一格不是"要不要造"，是"留了位、没人填"。** 接入形状（接口、能力声明、配置字段）都已经存在。
⇒ **代价评估应据此下调**：不需要新增架构概念，只需给出一个实现者 —— 这也正是"要不要动"必须先说清"在哪一格填"的原因。

> ⚠️ **这不改变红线。** `AF-CRITICAL-EVALUATION-20260815.md` 对"本地 ONNX 推理栈"的否决（自写分词、自建推理栈、硬塞 native 依赖）**仍然成立且未过时**。
> 事实 2 只说明"位置现成"，**不说明"应该现在填"**。填法可以是：① 本地模型（撞红线，需按规则 3 论证）；② **云端 embedding 接口**（框架本就是云端优先，`embeddingDimensions` 是路由级配置）；③ 暂不填，先做第四节的第 1、2 步。
> ⇒ **②此前没被摆上桌**，而它绕开了红线，且与现有 `allowCloud: true` ＋ `pinModel: true` 取向一致。**待裁决。**

### 对第四节"建议路线"的影响

**顺序不变**（先规则 + 修数据，再评估要不要模型），但第 3 步的性质变了：

| 原表述 | 现在应表述为 |
|---|---|
| "加 bge-small-zh 做**语义召回**（可选增强）" | "**把设计里已声明、实现里空着的『语义层』补上**（选本地还是云端，见事实 2 三条路）" |

⇒ 若只问"**关键词检索**这个功能"够不够用 —— 事实 1 说明：**要的是"关键词检索"，那本来两级都是关键词，规则 + 修数据就能达标，不需要模型**；
⇒ 只有要"**语义检索**"（换说法、同义、长句描述），才轮到模型 —— 而那才正是设计里空着的那一格。

### 事实 3 · `Summary` 字段：**448/448 全都有，而且不参与检索**（09-16 晚实测）

甲方追问「知识字段加语义简述层？」——**字段早就有了，问题在检索不看它。**

| 项 | 实测值 | 出处 |
|---|---|---|
| 字段定义 | `internal string Summary { get; set; }` | `AWAKE/src/WorldKnowledgeModels.cs:34` |
| **填充率** | **448 / 448（100%）非空** | 实测 `ModuleData/Worldbook/packages/calradia/runtime.json` |
| 长度 | 中位 **51** 字（17–108） | 同上 |
| **唯一读取点** | `WorldKnowledgeQueryService.cs:312`：`entry.Summary + Environment.NewLine` —— **只拼进输出文本** | 该文件 |
| 检索是否用它 | **❌ 完全不用**。`FindCandidates`（`:206-223`）**只查 `_snapshot.KeywordIndex`** | 该文件 |

样例（`awake:entry:culture.tales-charas-origins`）：
```
title:    Charas Bay: Three Origins 沙拉斯湾·三种来历
summary:  帝国"摇篮"史称、先祖登陆传说（未经确证）与船人怪谈：三种口径分层记录。
keywords: ['沙拉斯湾·三种来历','Charas Bay: Three Origins','沙拉斯湾',
           '帝国摇篮','卡拉德登陆','Charas Bay','doc.culture.tales-charas-origins']
```
⇒ 这句 summary 里已经含着**「摇篮／登陆／传说／怪谈／史称」**等玩家极可能说到的词，**但检索一个都不看**。

**⇒ `Summary` 的现状身份：给模型读的「前言」，不是用来找条目的「入口」。**

**顺带把红队那条系统性问题量化了**（同一份实测）：keywords 中位 **5** 个（3–9），**448/448 条目都含 `doc.*`**
⇒ **中位每条 5 个关键词里，就有 1 个是内部编号** —— 检索面上有 1/5 是噪声。

#### 评估：「把 Summary 纳入检索」值不值得做

| 维度 | 判断 |
|---|---|
| 成本 | ⚠️ **比"改一处"重，我先前说轻了**：见下"为什么没接上"——**索引里根本没有 summary 的字** ⇒ 要动**索引构建**（`WorldKnowledgeLoader.cs:160` `BuildKeywordIndex`）＋ 检索函数；索引结构在包内，**可能还要重编包并重投**。零模型、零显存、不撞红线。 |
| 收益 | 匹配面从"中位 5 个关键词"扩到"一句 51 字的自然语言" |
| ⚠️ 天花板 | **扩的是"可命中的词"，不是语义** —— 玩家说的词仍须出现在那句话里。**与 keywords 同类，只是更高** |
| ⚠️ 风险 | **过匹配会加重**（summary 是长句，反向匹配 `kw.IndexOf(text)` 下短词命中面更大）⇒ **必须同时收紧匹配方向 ＋ 加长度门槛**（与 §三判据②一致） |
| ❌ 治不了 | `doc.` 那种过匹配（**那是数据脏**）；以及"没命中就哑火"（**那是门**，见 `../AWAKE-KNOWLEDGE-GATE-20260916.md`） |

⇒ **定性：这是介于「纯关键词」与「上语义模型」之间的一个合理中间档** —— 便宜、马上可做、不撞红线；
⇒ **但它不是语义层。** 要真正跨过"玩家得说中文本里有的词"这条线，才需要事实 1/2 那一格。

#### 为什么它没被接上（09-16 晚查证）

**结论：不是"故意不用"，也不是"漏了一行 if"——是索引那一步压根没收它的字，而接缝就在这里。**

三条证据：

| # | 证据 | 说明 |
|---|---|---|
| 1 | **索引只从 keywords 建**：`WorldKnowledgeLoader.cs:160-170` `BuildKeywordIndex` **只遍历 `entry.Keywords`**，从不读 `entry.Summary` | **summary 的字从来没进过 `KeywordIndex`** ⇒ `FindCandidates` 查索引自然查不到。**不是检索函数漏写，是索引里没这些词。** |
| 2 | summary 唯一读取点是拼装输出：`WorldKnowledgeQueryService.cs:312` | 它进的是**"给模型读的正文"**，不是检索的引子 |
| 3 | 契约表：`worldbook-studio-plan/RUNTIME-MAPPING-CONTRACT.md:101` | `/summary` → **「现有 v1 映射：无字段」→ `unsupported_for_v1`** ⇒ 它进来时的定位就是**"包里的内容"**，不是"运行时消费字段" |

⇒ 合起来：**summary 从落地起职责就是"让模型读着顺"，检索那一路（索引 ＋ 匹配）压根没朝它看过。**

⚠️ **但没有任何一处文档写下过理由。** 按本项目的纪律（"判缺陷先查有没有写下理由"），
