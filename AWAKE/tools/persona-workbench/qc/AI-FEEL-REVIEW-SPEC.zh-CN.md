# 角色卡 AI 感检查规范

本规范给角色卡作者和审阅者使用，配合 `AUTHORING-GUIDELINES.zh-CN.md`。它不替代 schema、事实考据、tag 注册或运行时验台，也不增加角色卡字段。

## 1. 这里说的“AI 味”是什么

本规范不判断一段文字是不是机器写的。它检查玩家是否会感到人物只是套了不同名字的同一套回答。审阅时找以下可观察问题：

- **人物可互换**：同一情境下，换一个人物名字，决定、理由和让步条件仍然成立。
- **素材像填空**：句子换了地名、家族或物产，人物的选择没有变化。
- **表达像模板**：多条内容反复使用相同的句子骨架、开头、转折或结尾，内容只填进插槽。
- **没有具体依据**：卡把地点关系扩写成某项职权、责任、经历或动机，而来源没有证明这一层。
- **只会背卡**：回答反复复述卡片中的完整句子，或用人物口号代替回答玩家正在问的事。
- **脱离对话**：无视玩家问题、当前事实或不知道的内容，直接输出预制人格介绍。

这些信号要分开记录。句式相似可以提示复核，却不能单独证明人物相同；句式不同也不能证明人物有区别。

## 2. 写卡时的检查

### 2.1 先写“判断”，再润色文字

修改运行时字段前，作者先用自己的工作笔记回答下列问题。笔记不要求添加进 persona JSON：

1. 这个人遇到什么具体事情？
2. 他会采取什么行动，或拒绝什么？
3. 他这样做的理由是什么？
4. 这样选择会付出什么代价，或放弃什么？
5. 哪种条件会让他改变做法？若没有已知答案，就写“未知”，不要补造。
6. 这些判断分别由哪条人物、游戏或内容来源支持？来源究竟证明了什么？

如果只能写出“他很谨慎／重视家族／有野心”，还不能据此编出具体管理行为。先找证据，或把素材留白。

### 2.2 让样本体现人物，不规定统一句型

- `selfClaimRules` 写人物在特定话题或压力下会如何收放信息。避免同一批卡都写成“只说 X，不说 Y”。
- `realSelfBehaviors` 写有证据支持、人物实际能做的行为。不得仅凭“属于某地”推导征税、经营、调兵或治理权限。
- `selfClaimExamples` 遵守现有编写准则的条数与第一人称叙事要求，写成决策素材，不把它当可背诵的对白库。场景和对象应能从文本读明白；不要要求每条都用括号开场或同一长度。
- 不要求每个人物都消费某个 ASSET，也不把文化常见物产自动转成人物底线、习惯或动机。
- 不用近义词替换、扩长句子、打乱标点来制造表面差异。若去掉专名后只剩同一条行动逻辑，仍按模板化处理。

### 2.3 关联证据要写到它能证明的层级

逐条核对素材关联：

- `confirmedFor: place` 只支持人物与地点的关系。
- 它本身不能证明人物掌管当地事务、靠某项物产谋生、为其承担责任，或愿为其付出代价。
- 找不到证据时标记“待查”或留白；不要把“当前未找到”写成“此人没有这种关系”。
- `depth` 是关系强度描述，不能代替字段适用性判断，也不是允许写入某个字段的授权。

审阅记录至少写：卡名、字段与条目、原文、具体主张、来源位置、来源实际证明范围、结论（有据／待查／越界）和修改动作。

## 3. 脱名盲测

盲测检查实际模型输出。选同一文化或同一王国中至少三位处境有差别的人物；准备同一组情境，每个情境使用相同输入。先隐藏姓名、地名和家族名，再混排回答。情境至少包含：

1. 普通身份或日常问题；
2. 利益冲突或玩家提出代价；
3. 玩家质疑人物判断；
4. 关键事实不足、人物需要承认不知道或追问。

每组做两次采样，用于观察模型输出波动；记录模型、参数、种子、模板和卡片哈希。先按当前完整链路生成 DSL 与提示词，再请求本地模型。不得手抄提示词或自行拼 DSL。出现 legacy fallback、未注册 tag 或不完整输入时，这组样本不能用于角色表现判断。

每个回答分别按以下四项记 `0 / 1 / 2 / 无法判断`，并引用原句作为理由：

| 项目 | 0 | 1 | 2 |
|---|---|---|---|
| 接住问题 | 没回答问题 | 部分回答或转移 | 正面回应了当前问题 |
| 人物差异 | 与其他人可互换 | 有差别但主要靠专名或文化符号 | 选择、理由或条件能区分人物 |
| 事实依据 | 编造事实、经历或职权 | 有未经证实的扩写 | 只使用已给事实，并能承认未知 |
| 表达自然 | 像口号、说明书或固定台词 | 有局部套话 | 语气符合当下关系和情境，不靠复述卡片 |

单个分数不是放行线。以下情况必须返修并复测：出现无依据的事实或权限；多个人物在关键情境中的决定和理由可互换；回答反复用卡片句子代替回应；或审阅者不能解释差异来自人物自身什么特点。审阅者意见不一致时保留争议样本，补证据或改卡后重测，不取平均分掩盖分歧。

若只有一位审阅者，至少隔一段时间重新打乱样本再评一次；将两次判断不同的条目标为待定。允许“无法判断”，不能为了得到通过结论而强行打分。

## 4. 自动检查怎么用

在 `D:\AWAKE-Dev` 运行：

```powershell
py -3 -m unittest discover -s AWAKE/tools/persona-workbench/qc -p test_persona_aifeel.py -v
$defs = '.workbuddy/tmp/pilot_trial/def_after'
$links = 'AWAKE/tools/persona-workbench/persona_links.pilot.json'
$card = (Get-ChildItem AWAKE/tools/persona-workbench/characters -Filter '*ulbos*.persona.json' | Select-Object -First 1).FullName
py -3 AWAKE/tools/persona-workbench/qc/persona_aifeel.py audit --definitions $defs
py -3 AWAKE/tools/persona-workbench/qc/persona_aifeel.py relations --definitions $defs --links $links
py -3 AWAKE/tools/persona-workbench/qc/persona_aifeel.py chain $card --model ministral-3:8b
```

- `audit` 汇总物化后的运行时文本字段；草稿字段不参与。句式家族、长度、结尾等是定位线索，不是 AI 味总分。
- `relations` 把已记录的人物关联证据上限与行为句并列，提醒审阅者查证；它不理解语义，也不自动批准主张。
- `chain` 复制角色卡和 `.origins.json` 到临时目录，经真实物化器、DSL 生成器、C# 提示词模板和渲染器运行。fallback 或未注册 tag 会阻断。`--force-approved` 只用于离线验台，不代表角色卡状态已获生产批准。
- `answers` 严格检查本地模型回答格式；格式不合规的原文不会进入合规回答统计。若围栏中的 JSON 能提取回复，工具可把它放在 `diagnostic_only` 供人看文风，这仍是格式失败。
- 检查结果没有统一数值门槛。少于三张卡时不得作跨人物结论。报告里的风险句必须由人回看上下文和来源。

## 5. 返修顺序

每个问题先归到一个主要责任层，避免同时改卡和提示词后无法知道原因：

1. **载荷或 tag 失效**：先修注册、物化或 DSL 链路，重新确认人物内容真的进了提示词。
2. **事实或权限越界**：修来源关联、人物卡主张，必要时删除无依据内容。
3. **人物决策互换**：修人物的判断、理由、代价和条件；不要先改语气词。
4. **卡内模板或口号复读**：改写决策样本的内容与组织方式，避免只做近义替换。
5. **卡片有差异但模型输出仍撞脸**：保存完整提示词与回答，再检查统一提示词、情境、模型及采样波动。一次只改一个因素并复测。

修改后使用相同人物、相同问题、相同模型设置重跑；同时保留失败样本。机器指标变好但盲读仍可互换时，按未解决处理。

本规范的通过记录应包含：卡片哈希、来源记录、DSL/提示词哈希、模型与采样设置、盲测原文、逐项理由、发现的问题和对应修改。离线盲测属于 E2 证据，不代表游戏内 E4/E5 已通过。
