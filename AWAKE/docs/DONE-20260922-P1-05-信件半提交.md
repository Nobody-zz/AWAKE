谁也不知道。修法＝把编排从 UI 依赖里摘出来 + 给半提交留一条可查痕迹。

## 二、夹具的第一堵墙（派工单要求必须回答，不许复述任务）

`AppendLetterAsync` 名字叫「写正文」，实际是**两处写**：先落正文（Transcript 命名空间），
再写一次联系人索引（`AwakeTranscriptService.cs:173 EnsureContactAsync`，Contacts 命名空间）。
只注入 Transcript 与 Letters 两只存储时，这一步整条返回 false ⇒ **半提交窗口根本走不到**，
而且没有任何报错指向"你少注入了一只"。三只必须一起注入。已写进用例注释。

## 三、(g) 重试能不能收敛 —— 同键能，换键不能；而调用方走的是换键

- **同键重试**：正文不重复、账本补上 ⇒ 收敛。
- **换键重试**：正文出现第二份、账本多一封信 ⇒ 不收敛。
- **调用方现状**：`AwakeMessengerVM.SendLetterAsync`（`AwakeMessengerVM.cs:595-599`）把
  `conversationId` 传成 `string.Empty`；`AwakeLetterService.SendAsync`（`:146-148`）于是每发一次
  现取一枚 `Guid` 当幂等键 ⇒ **实际路径走的是"换键"那一支**。
- ⇒ 严重性不是"窗口期不一致"，是**重试即重复**：玩家在失败提示后重点一次发送，正文多一份、账本多一封。
  **这一条超出本单六项范围，属我在过程中另外发现（见第七节 §3）。**

## 四、(h) 只有生命周期、没有正文的账本记录 —— 分两种，行为完全不同

- **正文被校验拒**（超长，> transcript 层 1200 字节上限）：没有命令入队 ⇒ **账本落得下**
  `failed` 留痕；读侧表现为一条 `status=failed`、`failureReason=transcript_write_failed` 的记录，
  **不计未读**（`AwakeLetterConstants.IsUnreadStatus` 不含 failed）。
- **正文写盘失败**（真故障、可重试）：**账本留痕落不下去**（`failureRecorded=False`，实测）。
  机制：可重试的失败命令以 deferred 留在 store 队列里，同一实例内后续命令的落定判定被一并染成
  "未落定"（`WorldStateStore.cs:2361` DeferredRetry；`:2379` IsPersisted 要求 `!DeferredRetry`）。
- ⇒ 这套「正文没落盘就落一条 failed 留痕」的降级，**只在校验拒那条路上有效，在真故障那条路上失效**。

## 七、我自己在过程中发现的问题（派工单要求非空）

1. **信件服务此前没有任何判据保护，这是结构性的。** `AwakeLetterService.cs` 不在
   `AWAKE.Tests.csproj` 的显式清单里 ⇒ 这个文件里的任何改动，离线验台与三根门禁都不编它。
   不是"漏了一条用例"，是"这条路从来没有闸"。今天把编排摘出来才第一次有了。
2. **一笔可重试的写失败会传染给后续所有写。** 见第四节第二条：降级留痕在真故障路径上失效。
   它意味着「写失败之后做补救写入」这个模式在当前 store 上不可靠。P1-01／P1-02 与它同区，建议合看。
3. **幂等键取自 `conversationId`，而调用方传空** ⇒ 重试不收敛、重复落正文（第三节）。
4. **`AwakeRuntime.SetWorldStateStore(null)` 是空操作。** `AwakeRuntime.cs:501` 第一句就是
   `if (store == null) return false;` ⇒ 用例里 `finally { AwakeRuntime.SetWorldStateStore(null); }`
   自以为在清场，其实没清（`Program.cs:2695` 就是这么写的）。⇒ 用例之间的世界状态是**互相看得见**的，
   与用例表头"级联失败"那条警告同根。
5. **用例表存在状态耦合，且与用例完成度相关**：`g3-s0-focused-readiness` 只在
   `letter-half-commit` **提前中止**时跟着红（级联）。本次五轮读数完全符合该规律（我这条绿 ⇒ 它绿；
   我这条红中止 ⇒ 它红）。不是新问题，但值得记一笔：它的成败依赖前序用例有没有跑完收尾。
