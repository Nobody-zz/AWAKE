## 9 · 标签 vs 行文：对得上，但只是"整体上对得上"

拿同一批 2850 对卡，用**同一对**算两个数：

- `tagJaccard` = 两张卡标签集合的 Jaccard
- `idfCos` = 两张卡**全部文字字段**（`core`／三层 description／`tensionAxes`／三个作者数组／`commitmentProfile` 等，见 §9.1）拼起来后的 **5-gram IDF 加权余弦**

| 项 | 实测 |
|---|---|
| 打乱对照（同卡字序打乱、字频保留） | **cos 中位 = 0.000** ⇒ 虚词贡献被 IDF 压干净了 |
| 探针自检（同卡对自己） | cos = **1.000** |
| 真 `idfCos` 分布 | min 0.001 / 中位 **0.006** / p90 0.016 / max **0.059** |
| **Spearman(tagJaccard, idfCos)** | **+0.521** |
| 置换零假设（把标签在 76 张卡之间随机重排，200 次） | ρ 带 = **[−0.044, +0.047]**，中位 −0.000 |

⇒ **实测 +0.521 落在零假设带外很远** ⇒ **标签确实携带行文之外的信息，不是摆设。**
分桶中位也单调：tag[0,0.1)→0.004、[0.1,0.2)→0.006、[0.2,0.35)→0.007、[0.35,0.6)→0.010、[0.6,1]→0.015。

**两条修正**：

1. **行文并不雷同。** 第一版用裸 5-gram Jaccard 得中位 0.038，看着像"大家写得差不多"——
   那是**假象**，0.038 几乎全是中文虚词 5-gram 的贡献（打乱字序后对照为 0.000）。
   加了 IDF 之后真实重合中位 0.006、最大 0.059 ⇒ **76 张卡在措辞层面是分得开的**。
   ⇒ 与 §4 的"3 条骨架告警"一致：文字层的雷同**只有那么几条**，`PersonaCorpusAudit` 报的数量是对的。
2. **但尾部松。** 有 **25 对**卡：标签**完全不重叠**（Jaccard=0），行文却挤进前 10%
   （cos ≥ 0.016）；最像的前两对里，`阿巴该↔雅那`(tag 0.167)、`乌尔玻斯↔弥娜`(tag 0.364) 标签都不算近。
   ⇒ **标签列不能单独当"这两张不一样"的凭证**，只是"整体上有相关"。

> §9.1 取证口径：文字字段 = 卡 JSON 里**递归收集的全部字符串**（键名排序后拼接），
> 归一化去标点空白，取 5-gram。IDF 字典在真文本＋打乱文本上统一构建（避免打乱文本产出字典外的 shingle —— 第一版就是在这里 `KeyError` 挂的）。
> 逐卡字数 min 1371 / 中位 1749 / max 3214 ⇒ 无过短样本。

## 20. 重来第三轮：打「±3 是谁产出的」

### 20.1 打什么

接 §19.4 的挂账：「±3 无生产者」到底等于「工作台之外另有写手」，还是「走了一条我漏看的落盘口」。

### 20.2 结果一：落盘口只有一个，而它是「提交口」不是「生成口」

把 Web 层四个能碰到 document 的服务挨个看完：

| 服务 | 产出什么 | 落盘吗 |
|---|---|---|
| `PersonaPreviewService` | `PersonaPreviewResponse`（`IsValid` / `Dsl` / `Errors`） | **不落** |
| `BatchGenerationService` | `BatchGenerationResult`（`Draft` / `Dsl`） | **不落** |
| `MaterialImportService` | `MaterialSegment[]`（把粘贴文本切段落） | **不落** |
| **`WorkspaceDocumentService.SaveWithStatus`** | **写 `*.persona.json`** | **落** |

而这一个落盘口的入参是：

```csharp
public sealed class WorkspaceSaveRequest : WorkspaceDocumentRequest
{
    public PersonaDocument? Document { get; set; }   // ← 完整 document，请求体直接给
    public string? ExpectedContentHash { get; set; }
}
```

流程是：`CloneDocument(请求体.Document)` → `candidate.Status = status` → `PersonaValidator.Validate(...)`
→ 通过就 `workspace.Save(fileName, candidate, ...)` 落盘。

> **⇒ 工作台里没有任何一段代码「生成」这 25 根轴或那些标签。它只接收一个已完成的 document，
> 检查它合法，然后写下去。**

**⇒ 上一轮那句「工作台之外另有写手」方向是对的，但说法不准。**
准确的说法是：**落盘口是「提交口」——25 根轴的 1300 个值、227 个标签实例，全部是提交方给的。**

### 20.3 结果二：落盘是机械批量的，排除人工逐张

76 张卡的 `mtime`（毫秒级）：

| 时间 | 张数 |
|---|---|
| **2026-09-15 00:58:15（同一秒内）** | **49** |
| 2026-09-15 01:28:49 | 3 |
| 2026-09-13 23:50 / 23:24 / 23:17 / 23:11 / 23:01 / 21:43 | 5 / 5 / 3 / 3 / 2 / 2 |
| 2026-09-14 00:11 / 00:54 | 3 / 1 |

那 49 张的毫秒戳是**严格递增、每张 +26ms**：

```
00:58:15.3792954  00:58:15.4066189  00:58:15.4323417  00:58:15.4588460
00:58:15.4849800  00:58:15.5119999  00:58:15.5381529   … 直到 49 张写完
```

**人手在 UI 里一张张点，不会出现 26ms 的稳定间隔、也不会让 49 张的秒数完全相同。**
⇒ 这是一次循环写盘。

**排除两个混淆项：**
- `git status -- <characters/>` = **0 改动** ⇒ 不是「刚 checkout 导致 mtime 被统一」。
- `origins.json`（09-12 21:18 / 09-13 12:27）与 `persona.json`（09-13 21:43 起）**时间线分离**
  ⇒ 不是整目录拷贝（拷贝会让两者同批）。

### 20.5 顺带查实：`tools/` 与 `origins` 是同一毫秒区间落盘的

`tools/` 下 19 个脚本的 mtime 全挤在 `2026-09-13 12:27:24.933 ~ .960`（27 毫秒），
