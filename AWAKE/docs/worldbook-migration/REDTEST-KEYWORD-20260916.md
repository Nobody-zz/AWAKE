## 一、结论

**子串匹配这套，在标准问法上准，在真人说话上大面积漏；而它真正的问题不在漏，在"输入短词就炸出一大片、再在噪声里挑冠军"。**

48 条对抗样本：**RED 30 ／ OK 18**。唯一全过的两类是**大小写**（`OrdinalIgnoreCase` 吃掉）和**整句含关键词**（关键词作为子串存在于句中）——正好反证了机制。

| 分组 | RED/总 | 说明 |
|---|---|---|
| 过匹配 | **9/9** | 输入一个泛词，答出完全无关的条目 |
| 空格 | **4/4** | 词中插空格/Tab ⇒ 全漏 |
| 错别字 | **3/3** | 形近/同音/联想错字 ⇒ 全漏 |
| 繁体 | 3/4 | 繁体输入 ⇒ 全漏（A9 是简体对照，命中） |
| 标点 | 3/6 | **词中**插标点 ⇒ 漏；**词后**标点 ⇒ 命中 |
| 简写 | 3/6 | 倒装/拼音首字母 ⇒ 漏；截断/单字 ⇒ 命中 |
| 同音 | 2/2 | 全漏或命中错条目 |
| 边界 | 2/5 | 空串/纯空格 ⇒ 返回无关知识 |
| 全半角 | 1/1 | 全角字母 ⇒ 漏 |
| 大小写 | **0/3** | 全过（`OrdinalIgnoreCase`） |
| 整句 | **0/5** | 全过（关键词在句中即命中） |

## 二、三类根因

### 根因 1 · 漏报：子串连续性被破坏就永久失配（19/35）

子串匹配要求**逐字连续**。任何插入、替换、变换都让它归零：

| 输入 | 期望 | 实际 |
|---|---|---|
| `锅奎` `过盔` `锅灰` | 锅盔 | `not_found` |
| `鍋盔` `護鼻盔` `鏈甲圍帽` | 繁体对应卡 | `not_found` |
| `锅 盔` `护 鼻 盔` `锅\t盔` | 锅盔／护鼻盔 | `not_found` |
| `锅，盔` `锅、盔` `锅-盔` | 锅盔 | `not_found` |
| `盔锅`（倒装） `gk` `hbk`（拼音首字母） | 锅盔／护鼻盔 | `not_found` |
| `ＫＥＴＴＬＥ ＨＥＬＭＥＴ`（全角） | 锅盔 | `not_found` |

**词中 vs 词后是关键分界**：`锅盔。` `，锅盔` `锅盔？！` 全部**命中**（关键词仍连续），而 `锅，盔` 一定漏。⇒ **标点本身不是问题，"插在词中间"才是问题。**

### 根因 2 · 命中错条目：碎片子串被别的卡抢走（2 条）

- `练甲围帽`（链甲围帽 的同音错字）→ 命中 **布制围帽与头巾**
- `链甲 围帽`（词中空格）→ 同样命中 **布制围帽与头巾**

因为 `围帽` 是 `布制围帽与头巾` 的关键词，碎片化后两位候选打平，排序让布制卡赢了 ⇒ **玩家问链甲，拿到布制**。

### 根因 3 · 过匹配：短词/泛词炸出一大片，冠军靠运气（11/13）

`FindCandidates` 的反向匹配 `kw.IndexOf(text) >= 0` 使**任何短词**都能命中所有"包含它的关键词"。实测：

| 输入 | 命中条目数 | 实际答复 |
|---|---|---|
| `盔` | 10 | 【叠穿：盔下的那一层】 |
| `帽` | 7 | 【布制围帽与头巾】 |
| `铁` | 3 | 【奢华布面铁甲】（**答非所问**） |
| `头盔` | 2 | 【链甲围帽】 |
| `helmet` | 10 | 【闭面军阀盔】 |
| `doc` | **14（探针上限）** | 【奢华布面铁甲】 |
| `war` | 11 | 【鳞甲军阀护腕】 |
| `weapons` / `head` | 9 | 【护颊盔】 |

## 三、系统性问题（比单条漏报严重得多）

**458 / 458 条目（100%）都把自己的内部文档 id `doc.<domain>.<slug>` 写进了 `keywords`。**
⇒ 反向子串让**内部编号变成公开检索词**：

| token | 命中条目 | 占比 |
|---|---|---|
| `doc` | **458** | **100%** |
| `geography` | **408** | **89%** |
| `war` / `economy` | 21 | 5% |
| `items` | 15 | 3% |
| `head` | 12 | 3% |

poc2 器物卡还额外把**分类名与原始 XML id** 当关键词：
`["闭面军阀盔","Closed Warlord Helmet","HeadArmor","sturgian_helmet_closed","doc.economy.items-sturgian_helmet_closed"]`
⇒ 输入 `HeadArmor` 命中所有护具条目。

**这不是本批引入的**（`weapons-head-*` 只是沿用同一约定），是**全库生成器约定**。

**真正的伤害不是"答错一条"**：候选池被污染成几百条后，排序（`MatchQuality` 四档 + 串长）在噪声里挑冠军，**答哪条基本靠运气**。

## 四、边界（重要，避免夸大）

1. **空串 / 纯空格 ⇒ 返回一批无关知识**（实测 `known`，答【沙拉斯湾·三种来历】，命中 15 条）。
   但**真实对话入口已挡住**：`NpcDialogueService.cs:225` `IsNullOrWhiteSpace` ⇒ `ImmediateFail("对方在等你开口。")`。
   ⇒ **不是线上故障**；是**共享检索函数的潜在坑**——换调用方（或复用该服务的其它入口）就会踩。根因在 `FindCandidates:208`：空文本返回**全表**。
2. 探针 `hits` 有上限（空输入显示 15 而非 458），故上表 `doc` 的"14"是**探针显示上限**，真实候选为 458。
3. **未测真人语料**：本批是设计好的对抗样本，不是真实玩家日志。查全/查准率仍未量化。
4. **未改任何代码/数据**：本报告只出结论。

## 五、`doc.` 关键词的最终判定（09-16 晚 · 甲方口径 ＋ 查证）

> 本节收敛下节 P0 建议与 `REDTEST-OWN-CLAIMS-20260916.md` §三之二的**分歧**：
> 前者说「**删**」，后者查到 K1 设计注释后改为「**不是删，是让兜底生效**」。**两条都可以收口了。**

**甲方原话（一字不改）：**

> 还有那傻逼doc.，这玩意就不应该写进关键词里。你要么留一个文件名直接强制注入，你他妈的跟关键词能放在一起吗，放在那里想和谁抢语义空间？？？

### 一手证据：设计者与甲方**同一个意见**，但只写在注释里

`AWAKE/tools/worldbook-studio/src/Awake.WorldbookStudio.Core/RuntimePackageCompiler.cs:112-113`：

```csharp
// K1：keywords 是运行时的可读检索词，来源为「标题（多语言）+ 别名（多语言）+ 实体锚点的可读名称」。
// 内部文档 id 保留为兜底检索词并排在最后：它不是玩家/NPC 会用的说法，不应再充当主要关键词。
```

同文件 `:121` `AddKeyword(keywords, addedKeywords, sourceId);` —— **`sourceId`（即 `doc.*`）确实被加在最后**（在 title／aliases／实体锚点名之后）。

⇒ **"它不是玩家/NPC 会用的说法，不应再充当主要关键词" —— 这句话与甲方口径完全一致。**

### 但"排在最后"在运行时**零效果**

| 环节 | 实际行为 |
|---|---|
| `FindCandidates`（`WorldKnowledgeQueryService.cs:206-223`） | 只对 `KeywordIndex` 做**集合成员判定** ⇒ **数组位置完全不参与匹配** |
| `MatchQuality` | 只看**匹配串长度**，不看"这个词来自哪里" |
| ⇒ 结果 | **兜底词与主关键词完全等权**，"排在最后"没有任何语义 |

⇒ ⚠️ **而且它凭长度反超**：`doc.geography.castles-jamayeh-castle` = **37 字符**，比任何真关键词都长；
排序规则是"同级比匹配串长度**降序**（越长越具体）" ⇒ **它一旦命中就排在真候选前面。**
⇒ **这就是"抢语义空间"的确切机制** —— 不是"多占一个词位"，是**凭长度抢排序冠军**。

### 判定：**删是对的** —— 且与 K1 的核心意图一致

K1 有两半：「**不应再充当主要关键词**」（核心）＋「保留为兜底」（附带）。
查证发现**"兜底"这个能力在别处早就有了，不依赖 keywords**：

| "兜底"用途 | 已有实现 | 是否需要 keywords 里的 `doc.` |
|---|---|---|
| 按 id 直接取条目 | **条目本来就有 `Id` 字段**（`_snapshot.Entries[id]`） | ❌ 不需要 |
| 按 id / 关键词搜（开发用） | `WorldKnowledgeQueryService.Search`（`:94-101`）**直接查 `x.Id.IndexOf(text)`** | ❌ 不需要 |

⇒ **keywords 里的 `doc.` 连"开发用途"都不承担，它是纯粹的重复身份。**
⇒ **删掉它 ≠ 删功能**，是删一个**没有任何一处在用**的重复入口；K1 的核心意图（不让它当主要关键词）因此才真正生效。

### 顺带：净化的价值不只在"少一个词"

现在 `keywords` 里混着**两类语义**：「玩家/NPC 会说的词」＋「程序内部编号」。
⇒ 只要这两类还混在一起，**任何基于 keywords 的判断（加权重、2-gram、接 summary、排序）都无法做对** —— 因为分不清"这个命中该算几分"。
⇒ **修法顺序建议：先净化字段语义（拿掉 `doc.`／分类名／原始 XML id），再在干净的字段上做算法。**
（与 `LOCAL-MODEL-SURVEY-20260916.md` §四「先规则＋修数据，再评估要不要模型」同向。）

## 六、修法建议（按优先级，待裁决）

| 优先级 | 措施 | 落点 |
|---|---|---|
| **P0** | 生成器**不再把 `doc.<id>` 写进 `keywords`**；分类名（`HeadArmor`）与原始 XML id 也只在需要时保留 | 全库生成器 + 458 档重生成 |
| **P0** | 反转匹配方向收紧：**只允许 `text.Contains(kw)`**，或对反向匹配加**最小长度门槛**（如 ≥2 字且长度比 ≥0.5） | `FindCandidates:212` |
| **P1** | 入口加**归一化**：全角→半角、繁→简、去空白与标点、大小写折叠 —— 一次性解掉 B/D/繁体三组 | 检索前置 |
| **P1** | 空/纯空白输入**不进检索**（在服务侧而非调用方兜底） | `FindCandidates:208` |
| **P2** | 错别字/同音/拼音：子串方案**结构上解决不了**，需要编辑距离或本地小模型（即 AnimusForge 那条路） | 需架构决策 |
| **P2** | 命中多条时，按"关键词占比"而非"串长"排序，降低碎片误报 | `MatchQuality` |

## 七、顺带发现（非本批主题，红测撞出来的）

`weapons-head-kettle`（锅盔）的**两个 detail 表达都带 `culture_ids`（vlandia / empire）** ⇒ **无文化或非瓦兰迪亚/帝国的贵族拿不到 detail**，掉到村民口吻的 rumor（`state=partial`）。
而 `护鼻盔`／`全覆面盔` 的 detail 无文化限定 ⇒ 任何贵族都是 `known`。
锅盔是**通用形制**，不该只有两个文化看得到——**本批 10 张卡的文化限定口径不一致，需复核**。
