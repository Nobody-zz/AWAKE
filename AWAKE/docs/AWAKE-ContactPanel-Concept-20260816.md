# AWAKE 通讯录 / 关系面板概念方案

_状态：概念梳理，未进入实现。参考物：AIInfluenceHistoryManager 面板、AliceMM NPCChatWindow / LetterComposePopup。五条关键修正已完成 50 轮对抗审查，修订版见 `Five-Corrections-Revised-20260816.md`。_

## 目标

把现在的“通讯录”升级成一个统一的关系中心：

- 左侧：联系人列表（头像、姓名、地点、附近/远方、关系状态、未读、收藏、搜索）。
- 中间：实时对话流，保留流式输出，可继续作为场景内/大地图相遇对话的承载面板。
- 右侧：人物卡片（头像、身份、所在地、关系快照、记忆摘要、近期事件）。
- 人物操作：对话、写信、交互（代码保底动作）、查看历史。
- 对话历史分层：原始记录保留一段时间并支持固定，定时压缩成 NPC 记忆，不把整段原文塞给 AI。

## 当前基础

已经具备：

- `AwakeMessengerOverlay` + `AwakeMessengerVM`：联系人列表 + 会话流 + 实时流式输出。
- `NpcDialogueOverlay` + `NpcDialogueService`：NPC 对话会话，已支持流式输出与关系命令。
- `AwakeMessengerHistory` + `WorldStateStore`：按联系人持久化 200 条原始对话。
- `NpcMemoryService` / `NpcMemoryConsolidator`：NPC 记忆分层、衰减、合并、承诺分离。
- `AwakeDialogueSessionCoordinator`：统一会话闸门，适合所有对话入口共用。

尚未具备：

- 人物头像、地点、关系状态等右侧人物卡片。
- 信件撰写 / 寄出 / 延迟送达 / 附件。
- 确定性交互动作（给钱、给物、交易、具体动作触发）。
- 原始对话保留期、固定、手动压缩策略。
- 场景 T/Y、遭遇面谈、主动对话、通讯录统一到同一个面板。

## 参考拆解

### AIInfluenceHistoryManager

适合借鉴：

- 左侧 NPC 列表 + 右侧多 Tab 详情区。
- Tab：对话历史、角色信息、知识与秘密、事件与任务、世界数据。
- 对话历史支持手动添加、删除、清空、撤销、快照。

不适合照搬：

- 直接编辑/覆盖 AI 数据文件、快照回滚。
- 依赖特定模组的存档路径。
- 作为“调试/管理工具”而非玩家向面板。

### AliceMM

适合借鉴：

- 左侧人物头像区 + 中央对话气泡 + 输入区。
- 头像、身份标签、动作按钮、百科入口。
- 写信面板：收件人、正文、附件、发送。
- 对话内流式输出与建议按钮。

不适合照搬：

- Alice 专属立绘、美术资源和对话模式。
- 把所有对话都做成“图片场景 + 立绘”的高成本视觉模式。

## 评估框架：玩家观感 / 开发者制作维护

后续所有设计取舍都必须同时过这两轴，不能只问“能不能做、快不快、省不省 token”。

### 玩家观感

- 打开面板后能否一眼明白：谁在哪、我上次说了什么、他现在什么状态、我还能做什么。
- 对话是否像“和一个人持续相处”，而不是像在翻数据库。
- 原文保留、压缩、固定、删除这些操作是否让玩家有掌控感，不会感到“我的记忆被偷偷删了”。
- 大地图相遇、场景对话、写信、交互是否都出现在合理的位置，而不是每换一个入口就换一套 UI 和学习成本。

### 开发者制作 / 维护难度

- 每加一个功能，是只改一个面板/一个服务，还是要同时维护两套 overlay、两套 VM、两套存储。
- 新 schema、命令、迁移是否一次性登记完整，避免以后靠反射或字符串猜。
- 历史、记忆、关系、交互、信件是否边界清晰，改一个不会炸另一个。
- 普通玩家功能与开发者调试工具是否分开，避免把调试复杂度泄漏给玩家。

### 双轴取舍原则

- 当技术更“省”但玩家更困惑时，优先玩家可理解。
- 当玩家想要“更炫”但会明显增加维护成本时，默认先做低维护版本，内容包再扩展。
- 当两套 UI 带来玩家入口混乱和开发者双倍维护时，合并是正收益；但若合并让场景操作变重，则保留轻量快捷入口。

## 关键逻辑修正

### 1. 原始对话历史和 NPC 记忆不是同一份数据

建议拆成三层：

- 原始记录：玩家可回看，保存在战役存储，滚动保留 200 条/30 游戏日，可固定重要对话。
- 压缩记忆：由 `NpcMemoryConsolidator` 生成摘要、事实、承诺，作为 AI 上下文。
- 关系/世界状态：信任、爱意、敌意、地点、最近事件，由世界状态存储提供。

不能让“压缩清理”直接删掉玩家要看的原始对话，也不能把 200 条原文全部塞进 AI 提示词。

### 2. “交互”应优先做代码保底按钮，而不是让 AI 自由执行

建议：

- 面板提供确定性动作：给金币、给物品、交易、请求、举行互动等。
- 每个动作对应固定命令 schema 和代码适配器，先校验数量/物品/距离/关系再结算。
- AI 可以建议动作，但最终执行仍走同一套代码命令，避免模型幻觉和重复扣款。

### 3. 地图相遇对话进入面板是可行的，但需要统一会话入口

建议：

- 场景 T/Y、遭遇面谈、主动对话、通讯录都调用同一个 `AwakeDialogueSessionCoordinator` 和同一个对话服务。
- 面板作为“当前会话容器”，从哪个入口进入只影响上下文，不影响 UI。
- 场景内仍可保留轻量弹出对话；面板更适合地图/通讯录场景。

## 分阶段方案

### Phase A：关系中心核心

- 新 `AwakeContactHubOverlay`，替代现有 Messenger 面板。
- 左联系人 / 中对话流 / 右人物卡片。
- 人物卡片显示：头像、身份、所在地、附近/远方、关系快照、最近事件。
- 保留现有对话服务和流式输出。
- 操作区先放“对话”“写信（占位）”“交互（占位）”。

玩家观感：一屏看到“这个人现在怎样、我之前和他聊过什么、还能做什么”，减少在通讯录和人物档案之间跳转。

开发维护：优先扩展现有 Messenger VM/Prefab，而不是再造第三套 overlay；人物卡片数据只读聚合，不复制存储。

### Phase B：历史管理

- 原始对话带 `day / location / pinned` 元数据。
- 默认保留 30 游戏日或 200 条，固定对话不压缩。
- 定时把可压缩原文交给 `NpcMemoryConsolidator`，面板只读展示摘要。
- 历史 Tab：原文列表、固定、压缩状态、可搜索。
- 高级管理（手动删除/导出/撤销）默认放在开发者菜单，避免普通玩家误操作。

玩家观感：普通玩家只看到“固定 / 最近记录 / 已压缩摘要”三个明确状态，不会因为后台压缩而觉得记忆丢失。

开发维护：固定用 `pinnedIds` 元数据而非改写每条原文；删除/撤销做成命令和审计，不做整文档快照。

### Phase C：写信

- 联系人卡片进入写信：收件人、正文、附件（金币/物品）、费用、送达延迟。
- 远距离联系人通过信件对话，信件有未读状态。
- 收到回信时在大地图/命令台给通知。

玩家观感：远方联系人有“真的在通信”的感觉，而不是直接弹出即时聊天；未读和送达状态要看得见。

开发维护：信件状态存 campaign storage，送达由 CampaignBehavior tick 计算，不在内存里计时。

### Phase D：交互动作

- 动作按钮：给金币、给物品、交易、赠送、请求、互动。
- 新增 `awake.action.*` 命令适配器，统一校验与结算。
- 交互记录写入事件账本和 NPC 记忆，AI 能引用但不能绕过代码结算。

玩家观感：玩家点击“给金币”后必须得到确定结果，不能出现“AI 说给了但钱包没少/物品没动”的错位。

开发维护：v1 收窄到可严格校验的动作，先做给金币和请求/承诺账本；物品、交易等原生能力未证明前不写第二套实现。

### Phase E：统一对话入口

- 场景 T/Y、遭遇面谈、主动对话、事件讨论、通讯录全部路由到同一会话模型。
- 需要保留独立快捷入口时，只保留轻量启动器，不再复制三套对话 UI。
- 观察运行日志与 token 消耗，决定最终保留哪些 UI 入口。

玩家观感：同一段关系在一个地方延续，不因为入口不同而“换一个聊天框、忘掉上一段话”。

开发维护：合并后只维护一个 session 模型、一个 hub VM、一套历史写入；但场景 T/Y 是否保留轻量覆盖层需按玩家手感实测，不强制一步合并。

## 可行性判断

- 面板 UI：可行，现有 Gauntlet 模式可直接扩展；不建议使用 AF/Alice 美术资产。
- 头像：优先使用游戏内 `ImageIdentifier` / 角色头像，后续再考虑生成头像。
- 历史与记忆：可行，但要新增 schema 与保留策略，不能直接复用 Messenger 的 200 条无策略存储。
- 写信：可行，工作量中等，需要信件存储、送达调度、附件校验。
- 交互动作：可行但风险最高，必须从“给金币/给物品”这类可严格校验的动作开始。
- 全入口统一：可行，但会触碰现有场景 T/Y 与遭遇逻辑，建议最后做。

## 开放问题

- 原始对话保留多久：7 / 30 / 90 游戏日，还是按条数？
- 固定对话上限多少？固定后是否永不删除？
- 历史管理器是普通玩家功能，还是默认隐藏的开发者功能？
- 第一批复用动作选哪些：金币、物品、交易、请求、互动？
- 信件是即时送达还是按距离延迟？是否收金币/声望成本？
- 场景 T/Y 最终是打开完整面板，还是保留现有轻量覆盖层？
- 头像用原版角色头像，还是后续接入生成头像？

## 不在本方案内

- 不做 AIInfluenceHistoryManager 的磁盘文件直接编辑与快照回滚。
- 不复制 AliceMM 的立绘、美术资源和专属对话模式。
- 不在本批实现自由文本 AI 动作执行；所有动作先走代码保底。
