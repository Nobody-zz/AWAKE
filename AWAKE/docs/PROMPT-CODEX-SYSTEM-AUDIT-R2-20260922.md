### 2.2 机制：存储层为什么**必然**回显

`AwakeFileStorageService.cs` 内嵌的 `JsonFileKeyValueStore`：

```csharp
// SetAsync :163-165 —— 先污染内存字典，再 Save()
Dictionary<string, string> current = Load();   // Load():211 —— 有缓存就直接返回同一实例
current[key] = value ?? string.Empty;          // ← 字典已经改了
Save();                                        // ← 这里抛，走 catch
// catch 只记日志、返回 Failure，**不回滚 values**
```
```csharp
// GetAsync :140 —— 读的就是那本已被污染的字典
Dictionary<string, string> current = Load();
return ... current.TryGetValue(key, out value) ...
```

⇒ **同一实例内，`Set` 失败之后的任何 `Get`，都看不到失败。**

### 2.3 ★ 你报告里没写的那一层

`WorldStateStore.cs` 的 `AppendWorldFactJournalAsync` 里，**有两处读回确认**：

```csharp
// :3713-3719  分片写入 —— 这是【刻意】为"写失败但结果未知"设计的重读确认
OperationResult<bool> stored = await store.SetAsync(chunk.Key, chunk.Json, ...);
if (!stored.IsSuccess || !stored.Value)
{
    OperationResult<string> confirmed = await store.GetAsync(chunk.Key, ...);   // ← 想确认"其实写进去了没有"
    if (!confirmed.IsSuccess || !Ordinal.Equals(confirmed.Value, chunk.Json))
        return new WorldApplyResult { Retryable = true, CommitUnknown = !confirmed.IsSuccess, ... };
    // 读回来相等 ⇒ 视为写成功，继续往下走
}
// :3720-3722  紧接着又读一次校验
```
```csharp
// :3737-3742  root 写入 ——【完全不看 SetAsync 的返回值】
OperationResult<bool> rootStored = await store.SetAsync(WorldFactJournalRootKey, rootJson, ...);
OperationResult<string> rootReadBack = await store.GetAsync(WorldFactJournalRootKey, ...);
if (rootReadBack.IsSuccess && Ordinal.Equals(rootReadBack.Value, rootJson))
    return new WorldApplyResult { Applied = true, Code = "awake.world_fact.persisted" };   // ← 报成功
if (!rootReadBack.IsSuccess)
    return ... Code = rootStored.Error?.Code ?? "awake.world_fact.root_commit_unknown";
    // ↑ rootStored 只在这里被用到，就为了取一个错误码字符串
```

**三点推论：**

**（a）`rootStored` 是个摆设。** 它被赋值，但**不参与任何判定**，只在失败分支里贡献一个错误码。

**（b）`:3714-3719` 那段不是"多余的检查"，是**有意图**的检查** —— 它想表达
「Set 报了失败，但**失败不等于没写进去**，所以重读一次确认」；`CommitUnknown` 这个字段的存在就是证据。
⇒ 但它**建在会骗人的那层上** ⇒ 这个确认**恒为真** ⇒ 按本仓判据：**恒 True＝没测**。
**这道冗余防线不是"没写"，是"写了但已经失效"——比没写更难发现。**

**（c）所以"加一个 `if (!rootStored.IsSuccess) return` 就好了"是错的修法。**
那样会在「写失败但**其实写成功了**」的场景下**误报失败**（正是 `CommitUnknown` 想避免的假阴性），
而真正该修的东西一点没动。**修法必须落在存储层或读回路径上**，方向有三（**具体选哪条由你判**）：

- `SetAsync` 失败时把 `values` **回滚**到 `Save()` 之前的状态（需要先克隆）；
- 给 `IKeyValueStore` 补一个**绕过缓存、直读磁盘**的读口，读回确认走它；
- 把 `SetAsync` 的失败语义**拆成三态**：确定未生效 ／ 确定已生效 ／ **结果未知**。
  ⚠️ 现在只有"失败"一态（`Failure<bool>`）。而 `Save()`（`:233-249`）里
  `Directory.CreateDirectory` → `File.WriteAllText(temp)` → `File.Replace(temp, path, null)`
  这几步的失败含义**互不相同**：目录建不出来**必然未生效**；替换那一步失败则**结果需要读盘确认**
  （且即便失败，盘上还会留一个 `.tmp` 残留 —— 那是"结果未知"的一个可观察痕迹）。
  ⇒ 你首轮建议里那句「**需区分'替换前失败'和'替换后结果未知'**」——**那是这轮最值钱的一句，请把它展开成设计。**

→ **Q9**：三条修法里你选哪条、为什么；被否掉的两条，各自的**具体失效场景**是什么？
