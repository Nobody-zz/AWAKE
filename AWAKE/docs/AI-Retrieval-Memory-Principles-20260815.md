# 斯拉涅斯之拥 · 检索/记忆/对话原理与实现原则

> 日期：2026-08-15
> 背景：AF 的关键词检索思路合理，但实现是“近 1GB 暴力读取文件 + 本地 ONNX 迷你 NLP”，不可接受。本文定义斯拥自己的读取依赖、记忆和 AI 对话原理。
> 定位补充（2026-08-15）：斯拥是包容、强兼容的 AI 世界运行架构；情色/成人内容突出但可选，显式内容只随插件/世界书/内容包启用后进入检索与对话，核心默认纯净可玩。
> 项目两分（2026-08-15）：本文定义的检索/记忆/对话原理属于运行时层，对任何内容包通用；斯拉涅斯/齁改成人设定属于内容层，以世界书与事件 JSON 形式加载。

## 一、核心原理

**1. 索引先行，绝不暴力扫描**

- 知识库/世界书只在加载时解析一次，构建倒排索引；查询时走索引，不再对全部文档逐个做 `IndexOf` 子串扫描。
- 中文检索用“关键词表 + 字符 n-gram 索引”组合；不能用“整段文本 contains 查询”。
- 查询结果按 query hash + 知识库 fingerprint 做 LRU 缓存，同一场对话不重复扫。

**2. 分层召回，每层有预算和降级**

```
玩家输入/场景词
  → 规则层：精确关键词/身份/文化/地点条件命中（快、确定性；先过 ContentPolicy 门控，未启用内容层不进入查询）
  → 语义层：Marcus RAG（慢、但语义泛化）
  → 本地回退：倒排索引关键词命中
  → 无命中：不注入，用女神本知/角色本知作答
```

- 规则层永远先于 RAG，因为规则是世界观权威（四档世界书、神律、人物条件）。
- RAG 只做“泛化召回”，不能覆盖规则层；Companion 不可用时自动回退倒排索引。
- 每层返回都按字节预算截断，注入上限固定，避免上下文膨胀。

**3. 加载一次、指纹驱动**

- 语料文件只在模组初始化时读一次；文件哈希作为 fingerprint，RAG 按 fingerprint 判断是否需要重新 ingest。
- 游戏内不再 `File.ReadAllBytes` 读世界书；后续内容更新走“版本文件 + 重新构建索引”的离线流程。

**4. 记忆是结构化事件，不是原文堆叠**

- NPC 记忆 = 事件事实（`heroId/day/type/facts/weight/source`）+ 会话摘要 + 跨会话总览。
- 召回按 `weight → recency → relevance` 排序，永远取 top-k，不把整个记忆文档塞进提示词。
- 对话中的当前文本可以提取轻量关键词，用来提升相关记忆的权重，但绝不暴力读全部记忆。

**5. 对话上下文是有预算的组装**

- 每一轮提示词 = 角色状态 + 关系/身体/发情 + 记忆 top-k + 知识命中 + 当前场景 + 近期历史。
- 所有输入走 `NpcDialoguePromptPipeline` 的统一预算和截断顺序，先剪历史，再剪知识，最后才剪角色状态。
- 不在 UI/campaign tick 中做网络/文件/数据库阻塞；检索在后台完成，结果通过事件队列回到主线程。

**6. 观测优先**

- 每次检索记录 `mode=rule/rag/local/none`、命中数、耗时、注入字节、降级原因。
- 命中率过低时能定位是规则漏、RAG 未就绪还是语料缺词，而不是靠体感猜。

## 1.1 记忆分级与遗忘（按玩家/群友意见）

目标：模拟人的记忆——重大事件仔细记，日常小事随时间退化成“和 XX 一起干了 XX”，最后只留印象；诺言、承诺、誓言、婚姻这类不能忘。

**重要性分级**

| 等级 | 内容 | 保留策略 |
| --- | --- | --- |
| S | 诺言/承诺/誓言、婚约、生死、背叛、重大抉择 | 永久/极长保留，写入提示词常驻区，不参与普通遗忘 |
| A | 战争、旅途、关系里程碑、明显情绪转折 | 详细保留关键对话，按季度/年度合并 |
| B | 可注意的日常（一起去过哪、聊过什么） | 数周后降级为“和 XX 一起干了 XX” |
| C | 琐碎寒暄、动作流水 | 短期内删除，只留是否认识的痕迹 |

**关键规则**

1. 重大事件只保存“你说了什么 / 对方说了什么”，动作、走位、演出细节直接不要；压缩结果是稀疏的，不是流水账。
2. 诺言/承诺/誓言是独立记忆类型：带 `promise` 标记、兑现状态、约定内容、对方 ID；永不衰减，对话中提及相关话题时优先注入。
3. 婚姻、家族、主从这类“关系事实”同时写入关系状态，不只写记忆；记忆可以模糊，关系状态不能丢。
4. 权重 = 基础重要性 + 新鲜度衰减 + 当前话题相关性；S 级不受新鲜度衰减影响。
5. 日常降级由游戏时间驱动：B 级过了若干天重写为摘要行，C 级过了短窗口删除。
6. 汇总提示词要求“只留核心 + 关键对话”，并显式禁止逐句复述动作流水。

现有 `NpcMemoryService` 的 `weight/day/type/facts/summary` 正好可以扩展：`type` 增加 `promise/oath`，`weight` 按重要性表初始化，新增 `tier/decayDay/quotes` 字段，召回时按“常驻承诺 > 高权重 > 新鲜 > 相关”排序。

### 1.1.1 性格、恩怨与记忆点（按玩家/群友意见补充）

**性格影响分类**

- 小气 NPC：财物或尊严受损会被定性为恩怨，长期保留；事件本体记入“谁、何时、何地、损失价值”，并沉淀一条带情绪的评价短句。
- 慷慨 NPC：同类事件也留下负面评价短句，但定性更轻，是否升为永久恩怨由后续关系事件决定。
- 日常事件按性格决定是否上升为恩怨：小气者更容易把损失记成怨恨，慷慨者更容易大事化小。

**记忆点（memoryPoint）**

- 每条事件可沉淀一句“记忆点”：高度浓缩、带情绪与评价的短句，代表 NPC 对这件事最深的印象，而不是流水账。
- 记忆点是衰减后的最终形态，永久恩怨只保留记忆点 + 稳定身份，不保留动作流水。

**日常对话衰减时间线**

| 时间 | 形态 |
| --- | --- |
| 当日 | 完整：时间、地点、人物、事件、对话核心 |
| 7 日 | 简化：时间、NPC 与玩家在 <地点> <核心事件> |
| 15 日 | 只留记忆点；时间/地点若不计 token 可保留 |
| 30 日 | 一句式：和玩家一起做过 <核心事> |

**同类事件合并**

- 两个月的旧简化事件与新的同类当日事件，在 30 日时合并：消去具体时间，保留地点列表，如“和玩家分别在 <地点A>、<地点B> 一起做过 <核心事>”。
- 合并按 `category + 对方 + 核心词` 聚类，不跨类别乱并。

**重大事件阈值（不简化）**

- 承诺/誓言：NPC 亲口或被迫答应的事，记录“时间、地点”+ 承诺内容。
- 财产损失/交易：超过身份阈值 —— 平民 100 第纳尔、要人 10000 第纳尔、领主 100000 第纳尔。
- 失去定居点、因玩家失去亲人、建立关系、身份变更、玩家造成的肉体/精神伤害。
- 以上永远保留完整核心，不参与 7/15/30 简化。

设计参考：太吾绘卷“见闻/秘闻”、鬼谷八荒“人物经历”都强调全量记录但保持简略。斯拥采用“全量入档 + 分级衰减 + 记忆点沉淀”，吸收这个思路，但字段、判定和文案全部自建。

### 1.1.2 参考机制提炼（太吾绘卷 / 鬼谷八荒）

> 以下按“原游戏机制 → 对斯拥有借鉴意义 → 斯拥落点（不照搬）”三层记录。字段、数值、命名与判定全部自建，只借用“让 NPC 记得住、会遗忘、会传播、有独立人生”的设计意图。

#### 太吾绘卷：见闻与秘闻分层

**见闻（日常信息流）**

- 见闻按地方、门派、志向等类型归档，可互相交换；NPC 对异乡见闻、故乡见闻和自身不擅长领域的见闻更感兴趣。
- 闲聊见闻增加好感、降低戒心，有等级差；不同人物对同一见闻的反应分为显著、普通、无效三档，无效则零结算。
- 见闻闲谈每月对同一人限一次，消耗精力；打探对方持有的见闻需要好感到“喜爱”，只能打探地方、门派、志向见闻。

对斯拥的启示：

- 日常记忆 B/C 级就是“见闻”：按文化、地点、事件类别做兴趣过滤；NPC 对异乡见闻和故乡见闻更感兴趣。
- 闲聊有冷却、有结算差异：同一件日常事对商人、士兵、贵族、修士的“值得聊程度”不同；聊对方不感兴趣的话题不产生好感收益，甚至可以降好感。
- 打探需要关系门槛：从“随口聊”到“愿意讲私事”必须由好感/信任解锁，不能所有内容对所有关系开放。

**秘闻（高价值信息）**

- 秘闻由人物行为或遭遇生成，邻近地格人物有机会得知；人物可自行传播，也可被玩家使用“使用秘闻”互动转述。
- 秘闻有性质（正面/普通/负面）、关联人物、等级、持续时间、传播消耗、可传播次数、传播倾向、传播来源。
- 传播倾向：人物更倾向传播自身或亲友的正面秘闻、仇敌的负面秘闻；传播会消耗威望，名誉过低会提高传播成本。
- 保密：被要求保密或传播倾向最低时进入保密状态，保密者不再主动传播，也不计入公开人数。
- 公开：知晓人数达到 10 人后秘闻公开，可能影响关联人物及其亲友/仇敌的名誉、心情，以及与传播来源的好感、戒心、关系；触犯法规还可能被门派悬赏处罚。
- “谁告诉我的”是信息的一部分，传播来源本身会成为公开后的追责对象。
- 人物经历同样分级：NPC 遭遇过的事按“某人、某地、某物”模板记录，部分特殊经历需要足够好感才能查看。
- 处世立场（刚正/仁善/中庸/叛逆/唯我）决定相合/相冲，影响互动结果和可用选项；赞颂/羞辱等互动对五类立场的收益方向甚至相反。

对斯拥的启示：

- 高价值事件（羞辱、背叛、罪证、丑闻、恩情）进入 S/A 级“秘闻”：记录 `knownBy` 传播链与“谁告诉了我”，传播需要信任/关系门槛。
- 秘闻必须有传播倾向模型：立场、性格、关系决定 NPC 是四处宣扬、默默记仇还是守口如瓶；玩家要求保密会成为真实约束。
- 公开阈值与公开后果：传播到一定人数后成为“公开传闻”，反过来改变关联人物名誉、关系与阵营反应；玩家把秘闻转告给谁，谁就可能来寻仇、灭口或求保密。
- 立场系统对应斯拥的世界观立场：不是现代善恶，而是神律、权力、欲望与习俗决定的处世方式；对话选项和 NPC 反应按立场给不同结果。
- 经历模板化：所有事件落库时先映射到稳定字段（谁、何时、何地、对谁、何事、代价），避免模型自由发挥成不可检索的长文。

#### 鬼谷八荒：关系、双好感与人生轨迹

**关系分类**

- 关系分亲族与人际两大类；同一人不会同时出现在同一角色的两个栏目里。
- 血缘关系永恒：不受好感影响，好感降到底也不会解除；非血缘关系（义亲、师徒、夫妻、道侣）相对稳定，但一方好感跌破 0 可决裂，且解除后不可复原。
- 好友是双向的：双方互相好感 ≥60 才成立，任何一方跌破即解除；仇人是单向的：一方对另一方好感 ≤-60 即成立，另一方不必对称。
- NPC 有概率攻击仇人，仇人的好友/亲人也可能间接攻击；厌恶（-60~0）不会主动攻击但会嘲讽，认识（0~60）只有基础交互。
- 陌生人是单向的，但“过目不忘”：一旦结识就不再退回陌生人；单恋/被单恋状态说明“我对 TA 的好感”与“TA 对我的好感”可以严重不对等。
- 好感每年一月结算衰减：2 星以下快速衰减、2~3.5 星正常、3.5 星以上缓慢；性格修正包括义气好友不衰减、睚眦仇恨反而增加、孤僻好坏都快速衰减、多情异性好感略增。

对斯拥的启示：

- 婚约、家族、主从、结义是“关系事实”，写入关系状态且永不因记忆压缩丢失；这正好对应斯拥的承诺账本与关系状态，不依赖记忆衰减。
- 仇恨与善意可以单向、不对等：玩家讨好对象可能仍旧恨玩家；NPC 的好友/亲族会替它出头，是“严重后果呈现连锁代价”的结构化来源。
- 敌对关系用单向 `hostility` 与反向视图建模，不要默认对称；NPC 是否主动攻击由仇恨值、实力差、性格共同决定。
- 淡忘不是一刀切：按关系强度和性格给不同衰减率；睚眦必报者记仇更久，重义者不淡忘好友，孤僻者什么都会快速淡忘。

**双好感与交互门槛**

- 好感分“NPC 对玩家”和“玩家对 NPC”两套：玩家界面默认只显示前者，后者要解锁好友关系才可见。
- 赠送主要增加“NPC 对玩家”的好感，不增加玩家对 NPC 的好感；切磋、双修、交谈、论道、结义、结缘才是双方同步增加的方式。
- 互动选择受双方实力、正魔道值、交情综合判定：实力碾压时 NPC 会回避冲突；交情不足时大量选项不可用。
- 关系是部分互动的前置判定，且优先于好感：比如双修先判关系是否允许，再判好感/性格。

对斯拥的启示：

- 斯拥同样需要双通道关系：`npc→player` 参与 NPC 行为与对话，`player→npc` 可以长期隐藏，只在玩家主动查看或关系解锁后可见；这与鬼谷八荒思路一致但命名与存储自建。
- 对话/身体互动先判关系与场合门槛，再判好感与身体状态：关系不允许时直接给角色内拒绝，不进入数值判定。
- 好感推进要区分“单方施予”与“共同经历”：财物、地位施压更多改变对方对你的态度；共同战斗、共同经历、仪式互动才同时改变玩家对 NPC 的态度。
- NPC 会评估实力与风险：打不过就回避、谈条件或记仇，不无脑攻击；玩家强横时 NPC 选择更谨慎的报复方式（流言、暗算、借刀杀人）。

**性格驱动行为与独立人生**

- 性格不只影响好感增减，还直接驱动 NPC 行为逻辑：天伦+义气+仁善者交友广泛、维护亲族与宗门；利己+孤僻+睚眦者到处惹事结仇。
- 传承性格喜欢收徒/拜师，忠贞性格会主动寻找配偶，情种性格喜欢结道侣，护短/义气性格会帮后辈或朋友报仇，利己性格优先做对自己有利的事。
- NPC 有完整关系网与人生轨迹：朋友、亲族、婚姻、仇怨独立于玩家进度；玩家不在场时世界继续推进。

对斯拥的启示：

- 斯拥的性格维度应落在世界观口径上（虔诚、淫荡、贪婪、睚眦、重义、护短、怯懦、野心等），不借用现代心理学标签；性格驱动“主动发起什么、如何回应、遗忘快慢、传播什么秘闻”。
- P1 先做“玩家在场时 NPC 的独立动机”，P2 再做“玩家不在场时世界离线推进”；第一批量不承诺全图模拟。
- 每个 NPC 的主动行为（找人喝酒、传播流言、结怨、追求、报复）应由性格 + 关系 + 场合共同决定，而不是固定脚本。

## 1.2 并发与主线程回传

- 检索在后台 Task 执行；结果通过主线程派发队列回传，由调用方按“回合代数”消费，不直接跨线程改 VM/提示词。
- 队列所有权：当前复用 `SlaaneshUiDispatcher`（自建、可测）；若后续 Marcus 提供 `GameThreadDispatcher` 等价公开 API，则复用框架能力，不维护第二套。当前 SDK 参考中未发现该类型。
- 背压：单会话最多一个飞行中检索；新输入到达时把旧结果标记为陈旧（generation 递增），旧结果到达后丢弃，不替换新回合上下文。
- 取消：检索任务绑定回合 `CancellationToken`；用户关闭对话或开启新回合时取消，取消不作为普通失败吞掉。
- 组装归属：后台只负责“检索”，提示词组装仍由主线程的 `BuildPromptInputAsync` 完成；后台不写 VM、不打开 UI。

## 1.3 规则/RAG 组合与截断保护

- 两者都命中：规则块在前、RAG 块在后，按稳定 ID 去重后都注入。
- 规则与 RAG 正文冲突：规则优先，丢弃冲突 RAG 结果并记 `rule_rag_conflict` 日志。
- 截断保护：规则命中单独预算，不参与知识层截断；知识层（含 RAG）被截掉也不允许截掉规则命中。
- 顺序：承诺/关系事实（常驻）→ 规则命中 → 记忆 top-k → RAG 补充 → 场景 → 历史。

## 1.4 中文检索细节与数值默认

- Marcus RagEngine 使用 SQLite FTS5 unicode61 + 按非字母数字切词，未配置 embedding 时对中文接近单个长 token，中文召回很弱；因此本地 n-gram 回退是**必须项**，不是可选项。
- 未配置 embedding 时，Marcus RAG 本质是 token 匹配，与本地关键词层高度重叠；文档不把它称为“语义层”，而称为“框架检索层”。语义能力取决于框架是否配置 embedding。
- 中文索引：关键词原样 + CJK 2-gram；查询端做同样的 n-gram 展开，保证索引与查询对称。
- 融合加权：关键词命中权重 3、标题 2、正文 1；n-gram 命中只作为“候选召回”，不参与最终排序加分，避免长文本噪音；结果仍按关键词命中优先还原原文。
- term 表规模控制：每个 term posting 上限（正文 128、关键词/标题 512）；正文 2-gram 单文档最多 64 条。
- 集中默认值（放 `AiTaskConstants`）：规则预算 2048B、RAG/知识预算 3072B、记忆 2500B、历史 4096B、承诺块 1024B、top-k=12、LRU local=128 / rag=128、每层最大命中 5。

## 1.5 索引重载契约

- fingerprint 变化后：后台构建新索引（双缓冲），构建完成后一次性交换引用；进行中的查询继续用旧快照，不受影响。
- 触发点：模块初始化、战役开始、显式开发者命令；不允许“读档后静默失效”。
- 同一次会话内指纹不变则不重建；RAG 按 `ExpectedCorpusFingerprint` 校验，不一致时走本地回退并记录 `rag_fingerprint_mismatch`。

## 1.6 记忆抽取、权重与冲突

- facts 来源：对话结构化输出（LLM）为第一来源，规则事件（关系 delta、俘虏、主动邀约）为代码侧事实；两者都写入时以事件事实为准，避免模型自述覆盖系统事实。
- weight 初始化和衰减：由 `MemoryImportanceClassifier` 定基础权重，衰减按 1.1 的分级规则；relevance 计算 = 关键词重叠分 + RAG 分数（可选），不靠直觉。
- 记忆与世界书冲突：世界书/规则赢，记忆块标记为“印象”，注入顺序在规则之后。
- 身份：所有 heroId 用稳定 StringId，不用显示名、不用 `CharacterObject_*` 临时索引。

## 1.7 原版关系/家族设定的复用边界与成本取舍

结论：**原版关系是权威状态，斯拥只存“原版表达不了的叙事增量”**。太吾绘卷、鬼谷八荒式的关系/双好感/记忆点可以改进骑砍原版，但必须在玩家 token 消耗与游戏性能约束下取舍，不能照搬成一套完整替代系统。

内容层门控：核心默认只检索 clean/世界观层内容；显式内容包独立索引，未启用时不进入查询、提示词与事件池。门控在索引与查询边界执行，检索器不做成人内容自动判定，避免“漏检到未启用内容”或“越权外发”。

**A. 状态权威分工**

| 内容 | 权威来源 | 斯拥是否另存 |
| --- | --- | --- |
| 英雄间好感/仇视、家族、婚姻、血缘、师徒、主从 | 原版 `Hero` 关系图 / RelationModel | 不另存，读原版 |
| 阵营、家族外交（战争/和平/结盟） | 原版 `Kingdom` / `Clan` 关系 | 不另存，需要时读快照 |
| 人格特质（荣誉、慈悲、勇武、慷慨、算计等） | 原版 traits | 不另存，只做世界观标签映射 |
| 玩家/NPC 私密三轴（信任/爱意/敌意）、身体/发情、愿力 | 斯拥 `relationships/body_state` | 是，mod 专属状态 |
| 承诺/誓言、事件账本、记忆点、秘闻传播链 | 斯拥存储 | 是，原版没有的叙事事实 |

- 原版表达不了“为什么”：数值变化的原因、承诺内容、被谁羞辱、谁传的流言由斯拥记，且只记短事实，不镜像关系数值。
- 禁止把原版关系全量复制进 Marcus 存储再回写；原版存档是唯一权威，斯拥存储只是叙事历史镜像。

**B. token 取舍**

- 对话提示词只注入当前 NPC 的紧凑关系快照，加上最多 3~5 个强关联英雄（配偶、直系亲属、领主、死敌）的标签，绝不注入整棵家族树、全部同僚或整个关系账本。
- 关系用档位标签 + 正负号表达（敌视/陌生/相识/朋友/亲密），不用原版精确数值；精确值只进开发者工具。
- 硬预算：关系快照 ≤1024B；家族/阵营上下文 ≤512B；附近关系列表 ≤512B；单条记忆 ≤200B；top-k=8；总 prompt 32KB。超出按先历史、再知识、最后角色状态的顺序裁剪，关系快照单独预算不被裁剪。
- 关系数值变化不自动写记忆：普通 +N 好感、日常贸易、普通战斗只由原版结算；只有叙事转折（结仇、背约、羞辱、献身、婚约、家族变故）才写斯拥事件账本/记忆点。
- 原版可推导的（配偶是谁、属于哪个家族、是否敌对阵营）由代码确定性格式化，不让 LLM 去猜或去总结。

**C. 性能取舍**

- 原版关系只在对话打开、事件打开或显式查看时读取，不在 campaign/mission tick 里扫描全图英雄；批量取 `Hero.RelationWith` / 家族图快照，读一次缓存到本轮对话结束。
- 附近关系/候选人用场景内 `CurrentSettlement`、`MainParty` 成员这类局部集合，不做 `AliveHeroes` 全量遍历；遍历也必须有上限（如 5 人）。
- Marcus 存储读取按对话会话批量合并，不为每个字段单独 await；存储不可用时直接降级为空，不重试轰炸。
- 事件/记忆写入失败不影响原版关系与游戏流程；原版关系是即时结算，斯拥记忆是异步 best-effort。

**D. 冲突与改进边界**

- 原版关系赢：原版关系决定对话可用性、阵营行为和游戏内门槛；斯拥记忆只解释“为什么”，不能反向覆盖原版数值。记忆与原版冲突时标记为印象/流言。
- 斯拥私密三轴是原版之上的附加层：它们影响语气、态度和剧情倾向，但不能绕过原版关系门槛（例如家族/阵营硬约束）。
- 可改进点：家族/血缘作为永久关系事实注入 AI（原版本来就有，斯拥只是按需给标签）；人格特质映射成世界观行为驱动；事件账本补“原版只有数值没有原因”的缺口；双通道关系（NPC 对玩家 / 玩家对 NPC）作为斯拥轴扩展，不做完整仿鬼谷系统；秘闻传播只覆盖 S/A 级事件并设数量上限，不扩成全图流言网。

## 二、现状差距

| 环节 | 现状 | 问题 |
| --- | --- | --- |
| 语料加载 | `KnowledgeService.Initialize` 读一次文件 | 只读一次，但索引是 `List<LocalEntry>` 全量遍历 |
| 本地检索 | `LocalKeywordIndex.Search` 逐文档扫描 | 每轮查询 O(文档数 × 文本长度) 子串匹配 |
| 中文分词 | 按空白/标点切词 + `IndexOf` | 中文无空格，切词等于整句，命中率差 |
| 记忆召回 | `NpcMemorySelector` 每次全量排序取 top-k | 文档大时每轮全量排序，无索引 |
| RAG | Marcus `Rag.SearchAsync`（FTS5 unicode61） | 未配置 embedding 时对中文召回弱，可能退化为长 token 匹配；必须保留本地 n-gram 回退，且不把它当“语义层” |
| 预算 | `NpcDialoguePromptPipeline` | 已有统一截断，保留 |

## 三、落地方案

### P0 倒排索引（替换 `LocalKeywordIndex`）

- 构建：每个文档把 `keywords/title/documentId/content` 归一化后拆成 term；中文 term 用关键词原样 + 2-gram/3-gram 兜底。
- 存储：`term → List<Posting(docId, fieldWeight)>`；同时保留 `docId → 原始内容` 用于结果组装。
- 查询：query 拆 term → 合并 posting → 按 `keyword=3 / title=2 / content=1` 加权 → 上限截断 → 去重。
- 缓存：`fingerprint + queryHash → hits`，local/rag 分开，LRU 各 128；场景词变化才失效场景段。
- 并发：检索在后台 Task 执行，主线程派发队列回传，回合 generation 丢弃陈旧结果，取消绑定回合 token。
- 重载：fingerprint 变化走双缓冲重建，查询持有旧快照；触发点为模块初始化/战役开始/显式命令。
- 验收：查询耗时与语料大小解耦（近似 O(term 命中数)），SdkSmoke 断言不再全量 `IndexOf`、查询路径无文件 IO、规则命中单独预算不被知识层截断、缓存命中率与规则命中率有统计断言。

### P1 世界书规则索引

- 把四档世界书规则（英雄/文化/地点/身份/角色条件）建成独立索引，支持 `When` 条件预筛。
- 对话/事件触发前先用规则索引定位候选，再决定是否走 RAG。
- 规则正文不进 RAG 向量库；RAG 只放补充知识，避免“规则被向量改写”。
- 规则/RAG 冲突处理：规则优先、冲突丢弃 RAG 并记日志；两者都命中按规则→RAG 顺序注入并去重。

### P1 记忆召回索引

- `WorldStateStore` 记忆文档增加轻量检索字段：`type/weight/day/keywords`。
- 召回 = 按英雄取候选（不是全图英雄）→ weight/day 排序 → 当前轮关键词提升相关条目 → 字节预算截断。
- 会话摘要和总览作为单独字段，不在每轮重建。
- 按 1.1 分级：S 级承诺/誓言常驻；A/B 级按新鲜度衰减；C 级到期清理；婚姻等关系事实走关系状态。

### P2 可观测性

- 新增 `retrieval_stats` 日志：`mode hits ms budget degraded`。
- 开发者检查中展示：语料大小、索引 term 数、缓存命中率、RAG 状态、最近降级原因。
- 规则命中率、缓存命中率、冲突计数进入开发者面板。

## 四、反模式清单（禁止）

1. 每轮查询全量扫描语料。
2. 对正文做 `string.Contains` 子串匹配。
3. 游戏内反复 `File.ReadAllBytes` 读世界书。
4. 本地 ONNX / 手写 tokenizer / embedding / rerank。
5. 把完整记忆、完整历史、完整世界书塞进提示词。
6. 在 UI/campaign tick 中同步等 AI/RAG 返回。
7. 绕过指纹直接重新 ingest 同一语料。

## 五、里程碑

1. P0：倒排索引 + 加载一次 + local/rag 缓存分离 + 后台检索/主线程回传 + 双缓冲重载 + SdkSmoke 性能与规则保护断言。
2. P1：世界书规则索引（含规则/RAG 冲突处理）+ 记忆召回索引。
3. P2：检索统计与开发者诊断（规则命中率、缓存命中率、冲突计数）。

## 六、进一步优化空间（按收益排序）

**1. 查询路由与实体提及（收益最高）**

- 检索前先做轻量路由：神律/人物/地点/身体/记忆/命令/闲聊，不同意图走不同召回权重。
- 用稳定的实体表（英雄 ID、文化、王国、定居点、身体区、事件名、放纵月等）从输入中提取提及，再按实体生成多条带权查询，而不是把整句扔给检索器。
- 好处：命中率、可解释性、RAG 调用量一起改善。

**2. 索引层升级**

- 关键词匹配用 Aho-Corasick 自动机：一次扫描输入即可命中所有关键词，复杂度与关键词数量解耦。
- 评分升级为 BM25：词频、字段权重、IDF 一起算，替代简单“命中 +3/+2/+1”。
- 中文检索保留“预置关键词 + 2/3-gram 兜底”，但把 posting 列表限制成 `docId + 字段掩码 + 计数`，不做位置全文索引。
- 规则条件（英雄/文化/王国/定居点/角色/性别）预建 O(1) 查找表，避免每轮遍历规则集。

**3. 记忆双温层 + 话题标签 + 合并**

- 热记忆：最近/高权重事件，随会话开始预取；冷记忆：已合并的摘要块，只有相关才召回。
- 写入事实时同步提取轻量话题标签，召回时按当前轮标签匹配，而不是全文检索。
- 日结 → 周总览 → 季度/长期总览逐级合并，每个英雄只保留有界数量的块。
- 多英雄共同事件写共享键，让对话能引用“你们一起经历过的事”。

**4. 对话上下文预算自适应**

- 预算按意图分配：命令/规则类意图多给规则层，闲聊/回忆类意图多给记忆与历史。
- 如果 RAG 无命中，把它的预算让给记忆或角色状态，而不是留空。
- 会话级缓存：关系/身体/发情/记忆在一天内不重复拉取，命令结算或换日才失效。

**5. 批量状态读取**

- 每轮把关系、身体、发情、记忆、玩家快照合并成一次批量读取，减少多次 `await store.Get*Async` 的串行往返。

**6. 规则与 RAG 冲突处理**

- 规则命中优先；RAG 结果标记为“补充”，与规则按稳定 ID 去重。
- 检测到 RAG 与规则语义冲突时丢弃 RAG 结果并记日志，不让模型被矛盾上下文带偏。

**7. 诊断与基准**

- SdkSmoke 用合成语料（1000 / 10000 文档）断言查询时间近似亚线性。
- 检索日志带 correlation ID、mode、命中数、耗时、预算、缓存命中、降级原因。
- 开发者面板展示：语料大小、索引 term 数、规则覆盖率、RAG 状态、缓存命中率、最近冲突。

**8. 按需检索与会话级免检（二轮复核新增）**

- 不是每轮对话都要检索知识。先按意图判定：命令/规则类、明确提问、实体提及才触发检索；闲聊、回应、情绪类沿用上一轮上下文。
- 会话内维护“已检实体/已注入规则”集合，同一话题不重复检索；场景词变化或换日才失效。
- 这一步比任何索引算法都能省更多耗时，因为直接砍掉了大量无效查询。

**9. 场景/角色知识预载**

- 进入定居点、开始与某 NPC 深谈、触发事件前，预载该场景/角色相关的规则子集与记忆热区。
- 对话开始时一次准备好，后续轮次不再逐轮全量检索；这符合“加载一次、索引驱动”的原则。

**10. 意图去噪与实体别名（借鉴 AF 思路，自建实现）**

- 输入先做轻量去噪：低信号短语（你好/请问/谢谢等）、前导语剥离、语气词收尾、canonical 归一化、近重复意图去重。
- 实体提及用稳定 ID + 别名表匹配（英雄名、称号、地名、文化、王国），不做模糊全文扫描。

**11. 并行化状态读取**

- 当前 `BuildPromptInputAsync` 对关系/身体/发情/记忆/知识是多次串行 `await`；Marcus `IKeyValueStore` 没有批量 Get，所以改为有界 `Task.WhenAll` 并行读取。
- 并行数固定（如最多 6），避免 UI 线程等待和内存峰值。

## 优化原则

- 每一项优化先写“解决什么问题、规模多大才需要、复杂度多少”，再决定是否做。
- 语料只有几十 KB 时不做 BM25/自动机，先保证正确；语料进入 MB 级或命中率低时再逐级升级。
- 所有优化必须保留本地回退和降级，不允许引入新的硬依赖（本地模型、外部服务、大文件常驻内存）。

## 七、二轮复核结论

- P0 范围不变：倒排索引 + 加载一次 + 查询缓存 + 性能断言。
- 实体路由、意图去噪、按需检索属于 P1 的前置优化，收益高于 BM25，优先于索引算法升级。
- Marcus 没有批量读取接口，状态读取只能做有界并行，不能当“框架已支持”来写。
- 优化顺序建议：会话级免检 → 实体提及路由 → 倒排索引 → 记忆标签 → BM25/自动机；不要一上来就堆算法。
