## 〇、结论

**分词不用自己写。** 用官方 `Microsoft.ML.Tokenizers` 的 `BertTokenizer`，配一份从 `tokenizer.json` 离线导出的 `vocab.txt` 就够。16 条真实中文问句与模型原始分词**逐位一致**；「分词 → ONNX → 512 维向量」这条链已在开发机**端到端跑通**。

**要随包带的 native 只有 3 个 DLL，合计约 10.5 MiB。**

⚠️ 一处必须知道的行为：**符号类字符会被静默丢掉**（不报错、不产生 `[UNK]`）。汉字／标点／数字／中英混排**不受影响**。见 §二.4。

## 二、分词实现

### 2.1 为什么 AF 要自己写，我们不用

**根因**：官方 `Microsoft.ML.Tokenizers`（我们已装 **2.0.0**）的 `BertTokenizer.Create` / `WordPieceTokenizer.Create` **只接受 `vocabFilePath`（`vocab.txt`）**，没有任何公开方法能读一体化的 `tokenizer.json`。

⇒ 这就是 AF 自写 `BertNormalizer` 的原因（AF 的 DLL 字符串表里分词相关串只有 5 条：`BertNormalizer`、`[CLS]`、`[PAD]`、`[SEP]`、`[UNK]`，**bin 里没有任何分词库**）。

**绕开办法**：`tokenizer.json` 的 `model.vocab` 里本来就有完整词表（**21,128 条，id 连续 0..21127**），**离线导出成 `vocab.txt`** 即可。导出是一次性的，产物随包走。

### 2.2 三步

**第 1 步 · 离线导出（开发机跑一次）**
脚本 `tools/_af_vocab_export_20260916.py` ⇒ 产出 `vocab.txt`（21,128 行，一行一个 token，按 id 排序）。

**第 2 步 · 装配分词器**
```csharp
var options = new BertOptions
{
    LowerCaseBeforeTokenization = false,
    ApplyBasicTokenization      = true,
    IndividuallyTokenizeCjk     = true,
    ClassificationToken = "[CLS]",
    SeparatorToken      = "[SEP]",
    PaddingToken        = "[PAD]",
    MaskingToken        = "[MASK]",
    UnknownToken        = "[UNK]",
};
BertTokenizer tk = BertTokenizer.Create(vocabPath, options);
```

**第 3 步 · 编码**
```csharp
IReadOnlyList<int> ids = tk.EncodeToIds(text, true, true, true);  // 加 [CLS]/[SEP]
```

### 2.3 配置对应表（照这张表抄，抄错会静默走偏）

| `BertOptions` | `tokenizer_config.json` / `tokenizer.json` | 值 |
|---|---|---|
| `LowerCaseBeforeTokenization` | `do_lower_case` | `false` |
| `ApplyBasicTokenization` | `do_basic_tokenize` | `true` |
| `IndividuallyTokenizeCjk` | `tokenize_chinese_chars` | `true` |
| `ClassificationToken` | — | `[CLS]` → id **101** |
| `SeparatorToken` | — | `[SEP]` → id **102** |
| `PaddingToken` | — | `[PAD]` → id **0** |
| `MaskingToken` | — | `[MASK]` → id **103** |
| `UnknownToken` | `model.unk_token` | `[UNK]` → id **100** |
| `MaxInputCharsPerWord` | `model.max_input_chars_per_word` | **100** |
| — | `normalizer` | `BertNormalizer`（`clean_text=true`、`handle_chinese_chars=true`、`strip_accents=null`、`lowercase=false`） |
| — | `pre_tokenizer` | `BertPreTokenizer` |
| — | `post_processor` | `TemplateProcessing`（`[CLS] A [SEP]`） |
| — | `decoder` | `WordPiece`（前缀 `##`） |

⚠️ `strip_accents` 是 **`null`**，不是 `false`。`BertOptions` 没有直接对应项，沿用官方默认即可（已实测与 HF 一致）。

### 2.4 ★ 已知差异：符号类字符被**静默丢掉**

C# 侧会把下面这些字符**直接删掉** —— **不报错、不产生 `[UNK]`**，输入里就没了：

| 码点 | 类别 | 例子 | HF 给的 id | C# 给的 |
|---|---|---|---|---|
| U+2163 | `Nl` | Ⅳ 罗马数字 | 100 `[UNK]` | **无** |
| U+00B2 | `No` | ² 上标二 | 182 | **无** |
| U+002B | `Sm` | `+` | 116 | **无** |
| U+00D7 | `Sm` | `×` | 190 | **无** |
| U+FFE5 | `Sc` | `￥` | 8101 | **无** |
| U+2606 | `So` | ☆ | 481 | **无** |
| U+2665 | `So` | ♥ | 491 | **无** |
| U+2764 | `So` | ❤ | 506 | **无** |
| U+1F60E | 非BMP/`So` | 😎 | 8105 | **无** |
| U+20000 | 非BMP/`Lo` | 𠀀 | 100 `[UNK]` | **无** |

**不受影响**（与 HF 一致）：汉字（`Lo`）、拉丁字母（`Ll`/`Lu`）、数字（`Nd`，含全角）、标点（`Po`/`Ps`/`Pd`）。
**双方一致地丢**（HF 自己也丢，不算差异）：`Cf` 零宽空格、`Cc` 控制符、`Zs` 全角空格。

⇒ 差异面 = **符号类（`Sm`/`Sc`/`So`/`Nl`/`No`）＋ 所有非 BMP 字符**。

**对策（做一层入参归一，把"静默"变成"可见"）**：在把文本交给分词器之前，先扫一遍，把上述字符**替换成 `[UNK]` 或删掉并计数**，计数记进日志／指标。理由是这一族问题的危险不在"丢"，而在"丢了没人知道"——和 08-15 记的"静默退化成常量向量"同族。

### 5.1 附：AF 那 1.04 GiB 是怎么来的（拆解）

`reranker/config.json`：`XLMRobertaForSequenceClassification`、`model_type: xlm-roberta`、`hidden_size 768`、
`num_hidden_layers 12`、`intermediate_size 3072`、**`vocab_size 250002`**、`torch_dtype float32`。

| 构成 | 参数量 | 占比 |
|---|---|---|
| **词表嵌入**（250,002 × 768） | **192,001,536** | **69.2%** |
| 12 层 Transformer | 84,971,520 | 30.6% |
| 位置嵌入等 | 397,056 | 0.1% |
| 分类头 | 769 | — |
| **合计** | **277,370,881** | 100% |

× 4 字节（float32）= **1,058.1 MB**；盘上实际 **1,060.9 MB** ⇒ 对得上（差额是图结构与 buffer）。

⇒ **体积不是被 ONNX 格式撑大的，是两个选择叠出来的**：
1. **词表大**：XLM-R 是多语言词表，**25 万词**，是中文专用（`bge` 的 21,128 词）的 **11.8 倍**。光这张词表就是 1.92 亿参数、占它自己 **69%**。
2. **没量化**：存 float32。同一份参数转 int8 约 **264.5 MB**（约四分之一）。

对照 `bge-small-zh-v1.5`：**21,575,681** 参数（词表占 50.1%、4 层占 48.6%），float32 = **82.3 MB**，
盘上 90.4 MB ⇒ 同样对得上。两者参数量差 **12.9 倍**。

（复算脚本：`tools/_af_onnx_size_math_20260916.py`）

### 5.2 附：重排器的内存与耗时（实测 AF 盘上那份）

**测法**：每个配置**起一个新进程**跑一次再退出（推理引擎的分配器不保证还给系统，同进程连着测会污染后面的读数）。
探针 `tools/_probe_onnx_mem_20260916/`。环境：本机物理内存 31.2 GB，ORT 1.18.0。

| 模型 | 权重 | 加载后进程 | 首次算 | 再算一次 | 耗时 |
|---|---|---|---|---|---|
| **向量模型** bge-small-zh | 90 MB | **+128 MB** | — | — | — |
| · 1 条 × 512 | | | +1 MB | +0 MB | **26–41 ms** |
| · 20 条 × 512 | | | +1059 MB | +0 MB | **559–616 ms** |
| · 40 条 × 512 | | | +2316 MB | — | 1278 ms |
| **重排器** XLM-R base | **1061 MB** | **+1534 ~ +2495 MB** | — | — | — |
| · 20 条 × 512 | | | +1059 MB | +0 MB | **3261–3392 ms** |
| · 40 条 × 512 | | | +1059 MB | — | 5076–7006 ms |
| · 20 条 × 384 及更短 | | | +1 MB | +0 MB | 177–2376 ms |

**五条结论：**

1. **权重是硬开销，且是常驻**。向量模型加载后进程约 130 MB；**重排器加载后进程 1.5–2.5 GB**。
   从加载到可用都在 **1 秒内**（两次都是 `加载秒=0`）。

2. ★ **有一个约 1 GB 的「台阶」，而且它跟模型多大无关**。
   小模型（权重 90 MB）和重排器（权重 1061 MB）在 **20 条 × 512 首次推理时都恰好多出 1059 MB**。
   ⇒ 这不是模型规模算出来的，是**推理引擎内部分配的一个固定块**。

3. **台阶只由「批量 × 长度」触发，不由条数单独触发**。重排器在 15 / 20 / 30 / 40 条 × 512 下都是同一个 **1059 MB**（不再涨）；
   而长度降到 **384 及以下就完全不出现**（+1 MB）。

4. **台阶是一次性的**，不是泄漏。首次之后同进程再算 3 次全是 **+0 MB**；会话释放 + 回收后进程回落到 **21 MB**。

5. ★★ **真正致命的是时间，不是内存。**
   重排器 **20 条候选 = 3.3 秒**（复跑 7 次，3.26 / 3.31 / 3.32 / 3.36 / 3.39 秒 —— **极稳**）。
   耗时随 `批量 × 长度` **线性**：20 条在长度 32 / 64 / 128 / 256 / 384 / 512 下是
   177 / 365 / 738 / 1509 / 2376 / 3315 ms。
   对照：同一个 20 × 512 输入，**小模型只要 0.56–0.62 秒**（约 5.4 倍差，与 3 倍层数 × 2.25 倍宽度相符）。

⚠️ **读数口径警告**：进程私有内存这个指标**噪声大** —— 同一个模型的「加载增量」在 **1534 / 1667 / 1932 / 2495 MB** 之间跳（差 40%）。
⇒ **内存数只能当量级看，不能当准数**。**耗时那个数是准的**（复跑离散度 < 5%）。

**对 AWAKE 的意思**：重排器要不要搬，**第一道关不是内存，是那 3.3 秒**。
内存还能靠加内存解决；对话里等 3.3 秒才能接一句话，是产品层面的硬伤。
而**小模型这条路内存很轻**：单条查询几乎不额外占（+1 MB），加载后常驻也只有 130 MB —— 完全可以常驻在服务进程里。

⇒ **结论：100 MB 档（约 90 MB 模型）是"只翻一倍"的量级，200 MB 档是"翻两倍多"。这个差别要甲方定。**

### 5.3 ★ 推理会吃几个 CPU 核（09-16 夜补测；「会不会卡游戏」的唯一剩余风险）

背景：内存那条已经用**进程外**（独立 Runtime Service）解掉了。但**进程外只解决内存，解决不了 CPU** ——
物理机就那么多核。这一条此前**没验过**，补测。

探针 `tools/_probe_onnx_threads_20260916/`。量法：跑一次求 `CPU时间 / 墙钟时间`，即**等效占用核数**。
本机 **24 个逻辑核**（`Environment.ProcessorCount`）。

| 输入 | intra 线程 | 墙钟 | CPU 时间 | **占用核数** | 占 24 核 |
|---|---|---|---|---|---|
| **1 条 × 32**（真实查询热路径） | 默认 | 2 ms | ~0.00 s | **≈0**（量不出） | 0% |
| 1 条 × 128 | 默认 | 7 ms | 0.08 s | **11.29** | 47% |
| 1 条 × 128 | 限 2 | 14 ms | 0.02 s | **1.52** | 6% |
| 5 条 × 128 | 默认 | 29 ms | 0.36 s | **12.37** | 52% |
| 5 条 × 128 | 限 2 | 70 ms | 0.14 s | **1.92** | 8% |
| **20 条 × 512**（建语料库那种批） | 默认 | **569 ms** | 6.73 s | **11.82** | **49%** |
| 20 条 × 512 | 限 1 | 2,573 ms | 2.57 s | **1.00** | 4% |
| 20 条 × 512 | **限 2** | **1,312 ms** | 2.61 s | **1.99** | 8% |
| 20 条 × 512 | 限 4 | 751 ms | 2.98 s | 3.97 | 17% |

**四条结论：**

1. ★ **默认设置下，推理会铺满约 12 个核，跟批量多小无关。** 1 条 × 128 是 11.29 核，5 条 × 128 是 12.37 核，
   20 条 × 512 是 11.82 核。⇒ **不是"用时久才占核"，是"一跑就全铺"。**

2. **并行效率很低，边际收益快速衰减。**
   1 核 → 2.57 s｜2 核 → 1.31 s｜4 核 → 0.75 s｜**11.82 核 → 0.57 s**。
   从 2 核加到 12 核，**速度只多 2.3 倍，CPU 消耗多 2.6 倍**（2.61 → 6.73 CPU 秒）。

3. **热路径的绝对时间小到不可能卡游戏**：单条查询 **2–29 ms**。每次对话查一次，这个量级可以忽略。

4. ★★ **要防的是批量那一步**：**569 ms 里吃掉约 12 个核**（占本机 49%）。
   放在游戏运行时做就会明显卡 —— 但**建语料库本来就该离线做**。

⇒ **落地要求（写进实现）**：
- **服务进程必须显式设 `SessionOptions.IntraOpNumThreads`**（建议 **2**，最多 4），**不能吃默认值**。
  代价：单条查询 7 → 14 ms、批量 0.57 → 1.31 秒。**换来的是占 2 个核而不是 12 个。**
- 建语料库的批量推理**离线跑**，或至少限线程后放后台低优先级。
- 可选加强：把服务进程优先级降到 `BelowNormal`（**未验**，留作后手）。

### 5.4 ★ 量化档位：int8 有用，fp16 是反向陷阱（09-16 夜补测）

模型官方仓库常同时挂 f32／fp16／int8／q4 多档。实测结论：

| 同模型对照（`bge-reranker-base`） | 体积 | 加载增量 | 20×512 |
|---|---|---|---|
| f32 | 1061 MB | +1535 MB | **3315 ms** |
| **int8** | **266 MB** | **+497 MB** | **2030 ms（0.61 倍）** |

⇒ **int8 在本机确实有效**：体积 1/4、耗时 0.61 倍、加载内存 1/3。

⚠️ **但 fp16 反向**：`bce-reranker-base_v1` 仓库只给一份 fp16 的 `rerank.onnx`（530 MB），
实测 **5127–5678 ms** —— **比两倍大的 f32 还慢 55%**。原因：x64 CPU 无原生 fp16 算力，ORT 要拆回 f32。
⇒ **落地判据：CPU 上只用 f32 或 int8，不用 fp16。**

⚠️ **量化档名带指令集后缀的，先查本机 CPU**（如 `qint8_avx512_vnni`）。
本机 **AVX512F/BW 有、AVX512-VNNI 无**（`tools/_probe_cpu_20260916/`）。

⚠️ **量化收益随模型变小而衰减**：`mmarco`（H384）f32 1575 ms → qint8 1404 ms，**只快 12%**（体积仍降 1/4）。
小模型的矩阵乘法短，量化的换算开销占比变大。⇒ **别默认"量化一定快"，要按型号实测。**

🚨 **★ 同一份量化档，速度好 ≠ 质量好 —— 量化必须做「质量实测」（09-17 补，最贵的一条）**

上面两条（fp16／指令集后缀）栽在**速度**上，这条栽在**质量**上。同一个 26 条真人问法题集、
同一份代码（CLS 池化 ＋ L2 归一），只换权重文件：

| `bge-base-zh-v1.5` | 语义臂 hit@1 | 无关句「今天午饭吃什么」的最高相似度 |
|---|---|---|
| f32（388 MB） | **19/26** | **0.33–0.37** |
| **int8（98 MB）** | **7–17/26**（加指令时塌到 7） | **0.68–0.75** |

无关句都拿 0.7 分 ⇒ **「什么都很像」⇒ 排序失效**。

诊断（先排掉"是不是我池化选错了"，再定罪）：

| 检查 | `small_int8`（好） | `base_int8`（坏） |
|---|---|---|
| 同句 f32↔int8 余弦 | **0.954–0.965** | **0.477–0.584** |
| 换 mean 池化会不会好 | 更差（0.85） | 更差（0.49–0.57） |
| 判决 | 只是数值近似 ⇒ **可用** | 向量本身换了东西 ⇒ **权重被量化坏了** |

⇒ **落地判据（补第三条）**：**CPU 上只用 f32 或 int8，不用 fp16；用了 int8 还要拿题集实测一遍质量。**
⇒ 两条必须一起做的对照：**① 无关句最高相似度**（高到 0.6+ 就是塌缩信号）
　**② 同句 f32↔int8 余弦**（掉到 0.6 以下就是坏了）。
⇒ 出处：`docs/FEED-20260917-怎么喂与要不要自训.md` §3.1；探针 `tools/_probe_int8_geom_20260917.py`。

完整候选表与评分见 `docs/SURVEY-20260916-重排器候选与评分.md`。
