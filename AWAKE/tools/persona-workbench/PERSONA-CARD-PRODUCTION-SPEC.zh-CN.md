# 角色卡制作规范：从证据到运行时人格

- 版本：v2.1（2026-09-25，有限范围验收修订；尚未切换为工作区现行权威）
- 性质：角色卡制作规范候选替代稿；通过验证并完成入口切换后，接管旧规范中的制作流程、语义质量和完成判定。
- 适用范围：新建角色卡、重写运行时人格字段、根据素材补写人物内容。
- 目的：让作者先建立有证据边界的人物判断，再写成运行时真正可见、能影响人物选择的素材；避免把百科事实、文化标签或作者想象直接变成人物动机。

> **当前仍是候选稿**：README 仍要求执行 `AUTHORING-GUIDELINES.zh-CN.md`，本文件尚未被接入正式入口。未经用户确认并完成入口迁移，不得声称旧规范已被替代。候选稿通过后，本文接管旧规范的“怎么创作、如何判断人格质量、何时可交付”；schema、registry、取证数据、程序和脚本仍是技术事实源，不因文档替代而失效。

## 一、制作的基本单位不是“特征”，而是有边界的人物判断

不要从“他很谨慎”“她重视家族”“这个文化崇尚马”直接扩写人物行为。每项准备进入运行时的内容，都应能回答：

1. **情境是什么？** 人物面对了什么具体局面？
2. **他/她怎么判断？** 关注的利害、风险或责任是什么？
3. **会采取什么选择？** 包括拒绝、拖延、交换条件、沉默、改变主意等可能性。
4. **依据支持到哪里？** 是游戏明文、可核实数据、已批准内容，还是作者推演？
5. **哪些部分仍未知？** 不知道的动机、权限、经历和关系必须留白，不能用“合理”冒充“有据”。

这里不要求每个人物都有复杂心理模型，也不要求每个素材都写成完整因果链。若来源只支持一条事实，就只写那条事实；人物可以简单、沉默、单一或资料不足。

## 二、先建立证据账，再写卡

### 2.1 逐项记录主张，而不是只收集资料

开始写正文前，为每项准备采用的事实或人物主张建立作者侧记录。每张新卡或实质人格改写都必须保存一份作者记录，建议放在 `tools/persona-workbench/docs/authoring-records/<persona-id>.md`。以 `qc/PERSONA-AUTHORING-RECORD-TEMPLATE.zh-CN.md` 为最小表单；它不进入 persona JSON 或玩家运行时。只记录本次新增/修改的主张，未改动的既有主张可引用已审记录。最少包含：

| 项目 | 记录内容 |
|---|---|
| Claim ID / 落点 | 卡内唯一编号（如 `C001`），以及最终 persona 字段和句子/条目；另记 `runtime_required=true/false` |
| 主张 | 准备写进卡里的具体句意，不写宽泛主题词 |
| 来源 | 文件/数据表/官方文本/已批准内容及精确定位（key、ID、行或路径） |
| 来源原文 | 足以复核的原文或数据值；遵守来源授权与项目边界 |
| 能证明什么 | 例如身份、亲属、封地归属、公开事件、明示态度 |
| 不能证明什么 | 例如仅有封地归属，不能因此推出治理权限、税务决策或私人情感 |
| 处理状态 | `SUPPORTED` / `INFERENCE` / `AUTHOR_ADDITION` / `UNKNOWN` / `REJECTED` |
| 审核 | 审核人、日期、结论；补写必须另有批准记录 |

最终卡片中的每个可核查事实、经历、职权、关系和人格因果主张，都必须能反向找到 Claim ID；不能只证明“找过资料”，必须证明“这条具体句子被什么来源支持”。不要把“来源里出现同一个地点”当成人物与地点之间所有关系的证据。不要把文化常见情况自动分配给每个角色。找不到人物层关联时，可以保留世界事实索引供将来检索，但当前人物卡应留白。

### 2.2 结论强度不得超过证据强度

- **来源明说**：可按来源范围写为事实，保留必要限定。
- **多条数据共同支持的有限推断**：写成谨慎、可撤回的推断；不要把推断升级成游戏明文。
- **作者补写**：不能由卡作者自行批准。必须先记录补写理由、适用范围、会影响的 persona 字段/运行时行为，并取得内容负责人或用户的明确批准；批准前只可留在草稿，不得写入候选可交付卡。批准后仍须标为 `AUTHOR_ADDITION`，不得伪装成游戏事实。
- **当前未查到**：标为待查或不写。不能改写成“此人没有”“此人从不”或“与此无关”。

素材与人物的关联至少要区分：仅存在/知晓、确有现实依赖、本人愿为之承担代价。三者是证据描述，不是字段白名单：不能因为关联被标为“依赖”就自动把它写入某个行为字段；仍要判断来源是否支持该行为主张。

## 三、写作前先做人物决策草图

情境草图是帮助作者把证据转成可复核判断的工具，不设最低条数。只记录来源实际支持的判断；没有可写的草图就留空，不得为满足数量补造动机。每个已写草图都必须至少有一个可回溯 Claim ID。草图不是运行时字段。

```text
情境：发生了什么（事实与虚构边界分开）
人物在意/担心：来源直接支持的部分；其余标为未知
可观察选择：他/她会做什么，或现有证据只允许确认到哪一步
代价/限制：选择会牺牲什么；没有依据时明确写“未知”
改变条件：什么新信息或压力可能改变选择；没有依据时不要编造
依据：对应证据账条目
```

草图不是要求所有人物具有相同复杂度、相同道德立场或不同寻常的秘密。多个草图可以体现同一核心关切，但必须是真正不同且各自有据的处境，不能只是替换地名/人物名或改变场景布置。草图答不出来时，缩小主张或留白；一张只含身份资料或一项有据行为的卡，可以在该范围内完成审核，不得因此宣称已验证更广泛的人格，也不得被迫扩写。

### 草图自检

- 把姓名、家族、地点、文化名遮住后，是否仍能看出具体处境与选择？若只剩“重视家族/荣誉/传统”，信息不足。
- 这项判断是否来自这个人物的证据，还是仅来自其文化、阶层或职位？
- 是否把“可能做得到”误写成“有权/会去做”？
- 有没有把同一条世界素材换名后分配给多个人？如果有，逐人查证，不按配额填满。
- 人物如果没有足够材料，是否允许卡片保持简短？必须允许。

## 四、把草图写入正确的运行时字段

当前制作链路的字段映射以 `materialize-definitions.ps1`、`PersonaDataLoader.cs`、`PersonaDslGenerator.cs` 和实际渲染提示词为准。当前代码核实结果：物化器将 `summary` 写入 definition，loader 也读取它；但 `PersonaDslGenerator` 没有消费 `definition.Summary`，因此当前不能声称 `summary` 已进入 DSL/prompt。`core / identityFacts / publicDescription / privateDescription / contradictionDescription / selfClaimRules / realSelfBehaviors / selfClaimExamples / tags` 则由生成器分别进入核心、身份、公开、私我、矛盾等段。作者草稿字段即使存在于 JSON，也不能被当成运行时人格已经生效。每张卡需在作者记录中列出“本次希望生效的 claim → definition 字段 → DSL 段 → 渲染提示词证据”；若字段到 prompt 的链路没有代码证据，该 claim 不得标为 `runtime_required`。

| 字段 | 制作目的 | 应写什么 | 不应写什么 |
|---|---|---|---|
| `core` | 人物最稳定、最能解释其判断的核心 | 有依据的身份性格概括；尽量可落到判断差异 | 空泛美德清单、文化刻板印象、无法区分人物的标签堆叠 |
| `identityFacts` | 帮助模型正确识别人物与关系 | 可核实的身份、亲属、职位、经历等；措辞标清确定性 | 无来源传闻、把作者补写混作史实 |
| `summary` | definition 中的简短总览元数据 | 可供工作台/其他明确消费方使用的压缩说明 | 当前 DSL 生成器不消费此字段；不得把它当作已注入模型的人格材料。若要依赖它影响模型，先修通并验证运行时链路 |
| `publicDescription` | 公开层面可见的身份与表现 | 可被外界观察或公开叙述的内容 | 未公开的私密动机、无据传闻 |
| `privateDescription` | 有依据且适合内部人格提示的私下信息 | 私下顾虑、冲突或限制；证据不足则留空/谨慎处理 | 为了“立体”而虚构秘密、把合理猜测写成事实 |
| `contradictionDescription` | 保留人物真实矛盾或限制 | 两种有根据的倾向如何冲突、在什么条件下偏向哪一边 | 机械制造“表面 X、内心 Y”反转；无条件万能底线 |
| `selfClaimRules` | 约束人物谈及自身时的信息边界 | 哪些话题会避谈、修饰、承认或转移，以及适用条件 | 对所有角色复用同一句隐私/职守模板；规定每次对话固定话术 |
| `realSelfBehaviors` | 提供行为层面的真实倾向 | 有依据、可观察且有场景边界的做法 | 单凭人物属于某地就赋予征税、治理、经营、调兵等权力；预制口号 |
| `selfClaimExamples` | 给模型看人物如何在情境中判断 | 有具体情境与利害的叙事样本；允许叙述、回忆、拒绝、犹豫、改变判断等不同形态 | 台词库、金句集、对玩家的统一称呼、用专名替换的同一故事骨架 |
| `tags` | 选择运行时注册的人格维度提示 | 只选 registry 中确实存在、能由卡片依据支持且互不矛盾的 tag | 未注册 tag、用 tag 代替人物内容、为了“丰富”而全选 |

字段是载体，不是必须填满的表格。某字段没有可靠内容就留空；不得为了满足示例条数、覆盖率或资产消费量而造句。任何草稿字段（如 `tensionAxes`、`commitmentProfile`、各类 `*Profile`、`sourceDescription`）只有在当前代码明确消费时才算运行时内容；否则只服务作者，不可据此声称人格已注入。字段语义变动或链路变动时，先更新代码事实映射，再据此写作，不得靠旧字段说明推断运行时效果。

## 五、让多张卡各自成立，而不是追求表面差异

每张新卡或实质人格改写，都要检索是否存在声明范围重叠、处境相近的既有卡；有可比对象时，至少检查两张或全部可用同类卡（不足两张时标注样本限制）。若卡片只声明身份事实、没有可比较的运行时行为主张，不得为凑对照而扩大内容；记录“无实质重叠范围”即可。比较对象按人物处境、职位、亲属/政治位置选择，不按“凑齐文化代表”选择。横向复核不是要求所有人物用不同词，而是检查相近范围内是否只换槽位复用相同选择与理由。

优先检查：

1. **选择是否可互换**：同一冲突中，两人是否总是采取同一行动、给出同一理由、接受同一代价？
2. **素材是否只当装饰**：删去地名/物产后，判断完全不变，且该素材没有真实人物关联时，不应把它塞进人格字段。
3. **句式是否成批复制**：不只查逐字重复，也查“先 X 再 Y”“只 X 不 Y”等可变插槽骨架，以及相同起手、转折、收尾姿态。
4. **是否为反差而反差**：不能为了区分人物，给每个人强配一条独特怪癖、秘密或底线。
5. **差异是否有证据**：语言差异或决策差异若来自作者选择，应在作者侧标记，不冒充来源事实。

如果相近人物确有同一项来源支持的做法，不必为追求“每人不同”而改写成反差；反过来，若共同做法没有人物层证据，也不能保留成共享模板，再要求作者只替每人编造不同理由。正确处理是撤下无依据的共同运行时主张，分别按各自证据留白或重写。

机械相似度只能定位线索；不以“每种文化必须有多少种句式”“每人必须消费几条素材”或未经校准的重复率数字作为质量结论。语义同质化按第 7 节的盲测协议判定，不能由作者自行勾选“已检查”。

## 六、完成前按真实载荷复核

每张新卡或发生实质人格改写的卡，完成顺序如下：

1. 校对证据账与身份归属；证据不足的主张删去、降级或标待查。
2. 写好运行时字段；检查没有把作者草稿误当运行时内容。
3. 运行现行 schema、归属、文本及项目要求的其他硬门禁。具体命令以 `README.md` 和 `AUTHORING-GUIDELINES.zh-CN.md` 当前版本为准，不从本文复制过期命令。
4. 用临时目录运行物化器。`materialize-definitions.ps1` 会清空 `-OutDir` 中的 `*.definition.json`，不得把它指向含有需要保留文件的目录。
5. 确认 definition 含预期字段与已注册 tags；运行真实 DSL 生成器和真实模板渲染。保存 DSL 和渲染提示词。必须确认每个标为 `runtime_required` 的 Claim ID 都仍可在最终渲染提示词中定位；只看 definition 有字段不算通过。`UsedLegacyFallback=true`、未注册 tag、必需 claim 缺失均阻断。`WasTrimmed=true` 时逐项检查裁剪结果；关键 claim 被裁掉即失败。不得手抄 DSL 或提示词。`chain` 报告中的 `definition_field_diagnostics` 只说明物化字段分布；AI 感的载荷读数看 `runtime_dsl_sections` / `runtime_dsl_metrics`，它从实际 DSL 的 `DATA_CN` 行解析，绝不把只存在于 definition 的字段算作模型输入。生成器会把若干原始字段合并成 DSL 段，因此该统计能证明“进入 DSL”，但不能单独证明每段内容的来源字段；主张落点仍须靠 Claim ID 和最终 prompt 核对。
6. 对目标卡和可比卡使用相同四类情境：日常/身份、利益冲突或代价、质疑、事实不足。每个情境各采样两次；记录模型、参数、种子、模板/卡片哈希和原始输出。比较只针对各卡声明范围内、且证据允许判断的重合问题；资料未覆盖的情境用于检查是否诚实承认未知，不得要求作者补写答案。角色输入仅允许替换必要的玩家/NPC 标识，不得给目标卡额外提示。
7. 至少由一位未参与该卡写作的复核者盲评；作者自评和同一人换顺序重读都不算独立复核。每张卡由一位独立复核者给出范围内 `PASS` 是默认可交付路径，不因资源少自动要求第二人。若复核者对证据边界标 `INDETERMINATE`、存在未获批准的 `AUTHOR_ADDITION`、匿名失败，或作者对负面结论提出有证据的异议，则升级第二位未参与写作的复核者；升级前不得 `approved`。匿名代号须随机映射，展示顺序打乱；第一轮提供匿名目标卡及可比卡（如果声明范围内存在可比对象）的运行时载荷与模型回答，并附目标卡匿名声明范围/未覆盖范围；不提供姓名、家族、地点、文化、作者说明或素材来源。若模型输出/载荷中含专名，先用一致占位符去标识，再由不参与第一轮评审的检查人确认没有明显身份线索。评审者先锁定判断，再查看去身份化的实际 prompt 输入和 Claim ID/来源证据表核事实。
8. 每位复核者逐个样本标 `PASS / ISSUE / INDETERMINATE` 并引用原文，分别判断：是否回应问题；在声明范围及卡间重叠范围内，选择、理由或适用条件是否有可区分证据；文本是否只替换名词而沿用同一决策骨架；样本是否复用同一开头、转折、两段式/三段式推进或结尾姿态；来源是否支持对应主张。若不存在范围重叠或卡片只含身份事实，人物差异项标 `NOT_APPLICABLE_WITHIN_DECLARED_SCOPE`，不得要求作者增写行为。身份名、家族名、地名或文化符号本身不能作为“人物可区分”的理由。若称“句式相似”，必须引用至少两条具体文本并指出相同骨架，不接受只写“像 AI”。对于 `unknown` 情境，逐句对照该样本最终 prompt 实际提供的知识、记忆和角色资料：不得把模型参数中的常识、合理猜测、未知传闻当成本轮已知事实。擅自点名嫌疑人/家族/部族、编造动机或地点活动、声称“刚查过”或“收到消息”，均是事实越界，除非输入确实提供了对应证据；答案可以明确不知道、询问线索或说明需要查证。若多个角色都发生同类越界，应优先归因共用提示词/运行时层，不能要求作者把未经证实的细节写进角色卡来让输出看似有据。
9. 出现任一事实越界、无据职权/经历或在声明范围内关键问题未回应，结果为 `REVISE`。一位复核者能引用目标卡与比较卡至少两条**不同情境的真实回答**，证明它们只替换名词/插槽、传达相同决定和理由，即足以判 `REVISE`；该比较只在两卡都声明覆盖的重合范围内成立，不得因一张简单卡没有覆盖某情境而判其失败。不要求第二人重复同一判断。单有共同句式、单个重复句、同文化或同职业，不足以阻断；若相似只体现在句型而选择/理由不同，应记为待看线索，不判失败。证据边界、匿名或人物差异确实无法判定时标 `INDETERMINATE` 并升级第二评审；第二人仍无法澄清、两人结论冲突或判断依赖专名/文化符号时，补证或重测前不得通过。若作者声明的范围超出证据可支持的部分，应缩小范围或删除该主张；这不自动否定仍有依据的身份卡/有限行为卡。
10. 返修时先定位责任层（素材/证据、tag、物化、DSL、模板、情境、模型），一次改一个层面，保留原失败样本；用同一固定集重跑。只有全部硬门和盲评为 `PASS`，才可按正式入口更新 `approved`。离线测试不等于游戏内验证。

### 结果记录最少项

- 卡片路径与 SHA-256；
- 主张/证据账位置及未决项；
- 物化 definition、tag 注册结果、DSL 与渲染提示词的哈希或可回放文件；
- 测试模型、采样参数、情境输入、原始输出；
- 盲评者对“回应问题、人物差异、事实边界、表达自然”的逐项判断及引用；
- 发现的问题、归属层、修改动作、复测结果；
- 证据等级及尚未完成的门禁。

盲评以 `qc/PERSONA-BLIND-REVIEW-TEMPLATE.zh-CN.md` 记录：三张卡的选择理由、每个情境两次采样、匿名映射和独立复核结论；触发升级时，第二位评审须另填表且先不看第一人的结论。匿名映射表与第一轮评审包分开保存；第一轮包不得含原始文件名、heroId、姓名、家族、地点、文化、来源账或能直接反查身份的提示词字段。第二阶段再提供逐样本去身份化的检索知识、记忆和场景输入，以验证模型是否凭空补事实；不能只给“source absent”结论而不给实际输入范围。任何人不得把平均分、总分或“读起来不错”替代阻断项判定。若工具尚不能安全产出匿名包，作者必须手工去身份化并由另一人检查泄漏；不得把含身份信息的原始 chain JSON 直接发给盲评者。

## 七、返修时先改原因，不先美容

| 现象 | 优先排查 | 合理修复 |
|---|---|---|
| 人格段消失，只剩身份名 | tag 是否注册、真实 DSL 是否 fallback、定义是否加载 | 修复载荷/注册或加载问题，再重测；不要先润色空卡 |
| 多人决定与理由都相同 | 证据账、草图是否独立，是否套用同一情境模板 | 重做具体人物判断；不能仅替换文化名词 |
| 回答反复复述卡片原句 | 样本是否像口号/台词、统一提示词如何要求吸收样本 | 把台词改为有情境、利害与限制的判断素材；对照真实提示词复测 |
| 无依据地谈某地治理、经济或职权 | 来源实际证明范围与人物关系 | 撤回越界主张；单有地点关联时不推定权限或动机 |
| 机械指标变好但盲读仍撞脸 | 指标是否只测词面变化、样本是否同一决策骨架 | 将指标降级为检索线索，保留语义盲评与反例测试 |
| 盲读不相似但事实错误 | 取证流程 | 先修事实；“更有个性”不能抵消失实 |

不允许通过近义词替换、加长句子、打乱标点或添加专名来伪造“去 AI 味”的改善。

## 八、通过状态与现有门禁的处理

每张卡的最终质量结论必须且只能是以下之一。结论针对作者记录中**明确声明的使用与刻画范围**；不得把 `PASS` 扩写成“人物已被完整刻画”或“模型在所有情境都能稳定扮演”。

按以下顺序判定，不能用后面的“可读/可生成”抵消前面的阻断：

1. **链路证据先行**：已知 `runtime_required` Claim 未出现在最终渲染 prompt、发生 legacy fallback、或存在未注册 tag，均为 `REVISE`，不得 `approved`；若链路根本未运行或报告不完整，记 `INDETERMINATE`，不能当作已通过。
2. **事实边界其次**：已写入运行时的事实、关系、职权或动机超出证据时为 `REVISE`。来源缺少不等于可以由作者补写。
3. **范围与证据分开判断**：作者记录须说明本次卡片拟支持的范围（例如“身份事实”“身份事实 + 一项有来源行为”或更广范围），并列出边界/未知项。可靠来源只支持较窄范围时，应先缩小声明范围；不能因草图只有一项、字段为空或情境数量少就把整张卡判为 `INSUFFICIENT_EVIDENCE`。若作者坚持声称超出证据的动机、职权或决策规律，对应主张必须删除或补证；不得靠场景拆分制造证据。
4. **最后才判断 `PASS`**：只有证据足以支撑所声明范围、硬门与最终载荷完整、盲评和记录均通过，才可 `PASS`。JSON 合法、字段不空、模型能生成回答，都不能单独证明范围内人格质量通过。

| 证据与声明范围 | 结论处理 |
|---|---|
| 证据只支持身份事实或少量明确行为；作者将范围如实限定 | 可取得范围内 `PASS` 并按流程申请 `approved`，前提是该范围的事实、载荷、未知情境处理和盲评均通过；不得宣称完整人格认证。 |
| 作者声明范围超过证据，或写入了无据动机/职权/行为 | 对越界主张 `REVISE`；删除或缩窄后重新审核。不得靠场景拆分或改变场景布置制造证据。 |
| 链路或盲评材料不足以判断声明范围 | `INDETERMINATE` / `PROVISIONAL`；补证之前不可 `approved`。 |

例如，资料只确认人物身份/职位和一项有来源的日常做法时，可以把卡片声明为“身份 + 该项行为”，不必补第二个行为。只要该窄范围的运行时载荷、事实边界、未知问题回答和独立盲评通过，就可在此范围内 `PASS` / `approved`；这不代表其野心、私人动机或其他情境已经被验证。若作者希望声称更广泛的人格特征，就必须为新增主张另找证据并重测。

| 结论 | 含义 | `approved` |
|---|---|---|
| `PASS` | 事实、技术链路、盲评与记录均在声明范围内通过 | 可按项目状态流程申请；仅批准记录中的范围，不代表完整人格认证 |
| `REVISE` | 已发现可定位缺陷 | 不可 |
| `INDETERMINATE` | 评审冲突、脱名判断依赖专名、样本/运行链不完整 | 不可；补证或重测 |
| `INSUFFICIENT_EVIDENCE` | 对某项主张或作者想扩大的范围，可靠来源不足 | 不可批准该项主张/扩展范围；应删除或缩小范围。若缩小后的卡片独立满足各项门槛，仍可对窄范围另行判 `PASS` |
| `PROVISIONAL` | 只有作者自评，或缺少本规范要求的独立复核；两轮自读不改变该状态 | 不可；取得独立盲评后再定结论 |

当前 persona schema 的 `status` 只有 `draft / translated / review / approved`，不编码批准范围。因此，`approved` 只表示该卡在作者记录绑定的卡片 SHA-256 与声明范围内获准；范围记录必须与源卡一起留存在工作区。若范围记录缺失、哈希不匹配，或交接/发布时无法随卡追溯，则 `approved` 不可被解释为完整人格认证，且该卡须退回 `review` 重新确认范围。

## 九、规范边界与维护
